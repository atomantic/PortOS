# Unreleased

## Code Review Defaults
- **Each code reviewer can now be pinned to a reasoning-effort tier.** The reviewer table already let you pick which model a reviewer runs; how *hard* that model thinks was stuck at whatever its CLI defaults to, so the only way to buy a more careful review (or a cheaper, faster one) was to change the model. Every reviewer row now has an Effort column alongside Model, on the AI Providers → Code Review Defaults panel, the task form, the CoS schedule config, and the `/do:next` run drawer. Each row offers only the tiers that reviewer actually accepts — Codex's `minimal`…`ultra`, Claude's `low`…`max`, Antigravity's `low`/`medium`/`high`, and `low`/`medium`/`high` for the local LM Studio / Ollama reviewers — so the picker can't offer a level the CLI rejects, and Copilot, Grok, and `@username` reviewers show no control at all because they have no such knob. Because slashdo's `--review-with` grammar has no effort suffix, the pinned tier travels on the invocation instead: as `codex -c model_reasoning_effort=high` / `claude --effort high` / `agy --effort low` when an agent drives the reviewer CLI, and as an `effort` field on the local review request when PortOS runs it. Leaving a row unset keeps that reviewer's own default, exactly as before.
- **[issue-3606] A Review Loop reviewer whose CLI isn't installed is now flagged up front.** Previously the only way to find out a configured reviewer (Claude, Antigravity, Codex, or Grok) couldn't actually run was to wait for the review loop itself to discover its command was missing — after PortOS had already opened the PR and spent an agent run. The Code Review Defaults panel, task form, schedule config, and `/do:next` run drawer now show a "not installed" badge next to any reviewer whose CLI binary isn't found on this machine. It's informational only — the reviewer stays selectable, since a federated peer machine (or a later install) may still be able to run it.

## Cursor Agent provider
- **[issue-3615] "Refresh Models" now works for Cursor, and pulls your account's real catalog.** The Cursor providers shipped with a hand-curated 27-model slice, and the Refresh button was hidden for them because nothing on the server could answer — so the only way to reach a model Cursor offers you but PortOS didn't list was to type the id into the provider's model list yourself. Refresh now asks the binary directly (`cursor-agent models`) and stores everything it reports: 177 ids on a current account, including the `-fast` priority-compute twin of most tiers, and Cursor's own `auto` router at the top. Because that catalog varies by account, plan, and binary version, it's the only authoritative answer — which is also why a refresh that can't reach `cursor-agent` (not installed, or not on the server's PATH) reports the failure and leaves your existing list untouched, rather than quietly re-saving the shipped 27 and telling you it refreshed. The button appears for both the CLI and TUI providers, since `--model` applies to interactive sessions too.
- **A failed "Refresh Models" now tells you what actually went wrong.** Every refresh failure — any provider, not just Cursor — used to surface as "Provider not found or not an API type", which is simply false when the provider exists and its type is fine; the real reason (the binary isn't on the server's PATH, the endpoint timed out, that CLI has no catalog to fetch) only ever reached the server log. The toast now carries the actual message. A model list that comes back legitimately empty still saves as empty — an empty answer and a failed one stay distinguishable, which is the whole reason a failed probe refuses to fall back to the shipped list.
- **A provider whose *name* mentions another vendor is no longer refreshed against the wrong catalog.** Refresh picked its fetcher by checking the display name for vendor words before checking which binary the provider actually runs. So naming a Cursor provider "Cursor Claude Opus", or an Antigravity provider "Antigravity Claude Sonnet 4.6" — the natural name for a second provider pinned to that model, and Antigravity's own catalog does list Claude models — silently replaced its model list with Anthropic's, ids those tools reject. In the Antigravity case it also dropped the "use agy's own configured default" entry while the provider was still set to it, which blanked the model dropdown and read as though nothing was selected. The binary a provider runs now decides, and only falls back to the name when no binary matches.

## Added
- **Cursor's agent CLI ships as a provider, in both CLI and TUI flavors.** `cursor-agent` is a harness-capable coding agent, but PortOS had no entry for it — using it meant hand-rolling a custom provider and guessing at its flags. It now ships as `cursor-cli` (headless one-shot) and `cursor-tui` (interactive PTY), mirroring the Codex/Antigravity/Grok/Kimi pairs. Both ship disabled, so nothing changes until you enable them, and once enabled they're selectable anywhere a process provider is — CoS agents, runners, pipeline stages, TUI sessions. The headless path runs `cursor-agent --print` with the prompt on stdin; the TUI path runs the interactive agent. Both inject `--force`, which is doing more work than the name suggests: besides auto-approving tool calls, it clears Cursor's workspace-trust gate, and without it `cursor-agent` prints "Workspace Trust Required" and exits — which in a fresh CoS worktree is every single run. The model list is a 27-entry slice of the account catalog (Composer, Claude, GPT, Gemini families), each id verified against the live binary; the default is Cursor's own `auto` router, so unlike Grok/Kimi/Antigravity no configured-default sentinel was needed. Cursor bakes reasoning effort into the model id (`…-thinking-high`, `…-xhigh`, `…-max`) rather than exposing a flag, so no Effort control is offered for it. Existing installs pick the pair up on restart via migration `231-cursor-providers`. If your account offers a model outside the shipped 27 (the full catalog runs to 177 ids, most of them `-fast` twins), "Refresh Models" pulls the whole list from the binary — see above.

- **X account diagnostics and review-gated compose handoffs.** Comms now has an X page that stores bounded public snapshots, checks profile/search visibility and post reach through the managed browser, captures visible metrics, and routes drafts through Review Hub before opening X for a final manual submission. It does not store X credentials, post automatically, or claim that ordinary low reach proves a shadowban.
- **Stacker News triage is newest-first and action-oriented.** Each community sync is capped to a configurable newest-item count (30 by default), preserves source timestamps for stable ordering, captures direct image posts for Ollama vision analysis, and gives every newest item explicit reply, zap-handoff, moderation-handoff, and analysis actions behind the existing human review gate.
- **The claim-issue author gate has a "Me + collaborators" setting.** Until now the only way to let an agent work on a teammate's issue was "Any author", which also opens the queue to drive-by issues from strangers — so a repo with any real collaborators had to choose between ignoring their issues and claiming everyone's. The new option trusts you plus every account the forge already grants access to (GitHub collaborators, GitLab project members including group-inherited ones), which is the same set that could push the code anyway. It sits between "Filed by me only" (still the default) and "Any author" in the CoS → Schedule author-filter dropdown, in the per-app override, and in the `/do:next` run drawer, and applies to `claim-issue` and `claim-work` alike. Neither CLI's `--author` flag accepts more than one account, so the gate is applied to the issue listing rather than pushed into the query — both the work detector and the agent prompt resolve the trusted set first, then filter. If that lookup fails (a token without push access can't read the collaborator list), PortOS reports it and retries rather than quietly narrowing back to your own issues or widening to everybody — and because that failure repeats identically on every retry, both the run drawer and the "Run now" toast name the filter and the way out instead of the generic "try again shortly".

## Changed
- **[issue-3618] A newly added coding-agent provider can no longer silently miss one of the steps that launch its interactive session.** Adding a vendor means teaching several independent launch steps about it, and forgetting one is invisible from the outside: the provider appears in the picker and spawns, then either runs the wrong binary or comes up without the flags that let it work unattended and stalls on its first approval prompt with nobody there to answer. A test now walks every provider in the shipped catalog through those steps, so a vendor any of them doesn't recognize fails in CI instead of in a dead agent session. No shipped provider's behavior changed.

## Fixed
- **A `--model` you baked into a TUI provider's own arguments is now honored instead of silently overridden.** The CoS-agent TUI spawn path respected a hand-pinned `--model` for OpenCode providers only; for every other TUI it appended the UI's model choice as a *second* `--model` flag, and last-flag-wins meant your pin was quietly discarded (or the CLI rejected the duplicate outright). It now honors the pin for every provider, matching what the one-shot TUI path and the CLI path already did, and what the rest of the app documents. This only affects providers whose saved arguments hand-pin a model — no shipped provider does.
- **The AI Providers page no longer offers "Refresh Models" on providers the server can't refresh.** The button's visibility was decided by a deny-list of command names that had drifted from the server's actual dispatch, so Codex and Kimi Code — both shipped providers — showed the button and produced an error toast on every click. It is now an allowlist mirroring that dispatch's real shape: routed on provider type first, then the same per-vendor tests the server applies — including that its TUI path, unlike its CLI path, never consults the provider name. A test walks every shipped provider against a transcription of the server dispatch, so the next provider added without a matching client branch fails there rather than in the UI. (One deliberate non-change: the server matches `claude`/`gemini` on the *exact* command string, so a renamed provider pointed at an absolute binary path still shows no button — widening both sides is tracked separately in #3616 rather than making the client optimistically disagree.)
- **On a Bedrock box, a TUI provider that isn't Claude Code no longer has its model id rewritten.** Claude Code on AWS Bedrock needs region-prefixed model ids (`global.anthropic.claude-opus-5`), so PortOS rewrites bare Claude ids just-in-time when `CLAUDE_CODE_USE_BEDROCK` is set. That rewrite keyed only on the *model id* containing "claude" and was applied by default to every TUI provider — so any vendor that labels Anthropic models under its own ids got captured by it. Cursor is exactly that case: `claude-opus-5-thinking-high` would have been sent to Cursor's router as `global.anthropic.claude-opus-5-thinking-high`, an id it has never heard of. The rewrite now keys on the launch command actually being Claude Code, which is what it always meant. Two independent copies of that model-injection step (the one-shot TUI prompt path and the CoS-agent TUI spawn path) had already drifted apart on this; both now share one implementation, so the next provider can't be fixed in one and missed in the other. No shipped provider's behavior changes; a *custom* TUI provider running a non-`claude` binary against a claude-ish model id will stop being rewritten, which is the correct result for a non-Claude-Code binary.
- **The Antigravity card on the Usage page loads quota again after `agy` 1.1.x renamed its limit rows.** The `/usage` panel still groups Gemini / Claude+GPT windows the same way, but each window header grew a trailing "Remaining" (`Weekly Limit Remaining`, `Five Hour Limit Remaining`). The parser required the line to end on bare `Limit`, so it found the groups and returned zero meters — the card looked broken with "No quota data found." Both the new labels and the older bare-`Limit` form parse to the same keys.
- **Grok and Kimi agents now actually start, and an agent that fails to spawn says why.** Picking the Grok or Kimi provider for a CoS agent produced a task that never opened a shell: the durable agent runner keeps an allowlist of CLI commands it is permitted to spawn, and `grok` and `kimi` were never added to it even though both ship as selectable providers. Both are allowlisted now, and a test keeps that list in step with the shipped provider catalog so the next provider added without an entry fails in CI rather than in a silent agent. The reporting around it was the worse half of the bug: a rejected spawn was logged and dropped, never reaching the agent record. A TUI agent sat in "initializing" for a minute until the zombie sweeper finalized it as "Agent process terminated unexpectedly" — a message that named no cause — and the CLI equivalent was worse still, staying "working" indefinitely because the stale in-memory entry made every cleanup sweep skip it. Both paths now finalize immediately with the runner's actual error, the runner names the offending command instead of returning one opaque "missing or invalid fields", and an agent reaped without ever having recorded a process id is reported as never having started rather than as a crash.
- **The labels on LoRA training dataset images are readable again.** The source chip ("upload", "generated", "sheet crop", "gallery") and the view label ("front three-quarter") were tinted overlays — 20%-opacity color on top of whatever the training image happened to be — so over a bright photo, or under a light theme, the text all but disappeared. They were also pinned to opposite corners of the thumbnail, so a long view label collided with the source chip in a narrow column and the two printed on top of each other. Both chips now carry their own near-opaque plate with light text, and they share one wrapping row so a long label drops to a second line instead of overlapping.
- **The Antigravity code reviewer no longer looks like it isn't installed.** Antigravity's command is `agy`, but every agent prompt named the reviewer by its internal slug, `antigravity` — a command that exists on no machine. A review-loop agent went looking for it, found nothing, concluded there was no reviewer available, reviewed its own work instead, and merged the PR. Prompts now name the actual command, and a reviewer whose command genuinely isn't installed blocks the merge with a note on the PR instead of quietly being replaced by a self-review.
- **Pull requests opened by a CoS agent under a "merge when CI is green" policy now actually get merged.** The check that watches those PRs only ran when an app's optional "PR Watcher" scheduled task fired — and that task ships disabled, since its default prompt is a review-and-comment agent most setups don't want. So PortOS was queueing green PRs into a list nothing ever read: they sat open indefinitely, and because the retry counter never advanced, the safety net that gives up and notifies you after a few hours never fired either. The watch now runs on the normal CoS cadence, independent of that task.

## Internal
- **The six provider-seed migrations share one shell instead of six copies of it.** Every migration that ships a new AI provider to already-installed setups (OpenCode Ollama, its TUI sibling, Grok, Cerebras, Kimi, Cursor) repeated the same byte-identical read → validate → add-missing-ids → write body, so any hardening of it was a six-file sweep nobody did — and none of the six had picked up the reserved-key guard (`__proto__` / `constructor` / `prototype`) the split-migration family already applies. They now call a shared `makeProviderSeedMigration` factory that carries that guard, and each migration keeps only its own frozen provider payload, since a migration is the historical record of what it installed. Their duplicated shell tests collapse into one suite against the factory; every payload assertion each migration already made still runs unchanged.
- **Whether a provider can refresh its model list is now the server's answer, not the client's guess.** The "Refresh Models" button used to be gated by a hand-written client-side re-derivation of the server's model-refresh dispatch — a mirror kept in step by a comment, backed by a parity test that transcribed the same dispatch a *second* time (so it only ever proved the mirror matched the test's copy). It drifted, silently, in both directions: too generous showed a button that errored on every click, too stingy hid the feature with no error at all. A gemini provider configured by absolute path was in the second bucket. The server now derives the answer from one per-vendor table and sends it on the providers payload as `canRefreshModels`; the client just reads it. The three keying conventions that had accumulated as prose above each branch (exact command string, path-tolerant command basename, display-name substring — and which of them a TUI provider is allowed to use) are columns in that table now, so adding the next vendor is one row instead of four coordinated edits across two repos' worth of files. The field is computed per response and never stored, so it can't go stale against the dispatch it describes. No shipped provider's button visibility changes; the one behavior that does is that a provider whose *command* is literally `gemini` now refreshes as gemini even if someone named it "Claude Something", which is the same "an exact command beats a display-name substring" rule the dispatch had already grown for cursor and Antigravity.
