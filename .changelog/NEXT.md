# Unreleased

## Stability

- **[issue-3703] A worktree agent is no longer failed for commits it didn't write.** The primary-checkout guard used to fail any worktree agent whose run window overlapped commits landing on the shared primary checkout — but a concurrent coding-on-main agent, your own terminal, or `update.sh`'s pull can move it too, so read-only reasoners and correctly-behaved agents were being blamed and escalated to you. The guard now attributes the stranded commits by patch-id (`git cherry`, so a cherry-picked or rebased copy still counts) to the agent's own branch: only commits actually traceable to that agent fail the run. Everything else is warn-logged — the unreviewed commits on the primary are still surfaced — but a run that didn't cause them stays a success.

- **[issue-3704] The UI no longer goes blank when iCloud offloads a synced file** — macOS "Optimize Mac Storage" can evict MortalLoom and Obsidian files to the cloud. Reading one of those offloaded files used to stall indefinitely, and a handful of stalls was enough to freeze every page in PortOS while the server still looked healthy — pages simply never loaded and only a restart brought them back. PortOS now detects an offloaded file up front, skips the read, asks iCloud to download it in the background, and reports "temporarily unavailable" for just that record until it arrives.

- **[issue-3706] Saving a note that iCloud has offloaded no longer risks freezing the UI.** [issue-3704] stopped offloaded files from stalling PortOS when they were *read*, but saving over one was still unguarded — and measuring it showed that overwriting an offloaded note stalls exactly like reading it, even though the save replaces every byte of the file. That matters more than a manual save: your Brain daily-log mirror and YouTube transcript ingest write notes on their own schedule, so a stuck iCloud could have frozen every page with nobody at the keyboard. PortOS now checks before saving, asks iCloud for the note and waits briefly, and if it still hasn't arrived reports "temporarily unavailable" for that one note — leaving its existing contents untouched — instead of hanging. Background mirrors skip that note quietly and pick it up on their next pass.

- **[issue-3706] Re-ingesting a YouTube video no longer loses track of its existing vault note.** If the note had been offloaded by iCloud, the mirror was skipped — and the skip was recorded as "this video has no note", which stranded the existing note where deleting the ingest could never clean it up, and made the next re-ingest create a second note at a fresh date. A skipped mirror now keeps the existing note's location and simply retries next time.

- **[issue-3706] "Re-sync all entries now" stops early when the vault is unavailable instead of grinding for hours.** With a stuck iCloud, every entry waited up to 20 seconds before being skipped, so a full re-sync of a long daily-log history could run for hours with no way to cancel it. It now stops after a run of consecutive failures and reports that it stopped, so you get an answer in seconds and can fix the vault first.

- Internal: [issue-3706] the awaited `brctl download` used before an overwrite moved out of `mortalLoomStore` into the shared `icloudFile.materializeAndWait`, now that Obsidian's `updateNote` needs the identical bounded materialize — the second caller is what earned the extraction. It also no longer throws when `spawn` fails synchronously (EMFILE under load), which would otherwise surface from a save as a raw spawn error instead of the handled refusal. The module docblock gained a measured syscall table — `stat`/`open`/`rename` never materialize a dataless file, while `read`, `write` (including after `O_TRUNC` — truncating does **not** skip the download), `link`, and `clonefile` all do — so the next reader doesn't re-derive it from first principles and reach the intuitive, wrong conclusion.

- Internal: [issue-3705] the MortalLoom store's boot/settings-change eviction pin no longer carries its own copy of the `brctl download` spawn/detach/exit-handler plumbing — it now delegates to the shared `icloudFile.requestMaterialization` helper the read paths already use. The helper gained an explicit dedupe policy (`retryAfterExit`): the read paths stay tracked in its capped in-flight map so a later read can retry, while the pin opts out and keeps its own single-sticky-path dedupe (re-pin only when the configured path changes) plus an `onFailure` hook that clears the sticky path so a failed or killed pin can retry. The once-per-process "brctl not found on PATH" warning also folded into the shared flag, so it fires at most once across the pin, read, and write paths rather than once per caller. ~40 lines of duplicated spawn plumbing removed. Two small, deliberate behavior changes come with the consolidation: the pin now inherits the shared 120s download deadline (a wedged boot pin is SIGKILL'd and left to the next `settings:updated` to retry, instead of lingering unref'd forever), and it now only spawns `brctl` for genuine iCloud (`/Library/Mobile Documents/`) paths rather than any macOS path — the pin exists solely for the iCloud store, so a non-iCloud configured path is no longer handed a doomed `brctl download`.

## Added

- **Series Autopilot now builds characters before it spends on plot.** A new pre-arc planning stage completes the core cast's causal Ghost → Wound → Lie → Want → Need engines, distinct voices, secrets, relationships, and provisional whole-series transitions before the macro arc is generated. Arc planning then treats those foundations as plot engines: external turns must force character choices rather than inventing a plot and asking late repair passes to retrofit motivation. The existing full-foundation gate remains after the issue-level synopsis plan, where it acts as reconciliation—preserving established identities and adding at most a small number of genuinely story-required characters—so character and story can still change one another without repeatedly rebuilding the expensive arc.

- **Three.js Models now tells you the truth about rigging.** Every generated model was described as "animation-ready", including characters — but the spec holds a parts hierarchy and sockets, never a skeleton, a bind pose, or a deformation contract, and PortOS does no skinning at all. A character spec can now declare a bounded, optional **articulation graph**: stable joint ids, exactly one root, each joint naming a parent declared before it (so a cycle or a dangling parent is unrepresentable rather than merely unlikely), a named pivot socket per joint, and an explicit list of parts that are *carried* rather than articulated. An impossible graph is rejected outright at generation — two roots, a duplicate joint id, a joint pointed at a part or socket that does not exist, one part driven by two joints, or a part declared as both an attachment and a joint — and only a graph that passed reaches the exported factory's runtime metadata. Alongside it the record now stores a rig-readiness report, and it is honest in both directions: a model with no graph reads **static assembly** with the reason attached rather than a silent pass, and a graph that validates but rigs into nothing (a lone root, or child joints with no pivot axis) is reported the same way. The detail page shows the verdict, the joint/pivot/attachment counts and the reasons; the preview badges static versus articulation-ready and names the joint driving whichever part you click. The generation prompt asks for the contract only when the subject could be a character — a vehicle, weapon, architecture or device family, or a refinement of a spec already classified as an object, leaves the prompt exactly as it was. Models generated before this shipped have no graph and no report; they read as static and unevaluated, never as rigged. Deliberately out of scope: automatic skinning, external rigging models, and generated GLB assets.

- Video Gen **can now finish a draft**. A fast, low-step model is the right way to find a shot, but the only way to then render it properly was Remix — which reuses the settings you had, so the delivery render came back as a *different* composition unless you noticed the seed and moved the model yourself. Video cards in Recent renders now show a **Finish** button that reloads the draft's prompt, negative prompt, size, frames, fps and — critically — the exact seed it actually rendered with, then switches the model to the full-quality sibling the registry declares for it and clears the draft's 4-step sampler so the delivery model uses its own. Nothing starts on its own: Finish only fills in the form, and you press Generate. The button appears only where it can honestly deliver the same shot — the draft model must declare a delivery pair (same weights, same runtime, differing only in step budget, not merely a similar name), that model must be installed here, and the render must be reproducible from the record alone. Image-, keyframe-, extend-, audio- and reference-conditioned drafts don't offer it, because their conditioning input isn't something PortOS keeps a durable copy of; renders made before this release don't either, since their records can't say for certain what steered them. Every render from now on records the seed it resolved to (random seeds included) and an inventory of what conditioned it — kinds only, never upload paths.

- Series Pipeline **Autonomous mode** gains an **"Unlock everything this series owns first"** option. A locked arc, volume, issue stage, or canon entry makes the corresponding fix path throw or silently skip, so a run would surface an editorial finding and then pause on a problem it was never allowed to resolve — leaving you to hunt down every lock toggle by hand before re-running. With the option on, the run's first step clears the arc freeze, the per-field arc locks, every volume lock and every issue stage lock, then reports exactly what it cleared and what it deliberately left frozen. Two boundaries are hard. **Shared records stay locked:** the universe's canon and world fields are only unlocked when this is the universe's *only* series — a stamp saying this series introduced a character records provenance, not exclusive use, and once a sibling series shares the universe that character may be one the sibling is built on. **Nothing is ever deleted:** the pass clears lock bits only, so characters, objects and volumes can be rewritten in full but stay in the Universe and the Catalog. Because unlocking the volume locks also removes the only thing that used to stop a regenerated arc from *dropping* a volume, all three arc-rewriting paths (arc generation, arc auto-resolve, and the foundation gate's structure fix) now re-insert any volume the rewrite omitted, and existing volumes win the per-series volume cap so a large regeneration can't push them out of the list. Consent is per run and per series: it is never saved as a default, the box clears itself once you launch, and it resets when you switch series — so a scheduled, repeat, or other-series run can't inherit lock-clearing. The dry-run plan names the step, with a count of the locks it would clear, before you commit.

- Series Pipeline **Autonomous mode gains an observing orchestrator** — the continuous, self-dispatching sibling of *Improve the pipeline itself*. With the new *Observing orchestrator* toggle on, the run watches its own telemetry step by step: when a step's fresh signals say the automation misbehaved (a retried or escalated child runner, a skipped step, an editorial check that threw, a filed gap), it spends one bounded diagnosis call asking what in PortOS should change — a missing or misordered step, an ineffective verify→resolve loop, a broken check or stage prompt, a misconfigured gate, even a missing autopilot option — and **dispatches the fix immediately** as an auto-approved CoS task that works in a worktree, opens a PR, and merges through the review loop with no human gate, so a defect noticed at step 4 is being fixed while steps 5–16 still run. Enabling the toggle is the explicit consent for those unattended changes; the guards are structural: execute-mode only, every pass billed against and gated on the daily cos budget, at most three mid-run passes plus one terminal pass per run, a higher confidence bar than the approval-gated post-mortem (which it supersedes at the run's end), and repeat diagnoses collapsing onto one open task. Live progress frames show each observation and dispatch, and the run's status banner lists everything that was filed. Off by default; scheduled runs inherit whatever you saved.

- Series Pipeline **Autonomous mode can now improve the pipeline itself.** A new Options toggle — *Improve the pipeline itself* — lets a run diagnose its own automation rather than only the story. When a run pauses, errors, or finishes carrying unhealthy telemetry (an editorial check that threw, a delegated runner that had to be retried, a step that was skipped), it spends one call asking whether the fault is the manuscript or PortOS: a missing editorial step earlier in the process, a stage prompt breaking its output contract, a runner swallowing a failure, a gate configured so it can't work. A pipeline verdict files a CoS task against PortOS itself — worktree-isolated, PR-opening, and waiting in your CoS approval queue, so an LLM's read of one run's telemetry never starts a coding agent on PortOS's own source by itself. Off by default, and a healthy run never spends anything on it; the diagnosis is billed as one cos action and skipped when the daily budget is spent. Repeat diagnoses of the same defect collapse onto one open task instead of piling up per run, and the verdict lands on the run's status banner. Scheduled runs inherit whatever you saved.

- **Video Gen chunks can each have their own prompt.** A chained render stitches up to eight clips into one longer shot, but every chunk was rendered from the same prompt — so a one-off action or line of dialogue replayed at each seam instead of the shot progressing. Raising Chunks above 1 now reveals an optional beat per chunk under Advanced: fill in the ones you want to direct ("she opens the door", "the storm breaks") and leave the rest blank to keep the main prompt. Each chunk still continues from the previous chunk's last frame, so the beats steer what happens next rather than starting a new shot. Lowering the chunk count and raising it again keeps the text you already typed, the beats survive a page reload mid-render, and they ride along on the finished clip so a Remix brings them back. Modes that anchor a single clip — audio-to-video, multi-keyframe, and the IC remixes — don't chain, so the editor stays hidden for them.

- Video Gen now offers Apple-local Wan 2.2 TI2V-5B plus validated 4-step A14B Lightning text- and image-to-video profiles through a pinned MLX-Gen runtime. Runtime tools/packages, immutable base snapshots, and exact Lightning adapters install only after an explicit UI action; existing installs receive an in-app repair/upgrade path, saved Hugging Face credentials are applied automatically, gated-source errors link back to the settings/access UI, and render/queue actions stay blocked until every required file is cached. The catalog identifies the A14B profiles as roughly 40 GiB downloads intended for 64+ GB Apple Silicon rather than understating their footprint. Wan-specific 4n+1 frame choices, FPS options, mode compatibility, process-tree cancellation, and locked Lightning sampler settings keep the UI aligned with the actual model contract.

- **Every managed app now has an Issues tab.** It queries the forge the app's work actually lives on (GitHub via `gh`, GitLab via `glab` — enterprise and nested-subgroup remotes included) and lists every open issue with its labels in the forge's own colors, assignees, author, milestone, and an expandable description, plus a filter box over all of it. Each row has a **Claim** button that queues the same `/do:next` CoS agent the Agent Operations panel does, pinned to that issue — so the run honors the app's configured Work Tracker, worktree, and PR settings. The list is gated on the app's *resolved* Work Tracker rather than its git remote alone, which is what keeps that promise: `workTracker` is user-settable and wins over the origin host, so an app with a GitHub remote but its tracker pinned to JIRA would otherwise have listed GitHub issues behind a Claim button that queued a JIRA-ticket run against a key that doesn't exist. Such an app now says so and points at the setting. An unreachable CLI says so and names the remedy; it is never reported as "no open issues".

- **JIRA config and the sprint Kanban board moved onto the app's own JIRA tab.** They were split across two surfaces that neither of them fit: the config was a cramped tab inside the 720px Edit App drawer, and the board was buried below the fold of the Overview tab. They now sit together at `/apps/:id/jira` with the full page width, and the config saves only its own slice, so a save there and a save from the Edit App drawer can no longer overwrite each other.

- Series Pipeline **Autonomous mode** now says which AI it will spend on. The Options popover names the provider and model the run resolves to, links to where per-stage pins and reasoning effort are configured, and offers a per-run provider/model override (never persisted — a one-off run can't silently re-point the whole series). The live progress line names the provider of an in-flight run too, including one the scheduler started.

- **Reference images now work on Codex, Grok and Agy, not just local FLUX.** Picking a reference image told you it was "Flux only", and it was: the server rejected reference uploads for every backend but local FLUX.2, and Agy refused an input image of any kind. All three cloud CLIs in fact expose a reference-image parameter — their tool schemas were probed directly rather than taken on the CLI's word — so each now receives them: Codex attaches every input image to `image_gen`'s `referenced_image_paths`, Grok routes them to `image_edit`'s `image` array (a reference-only render goes there too, since its `image_gen` has no image parameter at all), and Agy passes them as `generate_image`'s `ImagePaths`. The init image leads the list everywhere and still carries the strength → fidelity-phrase mapping. The Image Gen form offers as many reference slots as the selected backend actually accepts — Agy's tool takes at most 3 images total, so an init image there leaves room for 2 — and hides the per-reference strength slider on the cloud CLIs, which expose no numeric weight. Sprite forks, seeded reference renders and pipeline redraws no longer divert away from an Agy pin, and Agy alone still requires a prompt even with an input image, because its tool does.

## Fixed

- **A TUI provider that exhausts its own request retries no longer returns an error screen as successful story output.** Claude Code may retry a backend timeout ten times, render a final `Request timed out` banner, and still exit with code 0. One long foundation repair consequently spent nearly an hour, produced no response file, and then sent terminal chrome into the universe JSON parser as if it were a 13K-character bible. The one-shot TUI runner now distinguishes recoverable `Retrying … attempt N/10` banners from the terminal gutter-owned timeout, records the latter as a real timeout, and enters the existing fallback cascade. Genuine long-running model work keeps its configured ceiling; only the provider's explicit exhausted-retry state ends the call.

- Foundation-judge completion logs now report the provider and model that actually produced the verdict after fallback, rather than the primary pair that was requested. The persisted snapshot already distinguished requested from actual routing; live Autopilot supervision now tells the same truth.

- **Stopping a one-shot AI run no longer poisons provider health or repeats the work on a fallback.** PortOS restarts and the Runs UI both terminate an in-flight TUI with a signal. That intentional exit was previously finalized as an ordinary provider failure; worse, the error classifier scanned the whole prompt/screen, so an unrelated story word such as “credit” could relabel the stop as quota exhaustion, bench a healthy provider for an hour, queue an investigation, and begin the same expensive stage on a fallback while the server was already shutting down. External run stops are now tracked explicitly, host shutdown uses the existing process lifecycle latch, and both paths finalize as canceled: the run remains diagnosable in history but skips provider error analysis, failure hooks, fallback tiers, and health penalties. An unexpected PTY signal remains a real failure.

- **iCloud materialization logs now say a download was *requested*, not that the file is local.** `brctl download` returns exit 0 the moment it accepts and queues the request — it does not block until the bytes arrive, and it returns 0 even when the sync layer ultimately can't fetch the file. The on-demand materialize path logged that exit 0 as "materialized from iCloud", so an operator reading these lines during an iCloud outage would conclude a file was readable when it was still dataless. The logs now report the request, and the code comments spell out that the read path (`readStoreAtPathResult`/`readIfMaterialized`) fails closed — rejecting a dataless file rather than reading it — which is the reason the subsequent re-read stays safe and must not be removed. No behavior change.

- Preserve a Series Autopilot run's reasoning-effort override when the foundation gate delegates a worldbuilding repair to Universe Builder.

- Keep foundation worldbuilding repairs focused on the narrative bible they actually persist instead of spending most of the response on discarded image-prompt variations, reference sheets, and canon candidates.

- Route foundation findings to the editor that can actually apply them, so a plot synopsis that violates an established world rule is repaired as structure instead of looping through world-bible rewrites that cannot change the episode.

- Track foundation convergence per owning editor instead of against one global weighted-score high-water mark, so deepening a character can legitimately surface a new structure or craft gap without Autopilot pausing before that newly selected editor gets its first bounded repair attempt.

- Reject and retry foundation craft repairs that would be silently clipped by the persisted voice-guide schema. The repair prompt now receives the exact passage/note limits as a hard contract, and an oversized or incomplete exemplar response gets one focused rewrite before any series state is changed, so a strong reference scene cannot be stored mid-sentence and then mistaken for valid evidence by the next judge.

- Show the foundation judge every authored character transition, not just each arc's start and end. The judge now reuses the canonical character-arc prompt renderer, so a confession, relapse, sacrifice, or point of no return already placed in an issue cannot be reported missing and sent through another expensive character-repair pass.

- Validate foundation world-repair prose before Universe Builder's scalar sanitizer can silently slice it. An over-limit logline, premise, or style-notes field now gets up to two focused compression retries with the exact failed size, and the repair errors without changing canon if neither retry can fit, instead of saving a civic rule or paragraph that stops mid-sentence.

- Make over-limit world-bible retries compress the rejected draft itself instead of rerunning the original generation prompt. Two progressively tighter headroom passes preserve the draft's names, causal mechanics, costs, jurisdictions, and site operations while removing repetition, so an otherwise strong repair can converge on the persisted contract without regenerating the same oversized answer.

- Raise the Universe Builder and production-series premise ceiling from 4,000 to 20,000 characters. The former sanity cap forced legitimate multi-site world bibles with operational route, communications, rescue, ecology, culture, and resource rules into abbreviation-heavy ledgers; complete readable prose now persists directly, while the same fail-closed validator and draft-aware compression still contain genuinely runaway responses.

- **A successful agent run is no longer failed just because someone pulled `main` while it worked.** The branch-jack detector — which watches whether a worktree-isolated agent committed into the primary checkout instead of its own worktree — treated *any* movement of the primary as a branch-jack. So an ordinary `git pull` landing an already-merged PR flipped a run that had shipped its own PR into a failure, and told the user to consider `git reset --hard origin/main` over commits that already *were* `origin/main`. The guard now reports what a branch-jack actually leaves behind: commits the branch's upstream does not have, or the checkout parked on a different branch than it started on. A pure fast-forward onto upstream commits is logged as movement and nothing more. When damage is real, the recovery advice is sharper too — it quotes the number of *stranded* commits rather than how far HEAD travelled, and a checkout merely left on the wrong branch with nothing stranded is told to `git checkout` back instead of being pointed at a `--hard` reset that would discard nothing. A branch with no upstream to compare against still reports, since an unpushed commit is unreviewed by definition.

- **Recovering an AI provider now affects the very next routed run.** PortOS accidentally kept two in-memory provider-status services over the same JSON file: the Providers UI updated one while the AI Toolkit's runner consulted the other. A manual “Recover now” therefore looked successful and persisted correctly, yet a run started moments later could still bypass the recovered primary and spend time on a fallback. All legacy callers and the PortOS status routes now delegate to the Toolkit-owned singleton, and provider status socket events have one broadcast path instead of being emitted twice.

- **A timed-out creative stage no longer benches its provider as “quota exceeded.”** TUI finalization previously classified a hard timeout by scanning the whole terminal response, which includes the story prompt; ordinary narrative words such as “credit,” “payment,” or “billing” could therefore override exit 124 and sideline a healthy provider for an hour. The host's timeout signal is now authoritative, while non-timeout failures continue to use provider-output analysis for real usage, auth, model, and network banners.

- **Quality-first AI stages are no longer forced off at 30 minutes.** Provider, prompt-stage, and one-off run timeouts may now be configured up to 12 hours, matching the existing long-running TUI safety ceiling. The default stays five minutes and every provider keeps its own explicit cap, but an opted-in, high-effort story-planning or repair pass can be given enough wall time to finish instead of being killed while active and then repeated from scratch on a fallback.

- **An arc auto-resolve round that makes the draft worse is now undone instead of kept.** Autonomous mode's arc-verification gate hands the resolver the blocking findings it must clear and re-verifies afterwards — but whatever the resolver wrote was committed unconditionally, including a rewrite that cleared nothing and broke more than it touched. One run went 1 blocking finding → 3 → 5 that way: the loop noticed it had stopped converging and paused (correctly), but by then it had paused *on its own damage*, handing back an arc four findings further from the gate than the one the round started with. A round is now snapshotted before it runs — the arc, the volume list, each episode's planning synopsis and the volume it sits under — and if the next verification comes back with more blocking findings while the ones it was given are still standing, the round's edits are reverted and the run pauses on the original residual, labelled **round reverted**. The rollback is deliberately narrow: a round that genuinely closed everything it targeted is kept even when it surfaces findings that were latent underneath, since that's progress, and a round that merely stalls is still the existing non-convergence guard's business. Findings are matched by a normalized fingerprint rather than raw prose, so the verifier re-wording itself between calls can't disguise a finding as newly fixed. Volume ids, locked episodes, and the never-delete-a-volume guarantee survive the rollback, and no extra AI call is spent to detect it.

- **A CoS agent that commits to the primary checkout instead of its own worktree is now reported instead of recorded as a success.** A worktree-isolated agent running `/do:pr` applied its commits onto the primary checkout's local `main`, where they sat unpushed and unreviewed — on an unprotected branch, so any later push would have landed them without a PR — while PortOS recorded the run as completed. Every worktree run now stamps the primary checkout's branch and HEAD at spawn and re-reads them in the shared finalize path (so all three spawn modes are covered, not just TUI). A checkout that moved fails the run as `primary-checkout-mutated`, naming the drifted branch, the commit count, and the exact recovery command — and noting the commits are almost certainly on the agent's branch too. PortOS deliberately does not repair it: the repair is `git reset --hard`, which discards commits, and that stays your call. Runs that leave the primary alone are unaffected.

- **Universe Canon — "AI: differentiate cast" and per-character "AI: differentiate" now run.** Both threw `Stage pipeline-character-differentiate-cast not found` / `Stage pipeline-character-refine not found` on every install since they shipped: the prompt templates landed in `data.reference/prompts/stages/` but their `stage-config.json` entries were never authored, and `buildPrompt()` resolves the config entry first. Arc-verification **auto-resolve** (`pipeline-arc-resolve`) was dead the same way. All three entries now ship, migration 232 seeds them onto existing installs, and a new catalog-parity guard fails the build if a prompt template ever ships without its config entry again (or the reverse). The inverse gap on the Digital Twin side — ten stages whose config entry ships with no template, so each soul/twin AI pass silently runs its fallback — is tracked in #3644.

- A manual Autonomous-mode run now uses the series' own configured AI provider (the picker in the series header), matching scheduled runs and every other Pipeline action. It previously ignored `series.llm` and ran on the install's active provider, so the series header said one thing and the run did another. It stays a *soft* default: a stage pinned in Prompts keeps its pin, and an unavailable provider falls back instead of failing the run.

- Series Pipeline and Manuscript Editor pages can now scroll through their full content on mobile.

- A Layered Intelligence run that ends badly now says what actually went wrong. Its whole job is to return JSON that a deterministic step files as one tracker issue — its prompt *forbids* touching the repo — yet the idle reaper judged it by the same "is there a file change or a commit?" question it asks a coding agent, and reported `idle-no-changes`: "the agent did not modify files", on a task told not to modify files. The real miss was one question away and is now the one asked: the `.agent-done` payload never landed, so nothing was filed. Failures on this task type read `idle-no-deliverable` and point at the missing payload (a smaller model answering in the terminal instead of writing the file — see #3640), and a run that did write its payload just before the reaper is now correctly rescued rather than failed for a clean tree. Code-editing task types are unchanged.

- A CoS agent waiting on a **backgrounded reviewer** is no longer reaped as dead. `/do:pr`'s self-review gate runs each reviewer (an Ollama per-file pass, a headless `codex` pass over the branch diff) as a background command and waits to be re-invoked when it finishes — and in that wait the model has nothing to do, so it returns to the prompt and the terminal goes *completely* silent. Idleness is measured by terminal output, so a correctly-working agent looked identical to a dead one and the three-minute default killed it. On 2026-08-09 that cost one task three consecutive attempts: the feature was written, committed and pushed all three times, the review never got to finish, and the PR was never opened — twice reported as "no pull request exists", once as the actively misleading "idled out with no file changes", on a branch that by then held three commits. The reaper now extends its patience to 15 minutes whenever the terminal reports background commands still in flight, matching the existing merge-queue and multi-reviewer-loop graces. Those two didn't cover this: they latch on the multi-reviewer *loop*'s banners, which only print when the review loop is enabled, and this run had it off — the reviewers came from the ordinary self-review gate, which prints no such banner. Keying on outstanding background work instead covers any long-running background command, and the maximum-runtime backstop still bounds a genuinely dead session. The stranded work from that incident is recovered in #3679; a second defect the same three attempts exposed — the agent also writing its commits into the primary checkout — is tracked in #3680.

- CoS agents whose deliverable is a **commit** are no longer scored as failures. The idle reaper's "did this agent do anything?" gate read only *uncommitted* changes, so a `/do:release` or `/do:pr` run that committed, pushed, and opened its PR — leaving a clean tree *because it succeeded* — was recorded as `idle-no-changes` and retried. Two consecutive release runs on 2026-08-08 each did their whole job (cut the release commit, opened the release PR, then repaired it against review findings) and were both reported failed, holding the release for two days. The gate now counts commits made inside the run window as evidence of work, alongside a dirty tree. The report-shaped half of the same problem (`/do:review`, `/do:scan`, `/do:plan-task`, `/do:replan`, whose deliverable lands outside the repo) is tracked in #3636, and the unsatisfiable `[task-<id>]` success criterion one layer up in #3637.

- **CoS now brings recent unrated completed runs back to you.** The feedback queue was durable but easy to miss once a completion notification disappeared. Tasks now surface an actionable reminder that opens the Agents tab directly in its shareable “Needs feedback” filter, so a quick rating can actually improve future routing and task quality.

- Green merge-only PRs are drained on a real 30-minute cadence again. The pending-merge sweep had moved onto the CoS evaluation pass, but evaluation is event-driven — there is no evaluation timer — so on a quiet install it ran roughly once per PortOS restart, and the `MAX_PENDING_MERGE_TICKS` escape hatch counted restarts instead of the six hours it documents. The sweep now owns a `cos-pending-merge-sweep` interval job registered and cancelled with the other CoS timers, gated on the same "CoS auto-run is `execute` and not paused" switch. It stays decoupled from the `pr-watcher` task type, so leaving that task disabled still can't strand a queued merge, and `POST /api/cos/evaluate` still drains opportunistically.

- An agent that merely *prints* a provider banner no longer benches a healthy provider. The immediate-fallback detector stamped every match as provider chrome, so a CoS agent that quoted Antigravity's account-eligibility banner — investigating that failure mode, `cat`-ing a prior run's transcript, grepping for it — sidelined the provider for the full cooldown across every subsequently dequeued task, not just its own run. The banner is now promoted to provider provenance only when it opens its own line behind nothing but TUI gutter chrome, the shape the CLI actually renders; a quoted mention still fails that one run and routes it to a fallback, but is no longer treated as evidence about the provider's health. Real banners arriving as the run's own terminal output bench exactly as before.

- A CoS task whose agent spawn is **rejected by the runner** is now requeued immediately instead of being penalized for it. The runner-rejection path finalized the agent but never transitioned the task, so it sat `in_progress` holding its federation claim until the 15-minute orphan sweep — a path meant for genuine orphans, which charged one of the task's finite `orphanRetryCount` retries and armed a 30-minute cooldown for a failure the task did not cause (the agent never started; a momentarily unreachable runner was enough). It now runs the same `finalizeAgent` → `releaseRetryHold` chain the TUI path does, under its own `spawn-rejected` reason, so the task returns to `pending` with its claim released the moment the rejection lands and the runner's actual error is on the agent record.

- A failed X profile read no longer reads as "you are shadowbanned." The reach diagnostic settles the X SPA for a moment and only throws on an origin mismatch, so a page that rate-limited, rendered late, or returned an app shell resolved *successfully* with an empty profile — and all three visibility checks persisted as hard `false` while `last_error` was cleared, presenting a confident "your profile is not public, you do not appear in search, you have no recent posts" verdict produced by a read that simply failed. That is the one conclusion the feature exists to avoid drawing. Each of the three reads is now scored on its own evidence: a page that did not render yields `null` for its checks (shown as the warning-toned "Unknown", with a per-check hint to re-run) and names itself in a plain-language last error instead of clearing it. A page that read fine and did not match still reports `false`, and a positive search hit stays `true` on its own evidence even when a sibling read came back blank.

- CoS agents whose deliverable is a **report** are no longer scored as failures either. `/do:plan-task`, `/do:replan`, `/do:review` and `/do:scan` file an issue or print a report and are explicitly told to write no code, so they reach the idle reaper with a clean tree and no commit — the exact shape the reaper calls `idle-no-changes`. Widening the evidence probe to count in-run commits fixed only the commit-shaped half. Each launchable slashdo workflow now declares its deliverable on its catalog entry: the six that land a commit keep the clean-tree gate armed, and the four report-shaped ones carry `worktreeChangesExpected: false` and opt out of it, the same escape hatch a `reference-watch` run against a forge tracker already uses. `/do:next` still defers to the work tracker its claim flow actually resolved.

- Ten Digital Twin AI passes now actually run. Each shipped a `stage-config.json` entry with no prompt template behind it, so `buildPrompt()` threw "Template not found" and every call site's `.catch(() => null)` quietly took the fallback path — contradiction detection returned no issues, test generation and writing analysis produced nothing, trait extraction and confidence scoring never ran, enrichment served a generic canned question and stored answers unformatted, test scoring degraded to keyword matching, and import/interview analysis was skipped. All ten templates are now authored against what each call site's parser expects, `twin-interview-analyze` gained the config entry it was also missing, and a migration seeds both into existing installs. A new parity guard fails the build if a stage-config entry ever ships without its template again.

- Four sentinel/lifecycle gaps from the v2.40.0 diff are closed. A redirected X handoff (login wall, X redirect) left the Chrome tab it owned open forever, because `openXHandoff` verifies the landing path *after* taking ownership with `closeAfterRead: false` — the tab is now closed before the verification error bubbles. A pending-merge PR whose `gh pr view` fails permanently (deleted PR, renamed repo, revoked token) never ticked, so `MAX_PENDING_MERGE_TICKS` never fired and the entry re-shelled to `gh` forever with nothing surfaced; an unreadable cycle now counts as a tick and times out with a notification naming the PR. The `collaborators` author filter fetched the 100 *oldest* issues by any author and filtered them in memory, hiding a claimable collaborator-filed issue on any busy repo while `self` worked fine — it now fans out one server-side `--author` query per trusted login (capped at 25, with the truncation logged) and merges. And an `api` provider whose `/models` returns HTTP 200 with a non-JSON or unrecognized body no longer overwrites the stored model list with `[]` under a "Models refreshed" toast; it throws with the real reason and leaves the list untouched, the same posture the CLI arms already take. A genuinely empty catalog still saves as empty.

- Three behaviors that shipped with a suite that stayed green when they were deleted now have tests that fail without them. The X reach feature's two safety gates — the 24h stale-approval window and the state-transition guard that stop an approval the user no longer intends from opening a compose window — plus its sync/draft-open re-entrancy guards and the numeric-status-id filter on ingested posts; the review loop's per-reviewer reasoning-effort map, whose whole feature could be dropped from the resolved options with nothing failing; and the remaining provider-benching cases, which asserted against hand-written `{ category, origin }` objects instead of running a transcript through the real detector — the exact pattern that let a genuine usage-limit regression ship green. Each new test was verified by deleting the line it names and watching it fail.
- **CoS tasks filed for PortOS's own work now actually run.** Two producers used `metadata.app` as a feature tag when it is workspace routing — it has to name a record in `data/apps.json`. The Series Pipeline autopilot filed every gap it found (unparseable script, stalled verify, failed render, run-ending error) at `app: pipeline`, and the auto-fixer filed its AI-provider investigations at `app: portos`, which matches neither the seeded app id (`portos-default`) nor its name. Both were harmless until the wrong-repo guard (#3180) closed the silent fall-through to the PortOS root: since then each of these tasks was filed and then rejected at every spawn attempt, so the one mechanism that surfaces an autopilot capability gap never reached an agent. Both now file with no app — which resolves to the PortOS workspace they were always meant to run in — and migration 234 un-routes the ones already queued on existing installs (re-stamping them so the fix wins the sync merge against a peer that hasn't upgraded).

- A CoS task naming an app that doesn't resolve to a repository directory is now **parked as blocked** instead of retried forever. The spawn guard refused to start the agent (correctly — it would otherwise commit into the PortOS checkout) but left the task `pending`, so the scheduler re-dequeued it every tick and reprinted the same error, while the fix was only visible in that task's own log. It now lands in the Blocked list, and the message covers both ways an app resolves to nothing: no Repository Path set, or nothing in Apps matching that id/name at all (in which case the fix is to clear the app from the task, not to register a path).

- Autonomous CoS runs are no longer marked as having failed their success criteria by a check nothing could ever pass. `evaluateSuccessCriteria` judged a run by grepping for a commit whose subject carried the task id — a marker no prompt, template, or slashdo command ever asked an agent to write, and one the repo's own commit conventions forbid. So every ordinary code-editing run recorded `validationPassed: false`, and because a declared verdict outranks the exit code in task-learning, those fabricated failures filled the learning buckets that drive the Learning card, routing, and duration estimates. The criterion is now the same run-window commit probe the idle reaper already uses (did this run leave a commit stamped inside its own window?), shared as `server/lib/gitCommitProbe.js` by finalize, run completion, runner completion, and orphan recovery. A run with no usable window records the "no criterion declared" sentinel rather than a false miss, the existing exemptions for non-committing task types are unchanged, and a migration purges the buckets the old criterion poisoned.

- A programmatic-I/O run whose model **printed** its JSON answer into the terminal instead of writing `.agent-done` no longer throws the whole run away. For these task types the sentinel JSON *is* the deliverable — a Layered Intelligence proposal becomes a filed tracker issue — so a weaker (typically local) model answering in the TUI rather than through the tool call meant the hook ran with no payload and minutes of reasoning were discarded silently. When no sentinel was written, finalize now scans the ANSI-stripped tail of the run's PTY transcript for the newest complete JSON object and adopts it only if the owning hook's own shape predicate accepts it, logging the rescue so a salvaged run stays distinguishable from a clean one. Scoped to programmatic-I/O types on purpose: everywhere else the sentinel is a completion signal, not a product, and scraping a transcript for one would let an agent that merely discussed finishing be counted as finished.

- **Chief of Staff now exposes its persistent Pause/Resume control in the UI.** Stop only tears down the current daemon process; an always-on install can start it again, which made supervised live work a race against unrelated queued agents. The header now separates queue control from process control: Pause keeps CoS healthy but blocks new task evaluation and dispatch across restarts, Resume explicitly reopens the queue, and Stop remains available as the full shutdown. The pause copy also makes clear that already-running agents are not killed, so their work can be paused individually and preserved from the Agents tab.

## Privacy Center

- **Your PII vault stays on one machine — permanently, by decision.** The Privacy Center's vault, organization registry, change-of-address inventory and broker opt-out ledger were always machine-local, but that was recorded as a feature not yet built, which left the door open to syncing them to your other PortOS machines later. It is now a documented guarantee: none of it federates, and none of it ever will without a new decision record superseding this one. The reasoning is written up in full — chiefly that PortOS's peer-sync was built for creative work rather than identity data, that the display masks (`••••1234`, `j•••@example.com`) are readable even when the underlying values are encrypted, and that copying one encryption key to several machines would widen the exposure of every one of them. If you want the vault on a second machine, restore a backup and copy the key by hand — a deliberate act, rather than something that happens quietly in the background. Managing PII for other household members is unaffected and remains planned.

- **Peer-sync pull requests now honor the per-peer sharing settings the push direction already respected.** `GET /api/peer-sync/record` served any subscribable record by id with no notion of who was asking, so a peer configured for "universes only" — or one with sync switched off entirely — could still read every series, media collection, and writers-room record; the record/library/CoS-history/CoS-task manifests and the CoS agent-archive bytes had the same shape. Every outbound hop now identifies this install with an `X-PortOS-Instance-Id` header attached centrally in `peerFetch`, and the receiver resolves that id against its peer registry and runs the *same* `peerAllowsOutbound` + `peerHasCategory` predicates the push path uses, so the two directions can't drift apart again. Because peers upgrade independently this ships warn-first: a pull from an unidentified, unknown, or disallowed caller is still served and logs one `⚠️` per caller per restart. The new **Settings → Sharing → "Enforce per-peer sharing settings on pull requests"** toggle (`federation.strictPullAuthorization`, default off) turns those into a 403 — the default flips in a later release once peers have had time to update. Note that the instance id is *identification*, not authentication; the instance password remains the actual access control.

- **The Privacy Center can now hold more than one person — with consent enforced by the engine, not the UI.** Everything in the suite (vault records, organizations, holdings, change-of-address events, broker cases, consent rows) is now scoped to a *household subject*, so a partner, child or parent you have permission to act for gets their own vault and their own broker opt-out ledger, worked independently of yours. Adding someone requires recording *how* their consent was captured (verbal, written, signed form, guardian, power of attorney), and the exposure-scan and opt-out engines **refuse** to scan or submit for a subject with no consent on file — a hard 403 in the service, so a scheduled recheck, a direct API call or a future agent path is refused exactly like a hidden button would be. Deleting a subject is a hard delete that removes everything of theirs, and the `self` subject can't be deleted. Existing installs are unaffected: a `self` subject is seeded, every existing row backfills to it, and every endpoint still defaults to it, so an install that never adds a second person behaves exactly as before. The Digital Twin's privacy context and the org cross-link stay scoped to `self` — a household member's data never enters a prompt. This is the multi-person half of #2148; it stays machine-local like the rest of the Privacy Center, with no federation.

- **The Privacy Center now has the UI for those household members.** A subject bar above the tabs names whose records are on screen and switches between them; every tab — Overview, Vault, Organizations, Changes, Brokers — refetches under the selected person, and new vault records and organizations are filed to them. The choice lives in the URL (`?subject=…`), so a view of one person's data is shareable, bookmarkable and survives a reload, and it follows you across tabs and drill-downs instead of silently snapping back to you. Scoping to anyone other than yourself tints the bar and says so in words, and any revealed plaintext is dropped the moment you switch — the two ways a multi-person vault could otherwise let you read the wrong person's address and not notice. A **Household** panel adds and removes members, records how each person's consent was captured, and shows the full consent trail per person; removing someone spells out that their vault records, organizations, changes and broker cases go with them. There is deliberately no per-tab subject filter and no subject column: the API scopes to exactly one person per request, so the switcher *is* the filter and a column would print the same name on every row. Running a scan or opt-out pass for someone with no consent on file now says so in a sentence you can act on rather than surfacing the engine's raw refusal.

- A `/do:review` (or `/do:scan`, `/do:plan-task`, `/do:replan`) run queued from the **CoS quick templates** is no longer failed as `idle-no-changes`. The deliverable posture each slashdo workflow declares on its catalog entry reached the Agent Operations buttons but was silently dropped by the quick-template form, which read only the three run-shape toggles off a template's settings block — so the exact clean-tree misfire that posture exists to prevent still happened from the other surface. The flag now rides the template through the form as hidden state and into the create-task payload, and the strict template-settings schema accepts it so a user can save such a template back without a 400.

- **Series Pipeline runs can now pick a reasoning effort.** Pipeline stage LLM calls never emitted one, so a run's thinking effort was whatever the provider's configured CLI args (or an effort-encoding model id) happened to bake in — making a cheaper or harder-thinking autopilot run a global provider edit. Effort is now threaded exactly like the run provider and model: the Autonomous-mode Options popover (and a scheduled run's setup) offers it next to the provider/model picker for effort-capable providers, names the level the run resolves to, and applies it as a soft per-run default. A deliberate per-stage `effort` pin still wins, a level the chosen provider doesn't offer is clamped down its ladder rather than dropped, and a provider with no effort control simply gets no flag.

- Internal: the Autonomous-mode Options popover's saved-default/per-run-override plumbing moved onto a shared `usePersistedOptions` hook. Each option was seven hand-copied edits scattered across a 1000-line component, and forgetting one silently produced the "I toggled it and ran, but it did not apply" bug; an option is now a single spec row that owns its default, its saved-value reader, its clamp and its persist behavior. No behavior change.

- **Video Gen can now run MiniMax H3 locally on a 128 GB Apple Silicon Mac.** The new text-to-video profile uses PipeNetwork's source-audited MLX port and an 8-bit transformer, with every runtime and weight revision pinned and a reproducible isolated environment. Its roughly 103.3 GB of required files stay off the machine until the user explicitly installs the runtime and downloads the weights; generation itself is cache-only and receives no Hugging Face credential. H3 produces joint 24 fps video and stereo audio on its supported 17n+5 frame grid, while PortOS hides or rejects controls the released port cannot honor (image conditioning, negative prompts, silent output, tiling and chained clips). The MiniMax H3 Community License grants rights only in its Applicable Territory and explicitly excludes the EU, UK, Republic of Korea and United States, so both download and generation require the exact versioned acknowledgement shown beside the pinned license; PortOS does not guess a user's location or eligibility.

- **Video Gen now tells you what runs where, and under whose terms.** Model names such as "LTX-2.3 Distilled Q4 (~22 GB)" carried the only provenance a user got, and the local/hosted backend switch offered a one-line tooltip — so "local" was easy to read as "no rules apply", which is wrong: a local runtime only means PortOS isn't sending your prompt to a hosted provider, it doesn't waive the weights or runtime license. A compact disclosure now sits under the backend and model controls and updates with them, showing whether inference runs on this machine or is submitted to xAI, the model card and pinned revision, the weights license and the (often different) runtime license, the pinned-snapshot download size, the memory minimum against what this machine actually has, supported modes and runtime name. Every value was checked against a primary upstream source — the HuggingFace model card's own license metadata, the runtime project's LICENSE file, the file listing at the pinned revision — and anything that could not be established renders as "Unknown" rather than being guessed from a repo name. Custom models you added yourself show Unknown throughout, and so does a shipped model whose repo you re-pointed at a fork. The local wording says plainly that PortOS applies no model-level prompt filter *and* that the licenses still apply; the hosted wording says the request leaves the machine and xAI's terms and retention apply independently. Nothing about downloads, verification, render arguments or prompt handling changed — this is disclosure only, and it deliberately avoids ranking backends as more or less restrictive.

- Internal: recorded a feasibility spike on Krea Realtime 14B as a local Apple Silicon video backend (`docs/research/2026-08-09-krea-realtime-apple-silicon.md`). The answer is **no-go for now** and nothing shipped: Krea's own runtime initializes CUDA at module import and pins `triton`, which publishes no macOS wheel, so it cannot even install on a Mac; its inference code is CC BY-NC-SA 4.0 (the weights are Apache-2.0 — two different licenses that PortOS has to track separately), and the only native-MLX implementation of the pipeline is a third party's unpublished, in-progress crate inside a product monorepo. The report pins every revision it inspected, distinguishes Krea 2 RAW/Turbo (image) from Krea Realtime 14B (video), marks every benchmark explicitly "not run" with the reason rather than guessing, and names the specific upstream change that would justify reevaluating.

- Internal: the series-autopilot unlock-pass test suite no longer reads the checkout's real `data/` directory. It partial-mocked `fileUtils.js` with an in-memory store but left `PATHS.data` pointing at the repo, and the series collection store enumerates that directory with a real `readdir` the mock never intercepts — so on any checkout with real series on disk, two sole-universe-ownership tests failed with what looked like a regression on whatever branch happened to be checked out. CI never saw it because a fresh checkout has no `data/`. `PATHS.data` now resolves to a per-run temp dir via the shared `makePathsProxy` helper, and three added assertions pin the isolation so it cannot quietly come back. The three sibling pipeline suites named as suspects were audited and are already isolated — they replace `series.js` outright and never reach the store. Test-only change; no production code touched.

- Internal: audited the whole server test suite for the "test reads the checkout's real `data/`" class that #3683 fixed one instance of, and closed the one case that was actually a bug. The audit was empirical rather than static — a full-suite baseline against an empty `data/`, then a second run with obviously-fake probe records planted in all 74 `data/` subdirectories a service enumerates (prefix-aware, so the stores whose id allowlists require `iss-`/`ser-`/`stb-`/`game-` were actually reached, and including the dirs `data.reference/` seeds rather than only the ones the `PATHS` table names) — and exactly one of 1301 test files failed only in the second run: the missions suite, which addressed `<repo>/data/cos/missions` directly with no mock at all, so it read the developer's live missions *and* wrote its own fixtures into them. It now runs against a per-run temp root, with assertions pinning both the path it writes to and the set it reads back. The 67 suites that partial-mock `fileUtils.js` without redirecting `PATHS` were cleared by the same two-run diff — they replace the service graph wholesale and never reach a real `readdir`. Two further suites do read the live install on purpose and are left alone: the creative-director prompt suite prefers the installed prompt so it catches drift against a local edit, and the opt-in vision integration test enumerates real screenshots to feed a real model. Neither writes anything back. A new repo-wide guard now fails the suite when any other test names the checkout's own `data/` directory, through an install-root anchor or a parent-directory climb, with those two exemptions documented in place. It deliberately does not police the third spelling, importing the real `PATHS` and reading a data-rooted member: 50 files do that, nearly all safely, so that one stays covered by the two-run probe, whose recipe is now recorded beside the guard so it can be re-run. Test-only change; no production code touched.

- One malformed file in the CoS missions directory no longer takes out the whole Missions overview. `getStats()` dereferenced `mission.subTasks.length` on every record `loadMissions()` handed back, and that loader passed through anything that parsed as JSON — so a hand-edited file, a half-written record, or one written in an older shape threw a `TypeError` and blanked the page instead of costing one row. Records are now normalized at the single door they come through: `subTasks`, `goals` and `metrics` coerce to their expected shapes, `progress` to a finite number (no more `NaN%` average), and an absent status buckets under `unknown` rather than an `undefined` key. Anything that isn't a usable mission object is dropped with one `⚠️` line naming the file, so a corrupt record is visible rather than silently missing.

## Series Pipeline

- **Foundation results now call the next repair target what it is.** The gate deliberately chooses the largest weight-adjusted deficit, so a worldbuilding score of 8 can be the best next use of a repair round ahead of a structure score of 7. The Autopilot timeline and Series Review called that field the "weakest" dimension, which made the weighting look broken and obscured why a higher raw score ran first. They now say "next target," the options help names the largest weighted deficit, and server telemetry uses the same term; the persisted/API field remains backward-compatible.

- **Character-first planning now finishes the whole story cast instead of repeatedly polishing six people.** The foundation repair selector had a hard top-six cutoff, so a larger ensemble could spend every bounded repair round revisiting the same principals while later story-referenced characters remained blank. It now derives the series roster from authored arcs and issue synopses, processes every referenced character in sequential six-character work batches, and gives each batch the full ensemble map so voices, values and relationships stay differentiated. The foundation judge and its cache use that same series-scoped roster, so undeveloped characters belonging to other stories in a shared universe no longer make this series fail its character gate; before an arc exists, the small fallback remains and the architect may add only genuinely missing core roles.

- **A paused Series Autopilot run now resumes with its visual and gap-filing choices intact.** Those two controls were run-local, but the pause marker remembered only the current step and error. Reloading the page or restarting PortOS therefore made the Options form look like a brand-new run: visuals returned to their default and "File CoS tasks" silently turned off, so a later unresolved gap could disappear instead of being tracked. Active and paused markers now carry only those two safe continuation choices, the resume form restores them, and a completed run or different series still gets clean defaults. The one-shot "Unlock everything" consent is deliberately not re-armed: its pass already leaves the records unlocked, and repeating a spent mutation is not part of resuming.

- **Series autopilot now secures the foundation before it grows a manuscript.** The foundation judge now reads the actual volume and episode synopses, authored character arcs, and series voice/exemplars — and its cache invalidates when any of them change. A weighted average can no longer hide a critically weak dimension: every world/character/structure/craft score must also clear a floor. Character findings repair the referenced core cast as an ensemble and write whole-series character arcs instead of expanding whichever unrelated record has the most blanks; craft findings repair the series voice and add concrete tuning-fork examples instead of rewriting the universe's visual style; world findings carry the judge's specific directive into the world-bible pass. Foundation and structural verification now form one bounded planning loop: either one's repairs invalidate the other's verdict, every volume gets its own synopsis-level verification alongside the cross-volume pass, and autopilot refuses to start beat sheets until the two gates jointly converge.

- **Series autopilot no longer manufactures the duplicate volumes it then gets stuck on.** Arc auto-resolve matched the LLM's rewritten volumes back to your existing ones by `id` alone — but the resolve prompt routinely returns a rewritten volume *without* echoing its id, and that read as "a brand new volume", minting a second record. In the autopilot's unlock-for-run mode, which deliberately refuses to let a rewrite delete a volume, the original was then re-inserted right next to the mint. So every auto-resolve round left one more `Volume 1` than it started with, arc-verify filed the pile-up as a blocking finding, and the run paused for "no net progress" while pointing at damage it had caused itself. A rewrite is now matched to the record it is a rewrite *of* — by id, then title, then an unambiguous volume number — and lands on that record, keeping its episodes, themes and lock attached. There is no positional guessing: a volume that genuinely doesn't match still mints, because a wrong guess would overwrite one volume's prose with another's.

- **An arc write now repairs duplicate volume numbers instead of preserving them forever.** Two volumes sharing a number is not a state you can act on — the Arc Canvas draws both, an export can't tell which is canonical, and arc-verify blocks on it every round — but the sanitizer only ever de-duplicated by `id`, so the pair survived every pass untouched. Any ordinary arc write now collapses them, keeping whichever record has the strongest claim to the episodes underneath it (a volume you locked, else the one holding the most episodes, else the original), and re-points episodes stranded under the absorbed copies onto the survivor rather than dropping them into "Un-grouped". Content is only ever rescued, never overwritten: a field the survivor left empty is back-filled from the newest copy, and a field it already has is kept. A number shared by *two locked volumes* is deliberately left alone and warns instead — only you can say which freeze was meant. Installs already carrying duplicates heal on their next arc write, with no migration to run.

- **Autopilot now repairs duplicate volumes before it can waste work filling them.** Resume previously looked for empty volumes before any arc write reached the duplicate-volume self-heal, so malformed empty copies could receive a full issue breakdown only to be absorbed later. A zero-cost structural preflight now runs first, keeps existing issues attached to the canonical volume, and only then considers episode generation. If locks make the repair ambiguous, the run pauses before spending and asks for full edit control. Dry-run estimates mirror the same repair and no longer charge issue-generation calls for copies that will be absorbed.

- **Synchronous Codex TUI stages stay single-agent.** A machine-consumed pipeline prompt could inherit Codex's general multi-agent feature, fan out work it never needed, and then spend its entire timeout waiting on those agents before repeating the same request on a fallback provider. The one-shot TUI runner now disables that feature only for Codex prompt calls; long-running CoS coding agents keep their configured collaboration posture, and other TUI providers are unchanged.

- **A foundation repair no longer sends the entire episode list, and no longer takes the whole autopilot run down with it when it fails.** The foundation-quality gate's repair prompt carried the full synopsis-level plan — every volume *and* every episode synopsis — with no size limit, so it grew with the series forever. On a long-running series that section reached 28KB of a 35KB prompt, and the primary AI provider burned its entire ten-minute timeout on it without producing a single word; the fallback provider then repeated the same request and burned ten more. Twenty minutes spent, nothing written, and the whole autonomous run ended in an error that discarded every step it had already completed. The repair prompt is now bounded the same way the judge prompt beside it always was: the plan spine (arc, volumes, authored character arcs) is always sent in full, and the episode list fills the remaining budget by whole lines, oldest first, saying how many were left out — so the model reads a coherent outline instead of one cut mid-sentence. And a repair whose AI call fails outright now **pauses** the run rather than erroring it: the failure is a provider timeout or a dead CLI, not a verdict on your story, so the run keeps every step it finished, tells you which provider failed, and resumes from where it stopped. Autopilot also stopped quietly losing the reason it paused — "nothing to fix", "budget reached" and this new "provider failed" were all being emitted and then dropped before they reached the screen, leaving a bare "Paused" with no explanation; each now carries its own badge.
