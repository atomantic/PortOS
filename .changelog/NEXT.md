# Unreleased

## Added

- Series Pipeline **Autonomous mode** gains an **"Unlock everything this series owns first"** option. A locked arc, volume, issue stage, or canon entry makes the corresponding fix path throw or silently skip, so a run would surface an editorial finding and then pause on a problem it was never allowed to resolve — leaving you to hunt down every lock toggle by hand before re-running. With the option on, the run's first step clears the arc freeze, the per-field arc locks, every volume lock and every issue stage lock, then reports exactly what it cleared and what it deliberately left frozen. Two boundaries are hard. **Shared records stay locked:** the universe's canon and world fields are only unlocked when this is the universe's *only* series — a stamp saying this series introduced a character records provenance, not exclusive use, and once a sibling series shares the universe that character may be one the sibling is built on. **Nothing is ever deleted:** the pass clears lock bits only, so characters, objects and volumes can be rewritten in full but stay in the Universe and the Catalog. Because unlocking the volume locks also removes the only thing that used to stop a regenerated arc from *dropping* a volume, all three arc-rewriting paths (arc generation, arc auto-resolve, and the foundation gate's structure fix) now re-insert any volume the rewrite omitted, and existing volumes win the per-series volume cap so a large regeneration can't push them out of the list. Consent is per run and per series: it is never saved as a default, the box clears itself once you launch, and it resets when you switch series — so a scheduled, repeat, or other-series run can't inherit lock-clearing. The dry-run plan names the step, with a count of the locks it would clear, before you commit.

- Series Pipeline **Autonomous mode** now says which AI it will spend on. The Options popover names the provider and model the run resolves to, links to where per-stage pins and reasoning effort are configured, and offers a per-run provider/model override (never persisted — a one-off run can't silently re-point the whole series). The live progress line names the provider of an in-flight run too, including one the scheduler started.

## Fixed

- **Universe Canon — "AI: differentiate cast" and per-character "AI: differentiate" now run.** Both threw `Stage pipeline-character-differentiate-cast not found` / `Stage pipeline-character-refine not found` on every install since they shipped: the prompt templates landed in `data.reference/prompts/stages/` but their `stage-config.json` entries were never authored, and `buildPrompt()` resolves the config entry first. Arc-verification **auto-resolve** (`pipeline-arc-resolve`) was dead the same way. All three entries now ship, migration 232 seeds them onto existing installs, and a new catalog-parity guard fails the build if a prompt template ever ships without its config entry again (or the reverse). The inverse gap on the Digital Twin side — ten stages whose config entry ships with no template, so each soul/twin AI pass silently runs its fallback — is tracked in #3644.

- A manual Autonomous-mode run now uses the series' own configured AI provider (the picker in the series header), matching scheduled runs and every other Pipeline action. It previously ignored `series.llm` and ran on the install's active provider, so the series header said one thing and the run did another. It stays a *soft* default: a stage pinned in Prompts keeps its pin, and an unavailable provider falls back instead of failing the run.

- Series Pipeline and Manuscript Editor pages can now scroll through their full content on mobile.

- A Layered Intelligence run that ends badly now says what actually went wrong. Its whole job is to return JSON that a deterministic step files as one tracker issue — its prompt *forbids* touching the repo — yet the idle reaper judged it by the same "is there a file change or a commit?" question it asks a coding agent, and reported `idle-no-changes`: "the agent did not modify files", on a task told not to modify files. The real miss was one question away and is now the one asked: the `.agent-done` payload never landed, so nothing was filed. Failures on this task type read `idle-no-deliverable` and point at the missing payload (a smaller model answering in the terminal instead of writing the file — see #3640), and a run that did write its payload just before the reaper is now correctly rescued rather than failed for a clean tree. Code-editing task types are unchanged.

- CoS agents whose deliverable is a **commit** are no longer scored as failures. The idle reaper's "did this agent do anything?" gate read only *uncommitted* changes, so a `/do:release` or `/do:pr` run that committed, pushed, and opened its PR — leaving a clean tree *because it succeeded* — was recorded as `idle-no-changes` and retried. Two consecutive release runs on 2026-08-08 each did their whole job (cut the release commit, opened the release PR, then repaired it against review findings) and were both reported failed, holding the release for two days. The gate now counts commits made inside the run window as evidence of work, alongside a dirty tree. The report-shaped half of the same problem (`/do:review`, `/do:scan`, `/do:plan-task`, `/do:replan`, whose deliverable lands outside the repo) is tracked in #3636, and the unsatisfiable `[task-<id>]` success criterion one layer up in #3637.

- Green merge-only PRs are drained on a real 30-minute cadence again. The pending-merge sweep had moved onto the CoS evaluation pass, but evaluation is event-driven — there is no evaluation timer — so on a quiet install it ran roughly once per PortOS restart, and the `MAX_PENDING_MERGE_TICKS` escape hatch counted restarts instead of the six hours it documents. The sweep now owns a `cos-pending-merge-sweep` interval job registered and cancelled with the other CoS timers, gated on the same "CoS auto-run is `execute` and not paused" switch. It stays decoupled from the `pr-watcher` task type, so leaving that task disabled still can't strand a queued merge, and `POST /api/cos/evaluate` still drains opportunistically.

- An agent that merely *prints* a provider banner no longer benches a healthy provider. The immediate-fallback detector stamped every match as provider chrome, so a CoS agent that quoted Antigravity's account-eligibility banner — investigating that failure mode, `cat`-ing a prior run's transcript, grepping for it — sidelined the provider for the full cooldown across every subsequently dequeued task, not just its own run. The banner is now promoted to provider provenance only when it opens its own line behind nothing but TUI gutter chrome, the shape the CLI actually renders; a quoted mention still fails that one run and routes it to a fallback, but is no longer treated as evidence about the provider's health. Real banners arriving as the run's own terminal output bench exactly as before.

- A CoS task whose agent spawn is **rejected by the runner** is now requeued immediately instead of being penalized for it. The runner-rejection path finalized the agent but never transitioned the task, so it sat `in_progress` holding its federation claim until the 15-minute orphan sweep — a path meant for genuine orphans, which charged one of the task's finite `orphanRetryCount` retries and armed a 30-minute cooldown for a failure the task did not cause (the agent never started; a momentarily unreachable runner was enough). It now runs the same `finalizeAgent` → `releaseRetryHold` chain the TUI path does, under its own `spawn-rejected` reason, so the task returns to `pending` with its claim released the moment the rejection lands and the runner's actual error is on the agent record.

- A failed X profile read no longer reads as "you are shadowbanned." The reach diagnostic settles the X SPA for a moment and only throws on an origin mismatch, so a page that rate-limited, rendered late, or returned an app shell resolved *successfully* with an empty profile — and all three visibility checks persisted as hard `false` while `last_error` was cleared, presenting a confident "your profile is not public, you do not appear in search, you have no recent posts" verdict produced by a read that simply failed. That is the one conclusion the feature exists to avoid drawing. Each of the three reads is now scored on its own evidence: a page that did not render yields `null` for its checks (shown as the warning-toned "Unknown", with a per-check hint to re-run) and names itself in a plain-language last error instead of clearing it. A page that read fine and did not match still reports `false`, and a positive search hit stays `true` on its own evidence even when a sibling read came back blank.

- CoS agents whose deliverable is a **report** are no longer scored as failures either. `/do:plan-task`, `/do:replan`, `/do:review` and `/do:scan` file an issue or print a report and are explicitly told to write no code, so they reach the idle reaper with a clean tree and no commit — the exact shape the reaper calls `idle-no-changes`. Widening the evidence probe to count in-run commits fixed only the commit-shaped half. Each launchable slashdo workflow now declares its deliverable on its catalog entry: the six that land a commit keep the clean-tree gate armed, and the four report-shaped ones carry `worktreeChangesExpected: false` and opt out of it, the same escape hatch a `reference-watch` run against a forge tracker already uses. `/do:next` still defers to the work tracker its claim flow actually resolved.

- Ten Digital Twin AI passes now actually run. Each shipped a `stage-config.json` entry with no prompt template behind it, so `buildPrompt()` threw "Template not found" and every call site's `.catch(() => null)` quietly took the fallback path — contradiction detection returned no issues, test generation and writing analysis produced nothing, trait extraction and confidence scoring never ran, enrichment served a generic canned question and stored answers unformatted, test scoring degraded to keyword matching, and import/interview analysis was skipped. All ten templates are now authored against what each call site's parser expects, `twin-interview-analyze` gained the config entry it was also missing, and a migration seeds both into existing installs. A new parity guard fails the build if a stage-config entry ever ships without its template again.

- Four sentinel/lifecycle gaps from the v2.40.0 diff are closed. A redirected X handoff (login wall, X redirect) left the Chrome tab it owned open forever, because `openXHandoff` verifies the landing path *after* taking ownership with `closeAfterRead: false` — the tab is now closed before the verification error bubbles. A pending-merge PR whose `gh pr view` fails permanently (deleted PR, renamed repo, revoked token) never ticked, so `MAX_PENDING_MERGE_TICKS` never fired and the entry re-shelled to `gh` forever with nothing surfaced; an unreadable cycle now counts as a tick and times out with a notification naming the PR. The `collaborators` author filter fetched the 100 *oldest* issues by any author and filtered them in memory, hiding a claimable collaborator-filed issue on any busy repo while `self` worked fine — it now fans out one server-side `--author` query per trusted login (capped at 25, with the truncation logged) and merges. And an `api` provider whose `/models` returns HTTP 200 with a non-JSON or unrecognized body no longer overwrites the stored model list with `[]` under a "Models refreshed" toast; it throws with the real reason and leaves the list untouched, the same posture the CLI arms already take. A genuinely empty catalog still saves as empty.

- Three behaviors that shipped with a suite that stayed green when they were deleted now have tests that fail without them. The X reach feature's two safety gates — the 24h stale-approval window and the state-transition guard that stop an approval the user no longer intends from opening a compose window — plus its sync/draft-open re-entrancy guards and the numeric-status-id filter on ingested posts; the review loop's per-reviewer reasoning-effort map, whose whole feature could be dropped from the resolved options with nothing failing; and the remaining provider-benching cases, which asserted against hand-written `{ category, origin }` objects instead of running a transcript through the real detector — the exact pattern that let a genuine usage-limit regression ship green. Each new test was verified by deleting the line it names and watching it fail.
- **CoS tasks filed for PortOS's own work now actually run.** Two producers used `metadata.app` as a feature tag when it is workspace routing — it has to name a record in `data/apps.json`. The Series Pipeline autopilot filed every gap it found (unparseable script, stalled verify, failed render, run-ending error) at `app: pipeline`, and the auto-fixer filed its AI-provider investigations at `app: portos`, which matches neither the seeded app id (`portos-default`) nor its name. Both were harmless until the wrong-repo guard (#3180) closed the silent fall-through to the PortOS root: since then each of these tasks was filed and then rejected at every spawn attempt, so the one mechanism that surfaces an autopilot capability gap never reached an agent. Both now file with no app — which resolves to the PortOS workspace they were always meant to run in — and migration 234 un-routes the ones already queued on existing installs (re-stamping them so the fix wins the sync merge against a peer that hasn't upgraded).

- A CoS task naming an app that doesn't resolve to a repository directory is now **parked as blocked** instead of retried forever. The spawn guard refused to start the agent (correctly — it would otherwise commit into the PortOS checkout) but left the task `pending`, so the scheduler re-dequeued it every tick and reprinted the same error, while the fix was only visible in that task's own log. It now lands in the Blocked list, and the message covers both ways an app resolves to nothing: no Repository Path set, or nothing in Apps matching that id/name at all (in which case the fix is to clear the app from the task, not to register a path).

- Autonomous CoS runs are no longer marked as having failed their success criteria by a check nothing could ever pass. `evaluateSuccessCriteria` judged a run by grepping for a commit whose subject carried the task id — a marker no prompt, template, or slashdo command ever asked an agent to write, and one the repo's own commit conventions forbid. So every ordinary code-editing run recorded `validationPassed: false`, and because a declared verdict outranks the exit code in task-learning, those fabricated failures filled the learning buckets that drive the Learning card, routing, and duration estimates. The criterion is now the same run-window commit probe the idle reaper already uses (did this run leave a commit stamped inside its own window?), shared as `server/lib/gitCommitProbe.js` by finalize, run completion, runner completion, and orphan recovery. A run with no usable window records the "no criterion declared" sentinel rather than a false miss, the existing exemptions for non-committing task types are unchanged, and a migration purges the buckets the old criterion poisoned.

## Privacy Center

- **Your PII vault stays on one machine — permanently, by decision.** The Privacy Center's vault, organization registry, change-of-address inventory and broker opt-out ledger were always machine-local, but that was recorded as a feature not yet built, which left the door open to syncing them to your other PortOS machines later. It is now a documented guarantee: none of it federates, and none of it ever will without a new decision record superseding this one. The reasoning is written up in full — chiefly that PortOS's peer-sync was built for creative work rather than identity data, that the display masks (`••••1234`, `j•••@example.com`) are readable even when the underlying values are encrypted, and that copying one encryption key to several machines would widen the exposure of every one of them. If you want the vault on a second machine, restore a backup and copy the key by hand — a deliberate act, rather than something that happens quietly in the background. Managing PII for other household members is unaffected and remains planned.

- **Peer-sync pull requests now honor the per-peer sharing settings the push direction already respected.** `GET /api/peer-sync/record` served any subscribable record by id with no notion of who was asking, so a peer configured for "universes only" — or one with sync switched off entirely — could still read every series, media collection, and writers-room record; the record/library/CoS-history/CoS-task manifests and the CoS agent-archive bytes had the same shape. Every outbound hop now identifies this install with an `X-PortOS-Instance-Id` header attached centrally in `peerFetch`, and the receiver resolves that id against its peer registry and runs the *same* `peerAllowsOutbound` + `peerHasCategory` predicates the push path uses, so the two directions can't drift apart again. Because peers upgrade independently this ships warn-first: a pull from an unidentified, unknown, or disallowed caller is still served and logs one `⚠️` per caller per restart. The new **Settings → Sharing → "Enforce per-peer sharing settings on pull requests"** toggle (`federation.strictPullAuthorization`, default off) turns those into a 403 — the default flips in a later release once peers have had time to update. Note that the instance id is *identification*, not authentication; the instance password remains the actual access control.

- A `/do:review` (or `/do:scan`, `/do:plan-task`, `/do:replan`) run queued from the **CoS quick templates** is no longer failed as `idle-no-changes`. The deliverable posture each slashdo workflow declares on its catalog entry reached the Agent Operations buttons but was silently dropped by the quick-template form, which read only the three run-shape toggles off a template's settings block — so the exact clean-tree misfire that posture exists to prevent still happened from the other surface. The flag now rides the template through the form as hidden state and into the create-task payload, and the strict template-settings schema accepts it so a user can save such a template back without a 400.
