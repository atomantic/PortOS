## Added

- **Quota Burn is now its own page (`Dev Tools → Quota Burn`) driven by one programmatic loop.** It used to be a `quota-burn` entry in each managed app's `taskTypeOverrides`, which meant the schedule, the provider windows, and the burn prompt were duplicated per app — and two enabled apps ran two independent loops racing for the same window budget, even though quota belongs to the machine, not to any one repo. There is now ONE install-level loop inside PortOS reading one machine-local plan (`data/cos/quota-burn.json`), with a full config surface: master switch, poll interval, and per-provider-family reset window / reserve / dispatch cap / priority.
- **Each family runs an ORDERED list of burn jobs, each with its own type, model, and target** — so "have codex render every universe bible entry that has no image, and only then fall through to agent work" is expressible. Two job types ship: `agent-prompt` (the previous behavior — queue a CoS agent in a *named* managed app, so the work can still target any app) and `universe-bible-images`, a fully programmatic job that enqueues renders for bible entries whose `imageRefs[]` is empty, defaulting the render backend to the burning family's own image mode so a codex burn spends codex's image quota. A new job type is three server edits; the config form builds itself from the server's job catalog.
- The page states, per family, whether it will burn on the next tick and — when it won't — the exact gate that closed (`resets in 40h — outside the 24h window`, `dispatch cap reached (2/2)`, `62% left is at or below the 70% reserve`), evaluated by the same predicate the runner uses. Per-job pending counts, a run log that records skips *with reasons*, and manual "Evaluate now" / "Burn now" / per-job force-run controls are all on the page.
- **Game studio music bindings can now publish into the game repo, symmetric with the artwork lane.** `POST /api/games/:id/music/:bindingId/publish` copies the bound track's library audio into the managed app repository with SHA-256 provenance, an occupied/diverged-destination guard behind an explicit overwrite acknowledgement, a mid-deploy refusal, and per-repo write serialization shared with the artwork lane (one queue, so artwork and music publishes into the same repo can't race). Music bindings gained an editable repo-relative `destinationPath` (`PATCH /api/games/:id/music/:bindingId`, defaulted from the rendered audio filename under `game/assets/music/` at bind time), the integrity preflight now reports published/pending state for music exactly as it does for artwork — without changing the manifest-input hash of destination-less legacy bindings, so upgrading alone can't flag an existing bundle stale — and the Assets tab's music rows grew destination editing, a Publish button, and an inline overwrite-consent flow.
- **CyberCity's ambient music mood can now be pinned by hand.** The Audio tab of the city settings drawer gained a SOUNDSCAPE select — AUTO plus every mood (bright / neutral / tense) — persisted with the other city settings. AUTO is an explicit `null` sentinel, so "following live system health and agent activity" is never confused with a pinned mood, and an unrecognized stored value degrades to AUTO rather than freezing the music. A pinned mood re-derives the whole mood half of the soundscape (chord table, filter cutoff, pad detune) while leaving the activity-driven half live, and setting or clearing it re-ramps the running graph immediately instead of waiting for the next system-state change. (#3395)

## Fixed

- **A successful `branch-cleanup` run is no longer recorded as a failure.** The task deletes merged branches in the app's live checkout — its prompt `cd`s to the repo path and runs `git branch -d` / `git push --delete` — but it was the only git/gh coordinator type shipping with no `taskMetadata` at all, so `applyAppWorktreeDefault` filled `useWorktree`/`openPR` from the app's `defaultOpenPR: true`. Every run got a CoS-managed worktree it never touched (one that holds the very refs it was trying to delete) and a PR expectation it could never satisfy, and finalization scored the completed run `pr-missing`. The four non-committing coordinator types — `branch-cleanup`, `branch-reconcile`, `issue-reconcile`, `jira-status-report` — now share one documented `taskMetadata` posture: `useWorktree`/`openPR` explicitly `false` (not merely absent, which is what let the app defaults in) *and* locked via `MANAGED_AGENT_OPTIONS` so a per-app override can't re-attach them, plus `worktreeChangesExpected: false`, because a clean tree is the success shape for a branch deletion or a posted report and the TUI idle-complete gate must not read it as "the model produced no work". `jira-status-report` was hit by the same bug for a subtler reason: its `readOnly: true` skips worktree *creation* but the finalize-time PR-claim check reads `metadata.openPR` directly, so a posted report still scored `pr-missing`. A guard test now iterates `NON_COMMITTING_COORDINATOR_TASK_TYPES` — the set that already grants these types their commit-criterion exemption — so a future coordinator type can't be added to one list and not the other. Existing installs pick all of this up on the next schedule load: the taskMetadata deep-merge backfills the new keys and `enforceManagedAgentOptions` rewrites any stored `true`.
- **[issue-3396] CyberCity's ambient music no longer drifts under main-thread load.** The chord changes (every 2400ms) and the 16th-note arp plucks (every 150ms) rode two independent `setInterval`s that each read `ctx.currentTime` at fire time — so under load both drifted against the audio clock *and* against each other, the failure mode the sibling synth players adopted the shared lookahead scheduler to avoid. Both now come off one 16th-note step counter (16 steps per chord, so the arp is phase-locked to the chord changes by construction) and every event is written to the audio clock at an absolute grid time, `gridOrigin + step × 0.15s`, which cannot accumulate drift. The timing constants come from `SYNTH_TIMING` in `lib/lookaheadTransport.js` so the feel stays shared; the transport body itself is deliberately not reused, because it reads its clock from the shared `lib/audioContext.js` singleton while `cityAudioEngine` is a documented holdout that owns (and closes) its own `AudioContext` — scheduling this graph against a clock it doesn't run on would be worse than the drift. A backgrounded tab now re-anchors to the grid on return instead of dumping every missed step into one burst. Generative behavior (chord walk, mood sets, energy-driven arp gain) and the stop-ramp contract are unchanged.
- **A manually-triggered ("Run Now") perpetual claim drain no longer stalls after one item.** A `claim-issue` / `claim-work` schedule set to *perpetual* is meant to drain actionable work back-to-back. When the daemon's own scheduler drives it that works, but a manual "Run Now" (`RunTaskButton` → `POST /api/cos/schedule/trigger`) did not: the on-demand trigger only gates on the master Improve flag, so the first item ran, but `refillPerpetualForCompletedAgent` then gated the *continuation* on `canQueueImprovementTasks` — which additionally requires idle-review ON **and** CoS auto-run = `execute`. Those are exactly the postures in which a user reaches for "Run Now" (auto-run off/dry-run, or idle-review off), so the drain refused to spin up the next item even with a queue of claimable issues. The refill now routes a manual drain through `perpetualRefillPlan`'s `onDemand` lane: it re-issues an on-demand request for the same task type + app, gated only on the master Improve flag (matching what let the manual run START), and returns before the auto-run-gated queue lane — so a manual perpetual drain keeps draining, scoped to that one type+app (it can't leak unrelated rotation/idle autonomous work past the auto-run kill switch), until the work-detector parks. The on-demand spawn engines mark generated tasks `metadata.onDemand` (projected onto the agent as `taskOnDemand`) and forward the completion's `ignoreTaskId` to `addTask`, so the re-issued claim isn't rejected as a duplicate of the still-`in_progress` run that just triggered it. Scheduled perpetual drains are unchanged.
- **[issue-3400] Rendering two storyboard scenes at once no longer loses one of the jobs.** `enqueueStoryboardSceneVideo`, `enqueueStoryboardShotStartFrame`, and `refineStoryboardScenePrompt` each read `stages.storyboards.scenes` up front, then wrote the whole pre-read array back through `updateStage`. That write *is* serialized, but the array it shallow-merges was built outside the lock — so two enqueues for different scenes that both read before either wrote would revert each other's freshly-stamped `sceneVideoJobId` / `startFrameJobId`, and the losing render would run to completion with nothing left pointing at it. All three now patch a single scene through `updateStageWithLatest`, so the read-modify-write of `scenes` happens inside the write region and only the targeted index is replaced. A scene that disappeared between the caller's read and the write now 404s instead of resurrecting itself.
- **[issue-3413] A storyboard scene is now addressed by a durable id, and a rejected render write no longer orphans its job.** #3400 stopped two concurrent enqueues from clobbering each other, but scenes were still addressed purely by array index end to end — the route took `sceneIndex`, the media-job owner encoded `scene<idx>`, and the write patched `scenes[index]` — so a reorder or delete landing between a caller's read and its write silently retargeted the job id onto whatever scene now sat in that slot (only the out-of-range case 404'd), and the completion hook routed the finished render by the same stale index, making the mis-targeting consistent rather than self-correcting. Scenes (and shots) now carry a durable `id` stamped by `sanitizeVisualStage` and backfilled on existing installs by migration 222 (file store) + db-migration 007 (Postgres); the ids are deterministic (`scene-01`, collision-escaped) so concurrent readers and federated peers derive identical values. Every write region re-resolves the captured id against the fresh array and returns 409 `PIPELINE_SCENE_STALE_TARGET` / `PIPELINE_SHOT_STALE_TARGET` when the target is gone, distinct from the 404 for an index that never existed, with the index kept only as the fallback for pre-migration records. Media-job owners carry the ids too (percent-encoded), and the filename hook still attaches jobs queued under the legacy index-only owner. Separately, all three render surfaces — storyboard scene/shot, comic page slot, and issue/volume covers — now cancel the job they just enqueued when the stage write rejects, instead of leaving it queued with nothing referencing it.
- **[issue-3407] Stacker News sync works again.** Stacker News renamed its territory listing route from `/recent` to `/new`, so every browser-transport sync was refused with "landed on a different page than the one requested" — the redirect guard correctly caught the rename. Syncs now request the new route directly; the guard stays strict.
- **A completed TUI agent could be recorded as failed by a duplicate finalize.** `cleanupOrphanedAgents` runs every 15 minutes and calls `syncRunnerAgents`, which only checked `runnerAgents` for "already tracked" — but a runner-backed TUI agent is owned by the live `spawnTuiAgent` closure, which registers in `activeAgents` and never in `runnerAgents`. Any TUI run outliving one health-check tick was therefore hoisted into `runnerAgents` mid-flight, so the `agent:completed` event the runner emits when the TUI spawner's own `finish()` kills the session slipped past the `if (!agent) return` guard and ran a *second* `finalizeAgent`. That overwrote a sentinel-signalled success with `success: false, exitCode: 143` plus a bogus `startup-failure` analysis (computed from an output buffer that path can't read — a TUI writes `output.txt` under the dated run dir, not `AGENTS_DIR/<id>`), which in turn flipped the agent card to Failed and requeued the already-finished task as `pending`. Observed on a 55-minute release-check run that had already published v2.37.0 and merged all three of its PRs.
- **`completeAgent` is now idempotent, so the caller-level guard is no longer the only line of defense.** Six call sites funnel every terminal agent write through `completeAgent`, and each carried the same latent "I might be second" assumption. A duplicate call re-recorded `result` (success verdict, exit code, error analysis) and re-ran the completed-agent directory move; the guards that caught the TUI double-finalize above read the record *outside* the state lock, so they narrowed the race rather than closing it. `completeAgent` now returns an already-`completed` record unmutated from inside the lock it already holds — and skips the budget-ledger charge and the second `agent:completed` emit that would otherwise re-run the scheduler hand-off. `paused` records are still completable, so a resumed agent can't wedge. The one thing a duplicate *does* still do is finish a half-written archive: `archiveCompletedAgent` is now idempotent (the directory move is skipped once the date bucket exists, the index write always re-runs because `saveAgentIndex` swallows its own errors), and the cross-filesystem copy fallback rolls back a partially-copied target instead of leaving a directory that every later attempt mistakes for a finished archive.
