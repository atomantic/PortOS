# Unreleased

## Changed

- **The agent lifecycle has a named entry point instead of seven mutually-recursive modules.** The `cos.js → cosAgents.js → cosAgentLifecycle.js → agentManagement.js → agents.js → subAgentSpawner.js → agentLifecycle.js` cluster has no owner, so reasoning about one transition — pause, kill, complete, spawn — means holding all seven files in mind, and several of the back-edges are `await import(...)` calls that exist only to dodge a load-time cycle. `server/services/agentOrchestrator.js` is the facade above that cluster: it imports the transition owners one-directionally, carries the transition-vs-leaf classification in its header so later passes start from it, and renames apart the two different functions both called `terminateAgent` — `requestAgentTermination` only emits the event and returns, while `terminateAgent` keeps the name for the real SIGTERM/SIGKILL sequence. The four agent routes (terminate, pause, kill, stats) now go through it, one hop instead of three. `agentImportCycles.test.js` gains a guard that fails if anything reachable from the facade imports it back, statically *or* via `import(...)` — the dynamic form matters because reaching across a blocked layer that way is exactly this cluster's habit, and the forbidden set is derived from the graph rather than listed so it can't fall behind. Widening that suite's graph builder to walk subdirectories closed a hole in the pre-existing cycle guard too: it read only top-level `server/services/*.js`, so a cycle routed through one subdirectory hop (`agentTuiSpawning/outputSpooler.js` already imports back up to `../cosAgents.js`) was invisible to it. The remaining call sites and the dynamic-import workarounds follow in later PRs (#3450).

- **The agent-lifecycle cluster lost the deferred imports it used to reach across its own layering.** `cosAgentLifecycle.js` carried three `await import('./agentManagement.js')` forwarders — `pauseAgent`, `killAgent`, `getAgentProcessStats` — that existed purely so a caller holding a `cos.js` handle could reach the process layer from the agent *state* layer, which cannot import it statically without inverting the layering. Their only consumer was `cos.js`'s own re-export block, so both are gone: those three transitions come from `agentOrchestrator.js` now. `agents.js` moved onto the facade too, which needed an actual structural fix rather than an import swap — it was stuck reaching `killAgent` through `await import('./subAgentSpawner.js')` because `agentManagement.js` imported `unregisterSpawnedAgent` back out of it, and that same back-edge put `agents.js` inside the facade's closure where importing the facade was forbidden. Pushing the pid map both sides wanted down into `agentState.js` — the import-free leaf they already shared other agent state through — deleted the edge; `agents.js` fell out of the closure and took a plain static import. `subAgentSpawner.js`'s event wiring (`task:ready` → spawn, `agent:terminate` → terminate, runner-error → complete) now asks the facade for those transitions instead of three separate leaves. `agentImportCycles.test.js` gains a guard for each half, each verified to fail on a planted violation: no new deferred import from the state layer into the process layer, no process-layer transition back in `cos.js`'s re-export block (derived from the facade's own export blocks rather than a hand-listed set, minus the one genuine name collision), `agentState.js` stays import-free, and `agents.js` reaches the facade statically. The facade header now describes that extract-a-leaf move as the shape every remaining migration takes, rather than carrying a call-site inventory that would go stale (#3450).

- **The agent cluster's back-compat re-export barrel is retired, so a lifecycle transition has one address instead of three.** `subAgentSpawner.js` re-exported ~40 symbols from nine sibling modules "for backward compatibility" — a second, partial view of the cluster layered over `cosAgents.js` and `cos.js`'s agent block, including the same three process-layer transitions (`pauseAgent` / `killAgent` / `getAgentProcessStats`) that `agentOrchestrator.js` owns. That overlap is why the previous PR's "no module may re-export a facade transition" guard had to be narrowed to `cos.js`: stating the rule generally would have failed on the barrel. The barrel had almost no consumers left — `telegram.js` reaching `getActiveAgents`, two `await import('./subAgentSpawner.js')` calls in `cos.js` for `cleanupOrphanedAgents` / `handleOrphanedTask`, and three test files — and all of them now name the module that actually defines what they want, which also deletes the last two `cos.js → subAgentSpawner.js` edges from the seven-module chain. `agentLifecycle.js`'s pass-through re-exports of the leaves extracted out of it (`finalizeAgent`, `extractFinalSummary`, `syncRunnerAgents`, the worktree-cleanup cluster) went with it: the barrel was their last consumer, and an orchestrator re-exporting the leaves beneath it is what made "where does `finalizeAgent` live" a three-answer question. What remains in `subAgentSpawner.js` is what it actually does — `initSpawner()`'s runner connection and event wiring. Two guards in `agentImportCycles.test.js` hold the line, both bypass-probed: the transition re-export rule now runs over `cos.js` *and* `subAgentSpawner.js`, and a new one asserts each cluster orchestrator declares everything it exports, comparing the module's live key list against its own declarations so `export *`, `export { x } from …`, and `import` + a bare `export { x }` all fail identically rather than each needing its own regex (#3450).

- **Every view that used to show a bare "Loading…" text node now uses the shared loading affordances.** ~35 views across Music, MeatSpace, Media, Pipeline, Sprites, Writers Room, Sync, Catalog and a dozen pages rendered unstyled text while fetching, which read as broken content rather than a deliberate loading state. Small inline loads (buttons, side lists, drawer subtitles, popover menus) now render `BrailleSpinner`; full-page and card-grid loads render `PageSkeleton`, which reserves the eventual content's dimensions so the first paint doesn't reflow and announces itself via `role="status"`/`aria-busy`. Several hand-rolled `Loader2 + animate-spin` one-offs collapsed onto the same two components, and the pipeline audio music-library panel lost its duplicate second spinner.

- **Three structural cleanups that each removed a way to get something silently wrong.** `buildReviewWithArgs` took seven positionals, with two same-shaped reviewer-name arrays adjacent to each other and two same-shaped per-reviewer lookup maps adjacent to each other — transposing either pair produced a plausible-looking flag string and no error; everything past the reviewer list is now a named options object. The ecosystem-config branch of `streamDetection` nested eight levels deep to probe each PM2 process's vite config, duplicating that loop byte-for-byte in `parseEcosystemFromPath`; both now call the exported `resolveViteConfigPortForProcess`, which owns the gate and the candidate order and has its own tests (the "stray closing brace" flagged in that block turned out to be mis-indentation, not a structural bug). And `client/src/utils/fileUpload.js` no longer re-exports the four network-calling upload helpers it handed off to `services/apiMedia.js` — the real call sites import them from the services module directly, so the pure-helpers module has no reach into the network layer again (#3452).

- **The root `pm2` dependency moved out of the dev-only bucket, because `npm start` launches the production process with it.** The root `start`, `pm2:*` and `dev:stop` scripts all invoke `./node_modules/pm2/bin/pm2`, so an install run with `--omit=dev` (or `NODE_ENV=production`) would have left every one of them with no binary to run. Nothing in the repo installs that way today and `server/package.json` already declares `pm2` as a normal dependency, so this was a latent footgun rather than a live break — but it would have cost someone an afternoon the first time a slimmed Docker or CI install path appeared. The lockfile change is limited to the bucket rename and dropping `"dev": true` from pm2 and its transitives; no versions moved. `scripts/root-runtime-deps.test.js` now derives the rule from the manifest instead of hardcoding pm2 — every package a root script reaches into via `./node_modules/<pkg>/…` has to be a real dependency — so the next root script wired to a dev-only binary fails the suite rather than waiting for a production install path to expose it.

- **Replaced ESLint with Biome in the client, dropping 110 net packages including the `keyv` chain named in the August 2026 npm compromise.** `keyv`, `flat-cache`, and `file-entry-cache` were hit by the Shai-Hulud supply-chain attack. PortOS was never exposed — it held `keyv@4.5.4` / `flat-cache@4.0.1` / `file-entry-cache@8.0.0` while the malicious releases were the *next major* in each line, unreachable from the caret ranges in the lockfile, with no install hook anywhere in the tree (npm has since unpublished all three). They were not direct dependencies either: they arrived as a single chain under one root, `eslint → file-entry-cache → flat-cache → keyv`, dev-only and client-only. Since `eslint@10.8.0` hard-requires `file-entry-cache` and no release drops it, the only way to shed the chain was to stop using ESLint — so this is a maintenance win, not a security fix. An `overrides` pin would have been a no-op, because every range was already at the top of its published major.

  `@biomejs/biome@2.5.7` replaces the stack: a native binary with no regular dependencies and 8 platform optionals, of which one installs. The client lockfile goes 447 → 337 packages. That count includes `typescript`, which the migration orphaned — it was a client devDependency purely to satisfy `@eslint-react/eslint-plugin`'s peer dep, and with the client holding no `tsconfig`, no `.ts`/`.tsx` sources, no `tsc` script, and nothing peer-depending on it, it came out too (retiring a Dependabot ignore rule and issue #3351 with it). Parity was proven with fixtures rather than inferred from a clean run — a linter with no rules also reports zero problems — and `npm run lint` still covers the same 1859 files with 0 problems. The swap was cheap largely because `exhaustive-deps` was already deliberately disabled, which is the rule that usually makes linter migrations painful.

  The `crypto.randomUUID` ban is preserved as a GritQL plugin, and it matters: that call is undefined on insecure origins, and PortOS is routinely reached over plain HTTP via Tailscale. It matches on the syntax-tree node kind rather than code snippets, so it still catches `crypto.`, `globalThis.crypto.`, `window.`, `self.`, optional chaining, bare `typeof` references, and assignment targets — while continuing to ignore `crypto['randomUUID']` exactly as the old rule did. Its exemptions for `src/lib/uuid.js` and test files are written as negated globs because a Biome override's `plugins` list is additive, so an empty list does not disable an inherited plugin.

  Deliberately kept narrow: Biome's formatter and assist actions are off (turning them on would rewrite all 1859 files in one unreviewable diff), and the rule set is an explicit list rather than Biome's broader `recommended` preset, so this is a tooling swap and not a silent change to lint policy. Adopting more of Biome's rules is a separate decision.

## Fixed

- **Two agents working a swarm run could overwrite each other's pull-request descriptions.** Every agent in a swarm shares one scratch directory and — by design — runs byte-identical instructions, so when two of them reached the "write the PR description to a file" step they independently picked the same obvious filename and the second quietly overwrote the first. The failure was invisible: nothing errored, the text was well-formed, and it only surfaced minutes later when the first agent re-published its now-replaced description onto its own PR. Swarm runs now hand each agent its own scratch subdirectory named for the issue it's working, so no two agents can collide on a filename, and each agent re-reads its published description after creating or editing it to confirm the right one landed. Single-issue runs are unchanged.

- **Quota burn stopped after the first family it dispatched, so a longer-windowed provider never burned at all.** A cycle selected every family whose window was inside its reset horizon, sorted them soonest-reset-first — and then returned after the first successful dispatch. Families do not share a budget: each draws down its own subscription window, against its own reserve and its own `maxDispatchesPerWindow`, so stopping early protected nothing. It just meant the soonest-resetting family took every cycle. A `claude` window resetting in 2h beat an `agy` window resetting in 21h on every tick, and the Antigravity plan sat at "93% left · 0/5 used" indefinitely while its eight configured audits never ran. A cycle now dispatches one job per *family*, records a run-log row per dispatch (so no family is hidden from the audit list), charges each window against its own key, and continues past a family whose job declines. When several plans are walked, every skip reason is prefixed with the family it came from.

- **The burn-job preset picker snapped back to "Choose a preset…" the moment you picked one.** Applying a preset copies its text into the step's work prompt 60 lines further down the row, so with the control blank the click read as a no-op and people picked again. It now shows the preset whose prompt the step still matches verbatim — derived from the text rather than stored, since nothing on disk records a preset id, so it reverts to the placeholder as soon as the prompt is edited into something else and never claims a step is an audit it no longer is. Re-picking the preset a row already matches no longer raises the "replace your text?" confirm; the text *is* that preset's.

- **Content cards were nearly invisible against the page in every theme, and dissolved completely at reduced opacity.** Card and page colors were separated by as little as 1.04:1 (Classic Noon, Black ICE Terminal) — and the common `bg-port-card/40` spelling then faded even that toward the page, leaving a themed border floating around nothing. Cards now render against a per-theme fill floor (`--port-card-min-alpha`), every theme's card/page pair clears a 1.12:1 separation, and the card elevation rule covers all fill opacities instead of only `bg-port-card/50`, so two cards on one page can't sit at different elevations for no visible reason. Hover and active variants are deliberately left unfloored — a hover landing on the resting fill is not feedback — and translucent themes set their own lower floor so glass stays glass. `portosThemes.test.js` asserts the separation, the floor ordering, and that body and muted text still clear WCAG AA on the resulting fill, for every theme; `docs/themes/README.md` documents the three-level page/card/well scale.

- **The `ignore-scripts` supply-chain guard was silently inactive for every workspace install, including CI.** The repo-root `.npmrc` has pinned `ignore-scripts=true` for a while, but npm resolves the project `.npmrc` from the *local prefix* and never walks up the directory tree — so it never applied to `cd client && npm install`, `cd server && npm install`, or `npm ci --prefix server` / `--prefix client`, which is exactly what CI runs and what the documented per-workspace test workflow uses. In those paths every dependency kept an install-time code-execution slot: the same slot the August 2026 keyv/cacheable (Shai-Hulud) worm used, via a `preinstall` hook, to harvest credentials before any application code ran. `client/`, `server/`, `autofixer/`, and `browser/` now each carry their own `.npmrc`, so the guard holds in every workspace install path — whether entered by `cd`ing in or via `--prefix`.

  Closing the hole made the trusted-rebuild allowlist load-bearing for the first time, and it had drifted across its five copies (the root `setup` script, `scripts/ensure-deps.js`, `update.sh`, `update.ps1`, `setup.ps1`): the `esbuild` entries were dead — vite 8 dropped that dependency — while `onnxruntime-node` and `protobufjs` were missing entirely, so CI ran install hooks that the local setup skipped. All five now read one allowlist from `scripts/trusted-rebuilds.js`, and CI rebuilds it explicitly after installing server dependencies so `node-pty`'s native binding is still present for the smoke-boot. `scripts/trusted-rebuilds.test.js` fails if any workspace `.npmrc` loses the setting, or if a dependency shows up with an install hook nobody has decided about — the second case being how a missing native build otherwise surfaces much later as a confusing runtime crash.

- **Release notes told fresh-clone users to run `npm install`, which cannot produce a working install.** The fallback release-notes template in `.github/workflows/release.yml` printed a `git clone` + `npm install` + `pm2 start` sequence, but a bare root `npm install` skips the client, server, and Autofixer workspaces, never initializes the bundled submodules, and does no data/database provisioning. It now points at `npm run install:all`, matching the README.

- **Replaced a real Tailscale identity with placeholders across tracked files, and added a guard so it can't come back.** A real MagicDNS tailnet suffix, real device names, and a real CGNAT peer IP had been committed across server routes/lib, client lib, several test fixtures, two design-plan docs, and two released changelog entries — ~14 tracked files in a public repo. This violates the repo's own `CLAUDE.md` "Sensitive Data & Privacy" rule, which lists Tailscale node/MagicDNS names and Tailscale/LAN IPs as never-commit categories. Every occurrence is now an obviously-fake placeholder (`example-tailnet.ts.net`, `host-alpha`/`beta`/`gamma`/`delta`, a documented CGNAT test IP), preserving the two-host distinctness some tests relied on. A new `scripts/tailnet-identity-leak.test.js` enumerates *tracked* files via `git grep` and fails the moment a real-looking tailnet host or CGNAT address lands again — whether via a pasted log line, a doc example lifted from a live install, or a copy-pasted test fixture.

  These are identifiers, not credentials — Tailscale ACLs still gate all actual network access, and no auth key, token, or secret was ever committed. The historical occurrences remain in git history by deliberate decision (see #3455): a `git filter-repo` rewrite would break every fork and clone of this fork-aware project to remove values that grant no access on their own.

- **The productivity streak store no longer hands back its module-level defaults, and both it and the weekly digest now have real tests.** `server/services/productivity.js` and `server/services/weeklyDigest.js` were referenced in the suite only as `vi.mock()` targets, so ~1,400 lines of streak arithmetic, day/week-boundary handling, and digest assembly were executed by zero tests. They now have direct suites (66 cases) that stub only the file-I/O boundary and the agent-history source and assert concrete values — streak counts across gaps, midnight and year-boundary rollovers, insight copy, week-over-week deltas, and the rendered text summary. Writing them surfaced a real bug: `loadProductivity()` returned the shared `DEFAULT_PRODUCTIVITY` object when no store file existed, so the first incremental `onTaskCompleted()` mutated the module constant in place and every later "empty store" read came back pre-populated. It now clones the defaults per read.

- **Tests that re-implemented the code they claimed to test now import the real thing — which exposed a NaN bug and a timezone mismatch.** Seven suites (`meatspace`, `identity`, `meatspaceAlcohol`, `meatspaceHealth`, `taskConflict`, `appleHealthClinical`, `featureAgents`) defined local copies of the pure functions under test, with comments calling it the project pattern. Every one of those functions was already exported, so the copies bought nothing and passed regardless of what production did. Swapping in the real imports surfaced two divergences the copies had been hiding: `computeGoalUrgency` guards `horizonYears <= 0 || yearsRemaining <= 0` and returns `1`, which the stale copy lacked — so a lifetime-horizon goal computed after a user's life expectancy has elapsed divided `0/0` and rendered `NaN` urgency; and `computeRollingAverages` keys days by local calendar date while its fixtures used UTC, a mismatch that only bites near local midnight west of UTC and passed on UTC-set CI by coincidence. `meatspaceHealth`'s helpers were never exported at all, so that suite now drives the real async functions with I/O mocked, and takes its BP classifier from the client module that is its actual source of truth (kept in sync with the iOS companion) instead of a third copy.

- **The cron core beneath every scheduler is no longer executed by zero tests.** `server/services/eventScheduler.js` was `vi.mock()`'d out by all five of its consumers, so its field parsing and timer math never ran under test. It now has 43 tests covering cron syntax, out-of-range and malformed input, the `dayOfWeek` 7≡0 alias, and the `schedule`/`cancel`/`pause`/`resume` lifecycle under fake timers. Adds first coverage for `localThinking.js` (21 tests) and `useOpenClawStream.js` (10, including the stale-session-switch guard and abort-on-unmount), and exports `calculateBackoff` so its math is tested directly rather than transcribed.

- **The shared `settled()` test helper no longer inherits a 1-second timeout.** `client/src/test/settledInput.js` called `waitFor` with no override, and neither `client/vitest.config.js` nor `client/src/test/setup.js` raises testing-library's 1000ms default — too tight for a `user.type()` plus a React re-render when parallel workers are contending for CPU. It produced a phantom `toHaveValue` failure in 1 of the 7 suites that use it. Now 3000ms, with a comment explaining why so it doesn't get simplified back.

- **Covered the production memory backend, which had zero tests.** `server/services/memoryDB.js` — the Postgres + pgvector backend every real install runs — had no suite at all; the only "memory" coverage was `memory.test.js`, which exercises the dev/test-only file backend. The new `server/services/memoryDB.db.test.js` runs against the throwaway `portos_test` database via `npm run test:db` and covers the CRUD/embedding round-trip, listing filters and stats, `searchMemories`/`hybridSearchMemories` (vector, full-text and fused rankings, plus zero-result queries proven to be searched-and-empty rather than never-searched), `consolidateMemories` cluster merging, `applyDecay` boundaries (the 30-day archive gate, the 0.15 cut-off and the 0.1 importance floor), and `getGraphData`'s node/edge shape. It caught one live bug: `createMemory` echoed a wrong-dimension embedding back to the caller even though the column had stored NULL, so a re-embed check gated on the returned value would skip the record — it now mirrors `updateMemoryEmbedding` and returns `null`.

- **The boot order every install depends on is now executed by tests instead of only described in comments.** `server/services/bootstrap.js` opened with "ordering inside each phase is load-bearing" — and nothing tested it: the file can't be imported under test (it pulls the whole service graph and its steps open a listener, a database, and agent workers), so `bootstrapServices()` and `runBootSequence()` had no regression net at all. The ordering now lives in `server/services/bootstrapSequence.js`, which imports nothing and takes every step as a parameter; `bootstrap.js` supplies the real migration runner, toolkit, stores and listener, and the sequence module decides when each runs. 41 new tests assert the recorded call sequence — migrations before the toolkit reads its config, sync log before brain recovery appends to it, the media job queue before its completion hooks, the whole database phase before `listen()` — plus which steps are awaited and which are deliberately fire-and-forget, the fatal-vs-log-and-continue split at each failure point, and a source guard that fails if any AI-provider entry point is ever invoked from the boot path (CLAUDE.md "No cold-bootstrap LLM calls").

- **`PUT /api/lmstudio/config` validated nothing.** It read `baseUrl`/`timeout`/`defaultThinkingModel` straight off `req.body`, and `updateConfig()` assigned any truthy value into module-level config that every other LM Studio call then interpolates into fetch URLs — so one malformed request degraded local-LLM connectivity until restart. All eight routes in the file now validate through `lib/validation.js` schemas, matching the rest of `server/routes/`. The schemas are non-`.strict()`, so incidental extra fields still pass through.

- **A throw in the `logs:subscribe` socket handler could kill the process, and its error events were being silently dropped.** It was the only async handler in `server/services/socket.js` without a try/catch — and an `async` function passed to `socket.on()` has no framework rejection handler, so a synchronous throw became an unhandled rejection. Adding the guard exposed a second bug: `processName` was destructured inside the `try`, so the `catch` emitted `logs:error` without it, and the client's listener filters on `processName` — meaning every error event was discarded and the log panel hung with no feedback. Both fixed, with a test that fails against the old emit shape.

- **Two import cycles, one of which leaked filesystem I/O into a directory reserved for pure helpers.** `server/lib/storyBible.js` re-exported `createBibleStore` from `services/bibleStore.js`, which imports back from it — so roughly fifteen genuinely-pure `lib/` modules that import only sanitizers were transitively pulling in that service's file CRUD. Separately `meatspacePost.js` and `meatspacePostTraining.js` imported each other with none of the dynamic-import mitigation their sibling cycles carry; the shared streak computation and the training-log storage primitives are now two one-way modules. Both cycles verified gone with `madge --circular`. Also moves the upload functions out of `client/src/utils/fileUpload.js` (they made live network calls from a pure-helpers directory) into `services/apiMedia.js`, which already owned the underlying HTTP wrappers, behind a re-export so no caller had to change (#3452 tracks retiring it).

- **184 icon-only buttons had no accessible name, and 62 close buttons were smaller than a fingertip.** The icon-only buttons carried only a `title`, which is mouse-hover-only — undiscoverable on touch, and this app is opened from phones and tablets over the tailnet — and is not reliably read as the accessible name. The close buttons were sized to their bare icon (`w-4 h-4`, `p-1`) rather than the 44px minimum `Drawer.jsx` already established; only 9 of 59 files followed it, and one had no sizing at all. Where a smaller `min-h` token already existed it was replaced rather than paired, since two competing `min-h-*` utilities resolve by stylesheet order, not source order. `a11yConventions.test.js` now enforces both rules — writing the guard found five more buttons with no accessible name at all, and hardening it after review found two live sub-44px close buttons its first version couldn't see because it only matched literal `aria-label="Close…"` strings and missed every dynamic label.

- **The tailnet identity guard had a bypass on exactly the leak class it exists to catch.** Its suffix pattern required a digit in the `tail<token>` segment, but Tailscale picks that token at random from lowercase alphanumerics — so a real hostname whose token happened to be all letters passed silently. It now matches the shape and subtracts known placeholder tokens by exact name, which fails closed: an unrecognized placeholder trips the guard and gets looked at, rather than a real hostname slipping through for lacking a digit.

- **The MeatSpace life-progress bar was the one part of that panel that didn't follow the theme.** Its fill color was three inline hex literals (`#ef4444`/`#f59e0b`/`#3b82f6`) while the surrounding card already used `border-port-border` and `text-port-error` — so switching themes re-colored everything around the bar but not the bar. It now reads `rgb(var(--port-error))` / `rgb(var(--port-warning))` / `rgb(var(--port-accent))`. Separately, the `#3b82f6` default swatch was independently hardcoded at five places across the agents and calendar config UIs; a native `<input type="color">` genuinely needs a literal hex, so the literal stays — but there is now one `DEFAULT_AVATAR_COLOR` derived from the default theme's accent that all five import, instead of five edits to change the fallback (#3453).

- **The CoS week id paired the ISO week number with the calendar year, which both split and reused week ids around New Year.** `getWeekId()` was duplicated in `productivity.js` and `weeklyDigest.js` and built as `${date.getFullYear()}-W${isoWeek}` — so Mon 2025-12-29 and Thu 2026-01-01, one and the same ISO week, stamped `2025-W01` and `2026-W01` (breaking the weekly streak and mis-ordering the `longestWeekly` scan), while the *January* week of that same year stamped `2025-W01` too, so the late-December digest overwrote the early-January one on disk. The helper now lives once in `server/lib/isoWeek.js` and keys on the ISO week-numbering year — the calendar year of that week's Thursday — so one ISO week has one id and no id is ever reused. `isConsecutiveWeek` moved with it and now bridges a rollover only when the earlier week is genuinely its year's last, which a bare `week >= 52` check got wrong for the 53-week years (2026 is one). Migration 224 renames existing digest files and rewrites `streaks.lastActiveWeek`, resolving each record from its own stored `weekStart` / `lastActiveDate` and leaving anything it cannot resolve untouched rather than guessing a digest onto the wrong week.

- **The 1-second async-assertion timeout that flaked the QuotaBurn retry-budget test is now raised suite-wide, not per call site.** `QuotaBurn.test.jsx`'s "stops claiming it is saving once the retry budget is spent" failed roughly 1 run in 3 in isolation: it waits on a 500ms debounced save *plus* its retry — two sequential windows — against testing-library's uncustomized 1000ms `waitFor` default, which parallel-worker CPU contention pushes past. The same diagnosis had already been made once and fixed in one place (`settledInput.js`'s local `{ timeout: 3000 }`), leaving every other debounce-sensitive test exposed and the diagnosis waiting to be rediscovered. `client/src/test/setup.js` now calls `configure({ asyncUtilTimeout: 3000 })` once, carrying the rationale, and the five now-redundant local overrides in `settledInput.js`, `MediaCollections.test.jsx` and `ReferenceAnalysis.test.jsx` are gone. The cost is that a genuinely hung assertion takes 3s instead of 1s to fail; the full client suite still runs in ~26s.

- **The CoS prompt-builder suite let the contributor's own global `CLAUDE.md` decide its results, so its suppression checks had never actually run on CI.** `buildAgentPrompt` reads `~/.claude/CLAUDE.md` off the real filesystem and splices it verbatim into the prompt, and `agentPromptBuilder.test.js` then asserts the prompt does *not* contain things like `gh pr merge`. That made every negative assertion in the file unsound in both directions: it false-failed on a machine whose personal global instructions happened to mention the string, and — worse — false-passed on a machine with no such file at all, which is exactly what CI is, so the suppression those assertions exist to prove was never exercised there. `homedir()` is now stubbed to a path that cannot exist, making the global section deterministically empty, and a new fixture-backed test closes the gap from the other side: it points the stub at a throwaway home whose global `CLAUDE.md` deliberately *does* contain the suppressed strings, asserts the fixture really is spliced in verbatim, and then asserts every section the builder itself authored still omits them on the reasoning-only path. Verified by breaking the suppression and watching the new test fail (#3475).

- **`completeAgent` had three addresses, and the four callers that most needed one address were using the wrong one.** Continuing #3450's sequencing: `agentManagement.js`, `agentLifecycle.js`, `agentFinalization.js` and `agentCliSpawning.js` all reached the completion transition through the `cosAgents.js` barrel. These four are the callers the "move the caller above the facade" recipe cannot reach — the first two DEFINE transitions `agentOrchestrator.js` re-exports, so importing the facade from either is the cycle itself, and the other two are leaves those two must call to spawn and to finalize. So the rule they follow is the other half of the same property: above the facade's closure a transition comes from the facade, inside it from the module that DECLARES it (`cosAgentLifecycle.js`), and never from a barrel. `cleanupOrphanedAgents`'s `await import('./cos.js')` went with it — it was pulling `completeAgent` and `getAgents` through the `cos.js` re-export block while the module was already a static import three lines up, so the deferral bought no cycle protection at all. The new guard in `agentImportCycles.test.js` derives the transition names from the facade's export blocks and walks re-export edges to work out which modules forward them, so a barrel added later is covered without being named; it catches a named import, a renamed one, a namespace property read, a destructure off a namespace handle, and the three deferred spellings of the same reaches — including `const { completeAgent } = await import('./cos.js')`, the exact pattern this change deleted. Each bypass-probed.

- **The "Pick from Gallery" picker could only be narrowed by typing, so finding one object in one universe meant recalling a word from its prompt.** It now carries two dropdowns beside the search box: a scope select that groups every universe and media collection under `<optgroup>`s, and a type select built from the `entryCategory`/`entryKind` tags the Universe Builder stamps onto sidecars, labelled through the same `humanizeCategory` the Builder uses. Those two are separate vocabularies — a user-authored bucket can legitimately be keyed `canon` — so the type options are prefixed by which field they filter and grouped under Categories/Entry kinds rather than flattened into one list where the bucket and the stage would silently match each other. All three filters AND-combine, and both dropdowns list only universes/collections/types that actually match an image currently in the picker — a scope that can only ever produce an empty grid isn't offered, and a selection that stops matching resets itself to "All" rather than silently blanking the grid. Collection membership is matched on the stored `{ kind, ref }` pair (the same `<kind>:<ref>` string `normalizeImage` puts on `item.key`), not on a bare filename, so a collection holding video refs alongside images filters correctly. Both option fetches are best-effort: if the collections or universes call fails the picker keeps working, falling back to the universe name stamped on each sidecar, and the fetched lists are dropped on close so a reopen can't filter fresh images against stale membership. Sidecars are unvalidated JSON that also arrive from peers, so a tag that isn't a usable string is skipped rather than crashing the render — which surfaced a latent bug in the shared `humanizeCategory`: its label lookup wasn't `hasOwn`-guarded, so a user-authored category keyed `constructor` or `toString` resolved to an inherited function and handed every caller a label that throws on the next string method (#3479).
