# Unreleased

## Changed

- **Quota Burn's per-family "Provider ID" and "Window scope" boxes are gone.** Both were free-text overrides for decisions the page already makes correctly on its own: the family match already prefers the watchable TUI provider over the headless CLI (a hand-typed id could only ever pick a worse one), and window targeting already reads *every* window on the card — the broadest one as the target the reset horizon and dispatch cap key on, the narrowest as the one that will refuse first, the tightest as the one the reserve guards. Scope was a free-text filter over that, so its realistic uses were "type the same thing the classifier already picked" or "type a word this provider doesn't publish and silently never burn." A job still carries its own optional `providerId`, which is the level where naming a specific provider actually means something. Configs written before this load unchanged — the normalizer drops both keys on the next save — and migration 221 no longer carries them over from the retired per-app shape.

- **Quota burn's dispatch cap is now opt-in — `-1` (unlimited) is the default, so a plan stops when the *quota* says so rather than when a tally runs out.** `maxDispatchesPerWindow` counted how many burns one target window could spend, and at its old default of 5 it was routinely the first gate to close: a weekly window with days left and headroom above the reserve would sit idle at "dispatch cap reached (5/5)" — the exact "allowance expires unused" outcome the feature exists to prevent. It read as a safety property, but the gates that actually bound spend all measure live numbers: the reset horizon (`resetWithinHours`), the reserve (`reservePercent`, checked against the *tightest* window on the card), and the provider's own refusal, which blocks the family outright when the short window empties underneath a weekly plan. A count stacked on top of those adds no protection they don't already give. A hard ceiling is still available — set 1–50 on the family card — and the window is charged either way, so the card still shows how many burns it has spent (with no denominator when uncapped). `0` is deliberately not accepted: "never burn" is what switching the family off means, and the client's number field collapses anything below 1 to the sentinel so stepping the spinner down can't 400. Migration 226 lifts an existing plan that still carries the old default of 5 — a changed default reaches nobody otherwise, since the normalizer has written that 5 into every install's `quota-burn.json` — while any other stored value is a number the user chose and is left alone.

- **Retargeting a scheduled task at a different model no longer costs a trip through the config drawer.** Each card on CoS → Schedule now carries the provider, model and effort pins inline, right above its Run button — so the common loop of "point this task at a stronger model and run it on one app" is three clicks on the card instead of opening the drawer, scrolling to the provider block, changing it, and closing again. The pins write immediately, exactly as they do in the drawer (picking a provider clears the model and effort with it, since a model from the previous provider wouldn't resolve), and a failed write rolls the select back to what is actually stored rather than leaving the card claiming a setting the server never took. Run stays disabled while a pin is still being saved: the run reads the server-side config, not the inputs on screen, so triggering mid-write would quietly run the *previous* model — the failure this repo's "in-flight saves must gate dependent actions" rule exists to prevent, and one a tooltip would not have stopped. Leaving the provider on Default no longer means the model and effort selects have nothing to offer: Default now names the provider it currently resolves to and lists that provider's catalog, so "same provider, higher effort" doesn't require pinning the provider first — the same fallback the pipeline's LLM pickers already use. Effort only appears for providers that actually have a ladder, and it is narrowed by the picked model, so an Antigravity model with no tiers doesn't offer one. A pipeline task, whose provider and model are resolved per stage, gets a link to the stage config instead of a card-level pin that its runs would ignore. The card's three selects are the shared `ProviderModelSelector` rather than a fourth hand-rolled copy, so they inherit what that component exists to guarantee: a disabled provider isn't offered (unless the task is already pinned to it), and a task pinned to a local model that can't call tools says so — a scheduled task IS an agent run, and a non-tool-calling model narrates instead of working. Card and drawer share one implementation of the select/write/rollback trio (`useTaskModelPins`), so the two surfaces can't drift; the drawer's own Run button picked up the same in-flight gate on the way past, which it had been missing. And the Run button's disable is now one `disabledReason` string instead of a boolean per reason — the shape that let the first gate reach only one of the two call sites.

- **The `cosAgents.js` barrel is gone, so an agent function no longer arrives from a specifier that says nothing about which layer it lives in.** The #2530 decomposition split a ~1090-line module into four focused siblings — `cosAgentIndex.js` (date-bucket index + on-disk archive layout), `cosAgentLifecycle.js` (register / update / complete / output / terminate), `cosAgentFeedback.js` (capture + classifier), `cosAgentArchive.js` (state-eviction sweeps) — then put an `export *` wall back in front of all four so no import path had to change. Three years of imports later, `updateAgent` and `getAgentsByDate` came from the same specifier despite sitting in different layers, and the wall is what made `cos.js` a *two*-hop forwarder of a lifecycle transition, which is the shape #3450's guard exists to delete. All ~20 production importers and ~14 `vi.mock` targets now name the module that declares what they asked for — several of which turn out to want only the index (`cosReports.js`, the peer cos-history merge) or only the lifecycle layer (the runner sync, the TUI output spooler, the completion cleanup), so the graph gets narrower as well as flatter. The four leaf modules are unchanged; the two test files that only ever exercised one of them are renamed to sit beside it (`cosAgentLifecycle.test.js`, `cosAgentIndex.merge.test.js`). The forwarder guard in `agentImportCycles.test.js` — which walks re-export edges rather than naming barrels, so a new one is covered the day it is written — now asserts `cos.js` is the *only* module forwarding a transition, and was bypass-probed both ways: planting a fresh `export *` barrel turns it red, and so does routing a production import of `completeAgent` back through `cos.js`. Its two module-loading assertions also take an explicit timeout: they transform `cos.js`'s whole service graph, which lands at 5–10s and straddles Vitest's 10s default, so the guard was one busy machine away from failing for a reason that had nothing to do with the invariant (#3450).

- **The agent lifecycle has a named entry point instead of seven mutually-recursive modules.** The `cos.js → cosAgents.js → cosAgentLifecycle.js → agentManagement.js → agents.js → subAgentSpawner.js → agentLifecycle.js` cluster has no owner, so reasoning about one transition — pause, kill, complete, spawn — means holding all seven files in mind, and several of the back-edges are `await import(...)` calls that exist only to dodge a load-time cycle. `server/services/agentOrchestrator.js` is the facade above that cluster: it imports the transition owners one-directionally, carries the transition-vs-leaf classification in its header so later passes start from it, and renames apart the two different functions both called `terminateAgent` — `requestAgentTermination` only emits the event and returns, while `terminateAgent` keeps the name for the real SIGTERM/SIGKILL sequence. The four agent routes (terminate, pause, kill, stats) now go through it, one hop instead of three. `agentImportCycles.test.js` gains a guard that fails if anything reachable from the facade imports it back, statically *or* via `import(...)` — the dynamic form matters because reaching across a blocked layer that way is exactly this cluster's habit, and the forbidden set is derived from the graph rather than listed so it can't fall behind. Widening that suite's graph builder to walk subdirectories closed a hole in the pre-existing cycle guard too: it read only top-level `server/services/*.js`, so a cycle routed through one subdirectory hop (`agentTuiSpawning/outputSpooler.js` already imports back up to `../cosAgents.js`) was invisible to it. The remaining call sites and the dynamic-import workarounds follow in later PRs (#3450).

- **The agent-lifecycle cluster lost the deferred imports it used to reach across its own layering.** `cosAgentLifecycle.js` carried three `await import('./agentManagement.js')` forwarders — `pauseAgent`, `killAgent`, `getAgentProcessStats` — that existed purely so a caller holding a `cos.js` handle could reach the process layer from the agent *state* layer, which cannot import it statically without inverting the layering. Their only consumer was `cos.js`'s own re-export block, so both are gone: those three transitions come from `agentOrchestrator.js` now. `agents.js` moved onto the facade too, which needed an actual structural fix rather than an import swap — it was stuck reaching `killAgent` through `await import('./subAgentSpawner.js')` because `agentManagement.js` imported `unregisterSpawnedAgent` back out of it, and that same back-edge put `agents.js` inside the facade's closure where importing the facade was forbidden. Pushing the pid map both sides wanted down into `agentState.js` — the import-free leaf they already shared other agent state through — deleted the edge; `agents.js` fell out of the closure and took a plain static import. `subAgentSpawner.js`'s event wiring (`task:ready` → spawn, `agent:terminate` → terminate, runner-error → complete) now asks the facade for those transitions instead of three separate leaves. `agentImportCycles.test.js` gains a guard for each half, each verified to fail on a planted violation: no new deferred import from the state layer into the process layer, no process-layer transition back in `cos.js`'s re-export block (derived from the facade's own export blocks rather than a hand-listed set, minus the one genuine name collision), `agentState.js` stays import-free, and `agents.js` reaches the facade statically. The facade header now describes that extract-a-leaf move as the shape every remaining migration takes, rather than carrying a call-site inventory that would go stale (#3450).

- **The agent cluster's back-compat re-export barrel is retired, so a lifecycle transition has one address instead of three.** `subAgentSpawner.js` re-exported ~40 symbols from nine sibling modules "for backward compatibility" — a second, partial view of the cluster layered over `cosAgents.js` and `cos.js`'s agent block, including the same three process-layer transitions (`pauseAgent` / `killAgent` / `getAgentProcessStats`) that `agentOrchestrator.js` owns. That overlap is why the previous PR's "no module may re-export a facade transition" guard had to be narrowed to `cos.js`: stating the rule generally would have failed on the barrel. The barrel had almost no consumers left — `telegram.js` reaching `getActiveAgents`, two `await import('./subAgentSpawner.js')` calls in `cos.js` for `cleanupOrphanedAgents` / `handleOrphanedTask`, and three test files — and all of them now name the module that actually defines what they want, which also deletes the last two `cos.js → subAgentSpawner.js` edges from the seven-module chain. `agentLifecycle.js`'s pass-through re-exports of the leaves extracted out of it (`finalizeAgent`, `extractFinalSummary`, `syncRunnerAgents`, the worktree-cleanup cluster) went with it: the barrel was their last consumer, and an orchestrator re-exporting the leaves beneath it is what made "where does `finalizeAgent` live" a three-answer question. What remains in `subAgentSpawner.js` is what it actually does — `initSpawner()`'s runner connection and event wiring. Two guards in `agentImportCycles.test.js` hold the line, both bypass-probed: the transition re-export rule now runs over `cos.js` *and* `subAgentSpawner.js`, and a new one asserts each cluster orchestrator declares everything it exports, comparing the module's live key list against its own declarations so `export *`, `export { x } from …`, and `import` + a bare `export { x }` all fail identically rather than each needing its own regex (#3450).

- **Every view that used to show a bare "Loading…" text node now uses the shared loading affordances.** ~35 views across Music, MeatSpace, Media, Pipeline, Sprites, Writers Room, Sync, Catalog and a dozen pages rendered unstyled text while fetching, which read as broken content rather than a deliberate loading state. Small inline loads (buttons, side lists, drawer subtitles, popover menus) now render `BrailleSpinner`; full-page and card-grid loads render `PageSkeleton`, which reserves the eventual content's dimensions so the first paint doesn't reflow and announces itself via `role="status"`/`aria-busy`. Several hand-rolled `Loader2 + animate-spin` one-offs collapsed onto the same two components, and the pipeline audio music-library panel lost its duplicate second spinner.

- **Three structural cleanups that each removed a way to get something silently wrong.** `buildReviewWithArgs` took seven positionals, with two same-shaped reviewer-name arrays adjacent to each other and two same-shaped per-reviewer lookup maps adjacent to each other — transposing either pair produced a plausible-looking flag string and no error; everything past the reviewer list is now a named options object. The ecosystem-config branch of `streamDetection` nested eight levels deep to probe each PM2 process's vite config, duplicating that loop byte-for-byte in `parseEcosystemFromPath`; both now call the exported `resolveViteConfigPortForProcess`, which owns the gate and the candidate order and has its own tests (the "stray closing brace" flagged in that block turned out to be mis-indentation, not a structural bug). And `client/src/utils/fileUpload.js` no longer re-exports the four network-calling upload helpers it handed off to `services/apiMedia.js` — the real call sites import them from the services module directly, so the pure-helpers module has no reach into the network layer again (#3452).

- **The root `pm2` dependency moved out of the dev-only bucket, because `npm start` launches the production process with it.** The root `start`, `pm2:*` and `dev:stop` scripts all invoke `./node_modules/pm2/bin/pm2`, so an install run with `--omit=dev` (or `NODE_ENV=production`) would have left every one of them with no binary to run. Nothing in the repo installs that way today and `server/package.json` already declares `pm2` as a normal dependency, so this was a latent footgun rather than a live break — but it would have cost someone an afternoon the first time a slimmed Docker or CI install path appeared. The lockfile change is limited to the bucket rename and dropping `"dev": true` from pm2 and its transitives; no versions moved. `scripts/root-runtime-deps.test.js` now derives the rule from the manifest instead of hardcoding pm2 — every package a root script reaches into via `./node_modules/<pkg>/…` has to be a real dependency — so the next root script wired to a dev-only binary fails the suite rather than waiting for a production install path to expose it.

- **Replaced ESLint with Biome in the client, dropping 110 net packages including the `keyv` chain named in the August 2026 npm compromise.** `keyv`, `flat-cache`, and `file-entry-cache` were hit by the Shai-Hulud supply-chain attack. PortOS was never exposed — it held `keyv@4.5.4` / `flat-cache@4.0.1` / `file-entry-cache@8.0.0` while the malicious releases were the *next major* in each line, unreachable from the caret ranges in the lockfile, with no install hook anywhere in the tree (npm has since unpublished all three). They were not direct dependencies either: they arrived as a single chain under one root, `eslint → file-entry-cache → flat-cache → keyv`, dev-only and client-only. Since `eslint@10.8.0` hard-requires `file-entry-cache` and no release drops it, the only way to shed the chain was to stop using ESLint — so this is a maintenance win, not a security fix. An `overrides` pin would have been a no-op, because every range was already at the top of its published major.

  `@biomejs/biome@2.5.7` replaces the stack: a native binary with no regular dependencies and 8 platform optionals, of which one installs. The client lockfile goes 447 → 337 packages. That count includes `typescript`, which the migration orphaned — it was a client devDependency purely to satisfy `@eslint-react/eslint-plugin`'s peer dep, and with the client holding no `tsconfig`, no `.ts`/`.tsx` sources, no `tsc` script, and nothing peer-depending on it, it came out too (retiring a Dependabot ignore rule and issue #3351 with it). Parity was proven with fixtures rather than inferred from a clean run — a linter with no rules also reports zero problems — and `npm run lint` still covers the same 1859 files with 0 problems. The swap was cheap largely because `exhaustive-deps` was already deliberately disabled, which is the rule that usually makes linter migrations painful.

  The `crypto.randomUUID` ban is preserved as a GritQL plugin, and it matters: that call is undefined on insecure origins, and PortOS is routinely reached over plain HTTP via Tailscale. It matches on the syntax-tree node kind rather than code snippets, so it still catches `crypto.`, `globalThis.crypto.`, `window.`, `self.`, optional chaining, bare `typeof` references, and assignment targets — while continuing to ignore `crypto['randomUUID']` exactly as the old rule did. Its exemptions for `src/lib/uuid.js` and test files are written as negated globs because a Biome override's `plugins` list is additive, so an empty list does not disable an inherited plugin.

  Deliberately kept narrow: Biome's formatter and assist actions are off (turning them on would rewrite all 1859 files in one unreviewable diff), and the rule set is an explicit list rather than Biome's broader `recommended` preset, so this is a tooling swap and not a silent change to lint policy. Adopting more of Biome's rules is a separate decision.

- **A scheduled Chief of Staff task can now say what happens after it opens its PR, the same way a manually-entered task already could.** The task-entry form has carried an "After opening PR" choice — review then merge, merge on green CI, or leave the PR open for you — but the Schedule tab's per-task config only had the Open PR toggle, so every scheduled task was stuck on whatever its target app defaulted to. Not every recurring task wants a reviewer chain (a dependency refresh or a catalog sync is fine merging on green CI), and some you'd rather look at yourself before they land. The same three choices now sit under Agent Options on each scheduled task, alongside a fourth "App default" that leaves the decision to the target app exactly as it works today — so nothing changes for a task you don't touch, and PortOS's own self-improvement runs, which have no app, keep falling back to merging on green CI. Each app's row in the same drawer gets the same choice as an "Inherit (…)" override, next to the ones it already has for issue-author filter and swarm mode — so one app that wants review doesn't force review on every app the task runs against. The reviewer picker follows the choice rather than the Open PR toggle: it stays visible for review-then-merge and for the inherited default (an app may well default to review), and disappears for the two policies that never run a reviewer, where it was previously offering a reviewer list nothing would read. A task carrying the legacy `reviewLoop` bit — the pre-`prCompletion` spelling of the same decision — now shows "Review then merge" rather than claiming to be unpinned, and picking any policy retires the old bit so it can't outvote what you just chose.

## Fixed

- **Quota-burn tasks were queued and then never picked up, so the window they were meant to spend expired unspent anyway.** Three separate faults, each of which alone was enough to strand a burn. First, a queued burn inherited the per-app *review cooldown* — a 30-minute throttle re-stamped by every task that completes on that app. On an app that carries any other recurring CoS work (a perpetual claim-issue drain, which is itself exempt from the cooldown and therefore keeps completing) the cooldown never lapses, so the burn task sat in Pending indefinitely while agents ran past it. The cooldown was never this task's throttle: the burn plan's own gate ladder — the reset horizon, the family's reserve, and `maxDispatchesPerWindow` — is checked before the task is queued at all, so burns now bypass it, as pipeline continuations and perpetual drains already did. Tasks already queued carry no marker, so migration 225 back-fills it onto them rather than leaving them stranded — and a stranded burn is worse than late, because `addTask` dedupes on description + app, so a pending twin makes the runner report "an identical burn task is already pending" and that job in the plan is permanently unreachable. Second, the runner always walked the family's job plan from the top, and an `agent-prompt` job always probes as "work pending" (its probe only checks that an app and a provider resolve) — so job #1 won every dispatch forever and the other seven audits in an eight-job plan never ran once. The walk now resumes after the family's last dispatch, read from the run log rather than a second cursor file, and still runs the first job with pending work from there, so a probing job like `universe-bible-images` keeps its ordering. Third, the plan only advanced once per `checkIntervalMinutes` — at the 12-hour default, two dispatches a day against an allowance of five on a five-hour window. Each finished burn agent now re-evaluates its own family, so the plan is walked one agent at a time until a gate actually closes; the chain is bounded by the same ledger every other cycle charges, and switching the feature off ends it immediately. That re-evaluation reads only the burning family's quota card rather than respawning every enabled provider's TUI for numbers it then discards — a per-family scrape the usage page already asked for this way.
- **Quota Burn was watching the 5-hour window and calling it the weekly one, so its one real gate never gated anything — and it kept dispatching after the provider started refusing.** Every subscription family publishes two windows on the same card: a short rolling one (claude/codex `session` ≈ 5h, antigravity `5-hour`) and a long one (`week`, `month`). Selection picked "the soonest-resetting window", and the short one is nearly always the soonest — so a plan written against a weekly allowance showed "62% left · resets in 3h" on its card, `resetWithinHours: 24` was satisfied by a horizon that re-opened every five hours (making "only spend as the window is about to expire" bound nothing at all), and `maxDispatchesPerWindow: 5` silently meant *five burns every five hours* rather than five per week, because the dispatch ledger keyed on the short window's reset. A family now burns against its **target** window — the broadest one in scope, classified by period in the new `server/lib/quotaWindows.js` — and the card names which window its percentage and countdown describe, so the two can never be confused again. The **limiting** window (the narrowest) and the **tightest** window (least headroom, what `reservePercent` already guarded) stay separate concepts, because they answer different questions; the per-family Window scope field still pins the target explicitly for anyone who wants the old behavior. A provider whose window vocabulary this can't classify falls back to soonest-reset ordering rather than parking.

  Which exposed the second half: what actually *stops* a burn is the short window emptying underneath it. Spending a weekly allowance runs task after task until the 5-hour window is gone, at which point every further dispatch fails instantly, wastes an agent spawn and leaves a red card in the CoS queue — while the weekly card the runner gates on still reads "60% left, resets in 2 days", so nothing in the reported numbers ever says stop. That got sharper, not milder, once each finished burn agent started dispatching the next one immediately: the chain now walks straight into the wall at agent speed instead of interval speed. A refusal is therefore recorded as a fact rather than inferred from a meter — and recorded *inside* the completion continuation, awaited before it re-evaluates the family, because a block written after that dispatch (or from a second `agent:completed` subscriber, whose ordering against the continuation is not guaranteed) arrives one wasted agent too late every single time. The family is blocked until the reset the provider stated in its own refusal, else the reset of its limiting window, else a bounded 5-hour TTL so a reset-less block can't hold forever; a burn that *succeeds* clears it immediately, the provider serving being more current evidence than any stated reset. Four deliberate narrowings: only agents the burn plan itself dispatched count (the limiting window's reset rides on the task beside the `quotaBurnFamily` the cooldown exemption and the continuation already read, rather than inventing a second provenance shape); a transient `429` is a retry and not a spent window, so it does not block; an analyzer "usage-limit" verdict is trusted only when it came from a structured provider marker, not a loose keyword sweep over an agent narrating a prompt that happens to be *about* quota handling; and the block is bypassable by the ▶ forced run, which is how a user retries one they believe is stale. A ledger that can't be read is never overwritten and never silently reads as "nothing blocked", and the reset-out-of-refusal-text parsing is now one shared `parseObservedReset` rather than a second copy of what the image-gen quota ledger already did.

- **Two agents working a swarm run could overwrite each other's pull-request descriptions.** Every agent in a swarm shares one scratch directory and — by design — runs byte-identical instructions, so when two of them reached the "write the PR description to a file" step they independently picked the same obvious filename and the second quietly overwrote the first. The failure was invisible: nothing errored, the text was well-formed, and it only surfaced minutes later when the first agent re-published its now-replaced description onto its own PR. Swarm runs now hand each agent its own scratch subdirectory named for the issue it's working, so no two agents can collide on a filename, and each agent re-reads its published description after creating or editing it to confirm the right one landed. Single-issue runs are unchanged.

- **Quota burn stopped after the first family it dispatched, so a longer-windowed provider never burned at all.** A cycle selected every family whose window was inside its reset horizon, sorted them soonest-reset-first — and then returned after the first successful dispatch. Families do not share a budget: each draws down its own subscription window, against its own reserve and its own `maxDispatchesPerWindow`, so stopping early protected nothing. It just meant the soonest-resetting family took every cycle. A `claude` window resetting in 2h beat an `agy` window resetting in 21h on every tick, and the Antigravity plan sat at "93% left · 0/5 used" indefinitely while its eight configured audits never ran. A cycle now dispatches one job per *family*, records a run-log row per dispatch (so no family is hidden from the audit list), charges each window against its own key, and continues past a family whose job declines. When several plans are walked, every skip reason is prefixed with the family it came from.

- **The burn-job preset picker snapped back to "Choose a preset…" the moment you picked one.** Applying a preset copies its text into the step's work prompt 60 lines further down the row, so with the control blank the click read as a no-op and people picked again. It now shows the preset whose prompt the step still matches verbatim — derived from the text rather than stored, since nothing on disk records a preset id, so it reverts to the placeholder as soon as the prompt is edited into something else and never claims a step is an audit it no longer is. Re-picking the preset a row already matches no longer raises the "replace your text?" confirm; the text *is* that preset's.

- **Content cards were nearly invisible against the page in every theme, and dissolved completely at reduced opacity.** Card and page colors were separated by as little as 1.04:1 (Classic Noon, Black ICE Terminal) — and the common `bg-port-card/40` spelling then faded even that toward the page, leaving a themed border floating around nothing. Cards now render against a per-theme fill floor (`--port-card-min-alpha`), every theme's card/page pair clears a 1.12:1 separation, and the card elevation rule covers all fill opacities instead of only `bg-port-card/50`, so two cards on one page can't sit at different elevations for no visible reason. Hover and active variants are deliberately left unfloored — a hover landing on the resting fill is not feedback — and translucent themes set their own lower floor so glass stays glass. `portosThemes.test.js` asserts the separation, the floor ordering, and that body and muted text still clear WCAG AA on the resulting fill, for every theme; `docs/themes/README.md` documents the three-level page/card/well scale.

- **The `ignore-scripts` supply-chain guard was silently inactive for every workspace install, including CI.** The repo-root `.npmrc` has pinned `ignore-scripts=true` for a while, but npm resolves the project `.npmrc` from the *local prefix* and never walks up the directory tree — so it never applied to `cd client && npm install`, `cd server && npm install`, or `npm ci --prefix server` / `--prefix client`, which is exactly what CI runs and what the documented per-workspace test workflow uses. In those paths every dependency kept an install-time code-execution slot: the same slot the August 2026 keyv/cacheable (Shai-Hulud) worm used, via a `preinstall` hook, to harvest credentials before any application code ran. `client/`, `server/`, `autofixer/`, and `browser/` now each carry their own `.npmrc`, so the guard holds in every workspace install path — whether entered by `cd`ing in or via `--prefix`.

  Closing the hole made the trusted-rebuild allowlist load-bearing for the first time, and it had drifted across its five copies (the root `setup` script, `scripts/ensure-deps.js`, `update.sh`, `update.ps1`, `setup.ps1`): the `esbuild` entries were dead — vite 8 dropped that dependency — while `onnxruntime-node` and `protobufjs` were missing entirely, so CI ran install hooks that the local setup skipped. All five now read one allowlist from `scripts/trusted-rebuilds.js`, and CI rebuilds it explicitly after installing server dependencies so `node-pty`'s native binding is still present for the smoke-boot. `scripts/trusted-rebuilds.test.js` fails if any workspace `.npmrc` loses the setting, or if a dependency shows up with an install hook nobody has decided about — the second case being how a missing native build otherwise surfaces much later as a confusing runtime crash.

- **Release notes told fresh-clone users to run `npm install`, which cannot produce a working install.** The fallback release-notes template in `.github/workflows/release.yml` printed a `git clone` + `npm install` + `pm2 start` sequence, but a bare root `npm install` skips the client, server, and Autofixer workspaces, never initializes the bundled submodules, and does no data/database provisioning. It now points at `npm run install:all`, matching the README.

- **Replaced a real Tailscale identity with placeholders across tracked files, and added a guard so it can't come back.** A real MagicDNS tailnet suffix, real device names, and a real CGNAT peer IP had been committed across server routes/lib, client lib, several test fixtures, two design-plan docs, and two released changelog entries — ~14 tracked files in a public repo. This violates the repo's own `CLAUDE.md` "Sensitive Data & Privacy" rule, which lists Tailscale node/MagicDNS names and Tailscale/LAN IPs as never-commit categories. Every occurrence is now an obviously-fake placeholder (`example-tailnet.ts.net`, `host-alpha`/`beta`/`gamma`/`delta`, a documented CGNAT test IP), preserving the two-host distinctness some tests relied on. A new `scripts/tailnet-identity-leak.test.js` enumerates *tracked* files via `git grep` and fails the moment a real-looking tailnet host or CGNAT address lands again — whether via a pasted log line, a doc example lifted from a live install, or a copy-pasted test fixture.

  These are identifiers, not credentials — Tailscale ACLs still gate all actual network access, and no auth key, token, or secret was ever committed. The historical occurrences remain in git history by deliberate decision (see #3455): a `git filter-repo` rewrite would break every fork and clone of this fork-aware project to remove values that grant no access on their own.

Clearing the busy flag also moved into a `finally`, so a call that throws before returning a promise can no longer latch the button on "Checking in..." until a page reload.

## Three.js Models

- **[issue-3481] A generated model now tells you which of its own promises it did not actually build.** The spec check only ever proved that every feature the model listed pointed at a real part — so a spec could name eight defining features, aim all eight at the same box, and still validate clean: one fused mesh wearing a photograph. Each finished generation is now measured against its own inventory and the result is shown on the model's page: features collapsed onto a single shared part, geometry no feature claims, and features nothing was built for at all. Severity follows how much of the subject rides on the miss — a missing defining feature is an error, fine relief folded into the piece it sits on is called out as the correct modeling choice rather than a defect. When you hit Refine without typing your own notes, the refinement pass is now aimed at exactly those errors instead of a generic "improve it." The page states the check's honest limit alongside the findings: it proves the model built what its spec promised, never that the spec promised enough.

- **[issue-3483] Take a generated model apart and click any piece to find out what it is.** The preview used to render a finished model as one inert lump — the only way to check it was actually built from parts, rather than fused into a single shape, was to export the source and read it. An Explode slider now separates the assembly, and clicking any surface names the part it belongs to and lights up that whole component. Separation scales the layout outward from the model's centre instead of shoving every piece the same distance, so parts that were touching genuinely come apart, pieces sitting at the centre still clear their neighbours, and the camera re-frames to whatever the disassembly actually grew to. Surface detail — serrations, stria, trim, port floors — rides the part it belongs to instead of shattering into loose slivers, and clicking it selects that part; models are now generated with that distinction marked, and exported models carry it too.

- **[issue-3482] A model that looks perfect head-on and like cardboard the moment you orbit it now says so before you find out yourself.** Since the spec gained extruded outlines, a generation can score a near-perfect match against its reference — right silhouette, right colour zones, right part count — while every load-bearing piece is a flat slab standing on its own depth plane, because a head-on comparison actively rewards that flatness. A new cross-section check reads the finished geometry instead of the picture: it counts how many distinct planes each mesh actually occupies on its thinnest axis (a fan of four hundred triangles sharing one Z value has no profile at all) and treats an unbevelled extrusion as the two-plane slab it is by construction. It reports at the level of the whole model rather than per part, because a flat extrusion is the *right* answer for a badge, a sign, or a panel — the finding fires only when the majority of the subject's identity-defining features have nothing but flat parts behind them, and it names the parts responsible. The result sits beside the assembly-coverage findings on the model's page, and a Refine you didn't steer now asks for real depth as well as for the promises the last pass didn't build. The generation prompt was closing the loop from the other end too: it sold extrude for silhouettes without ever saying when extrude is the wrong answer, so it now states that a body with a real cross-section — a torso, a housing, a grip, a shell that varies in thickness — must not be an unbevelled extrusion, and gates on a subject that isn't genuinely plate-like not having every identity part flat along one axis.

- **[issue-3503] A fused model could hide from the assembly check by wearing a second part id.** The fusion finding only looked at features that named exactly *one* part, so a spec that aimed eight defining features at the same *two* parts — every one of them "hull and base" — reported completely clean, even though nothing in it distinguishes one feature from another. Features are now grouped by the whole set of parts they name, so any group of two or more defining features sharing an identical set is reported the same way a shared single part already was, with the finding naming the parts and how many features are riding them. Sets that merely overlap ("hull and base" beside "base and mast") are left alone — sharing a part is ordinary attribution, not fusion. And the existing rule that a set nothing was built on went *unbuilt* rather than fused still holds, so a refinement pass is never handed both "split this mesh" and "this mesh does not exist" about the same features.

## Internal

- **[issue-3497] The Chief of Staff no longer re-reads and re-parses its task lists on every scheduler tick** — an unchanged list is served from memory instead, which matters most on installs whose task history has grown large. Edits made outside PortOS (a text editor, a restore, a sync peer) are still picked up immediately.

- **[issue-3506] Typing in the ⌘K search bar no longer re-reads every Brain record off disk.** Brain keeps one file per record — people, projects, ideas, admin items, memory entries, links and inbox captures each live in their own directory — and unified search was opening and parsing all of them, across all seven stores, for every single character typed. On a Brain that has been in use for a while that is thousands of file reads per keystroke, which is exactly why the palette got slower the more you put into it. Search now reads a small in-memory projection of just the fields it matches on, refreshed as records change rather than rebuilt per query, so the disk is touched once per store instead of once per character. A store that is legitimately empty counts as read — otherwise the one case with nothing to cache would have kept re-scanning forever. Records arriving from a sync peer, which deliberately land without firing the usual change events so they cannot echo back around the network, now raise a local-only signal so the projection refreshes for them too; without it an inbound sync would have left search answering from a stale snapshot indefinitely. The old cap that only ever searched your 200 most recent inbox captures is gone with it — it existed solely to bound the disk cost that no longer exists.
- **[issue-3498] Opening a long-running agent's transcript no longer loads the entire log into memory.** A completed agent's `output.txt` has no size ceiling — a multi-hour TUI run writes tens of megabytes — and every request for that agent's details read the whole file and turned each of its 50,000+ lines into its own object, spiking memory and churning the garbage collector for a view that only ever shows the end of the log. The agent detail now hydrates the tail: at most the last 1,000 lines, and never more than 512KB read off disk. Both caps are needed, not just the line one — a repaint-heavy TUI transcript spools as effectively a single enormous line with no newlines in it, so a line count alone bounds nothing. When the log is longer than that, the view says so and reports the full size on disk rather than presenting a clipped transcript as the whole thing. The bounded tail read is now one shared helper instead of the two near-identical private copies that had grown up in the TUI failure analyzer and the Codex usage scan.

- **[issue-3499] Background scheduler ticks no longer fire a network `git fetch` and a `gh` process at GitHub every time they check whether a plan item is claimable.** Deciding whether a PLAN.md item is already in flight means reading the repo's claim branches and open PRs, which costs a `git fetch --prune`, a `git branch -a`, and a spawned `gh pr list` — and the evaluation loop runs far more often than claim branches actually appear, so the same three processes were being spawned over and over for an answer that had not changed. The scan result is now reused for a minute per repository, which is short enough that a newly pushed claim branch is still seen within a tick or two and long enough that a burst of checks costs one scan instead of one each. What gets cached is every claimed slug in the repo rather than one caller's filtered answer, so a second caller asking about a different set of items still gets a correct result off the same scan, and callers that overlap in time share a single in-flight scan instead of racing three more processes into the same repo.

- **[issue-3500] The Chief of Staff's cooldown sweep no longer re-scans its whole blocked backlog once per blocked task.** Tasks that get parked with an orphan-retry cooldown are revived by a pass that walks both task queues — the user queue and the internal one — and each revived task has to be written back to the queue it came from. That queue was being re-derived per task by searching the user queue for the task itself, a linear scan inside a linear loop, so the work grew with the square of the backlog on every scheduler tick. The two queues are now walked separately, which hands each task its origin for free and makes the sweep linear. Behavior is unchanged, including that a task carrying an explicit type still wins over the queue it was found in.

- **[issue-3508] The "N missing · Embed" badge on the Brain graph no longer reads your entire Brain off disk to compute a number.** Checking embedding coverage means counting live records and asking which of them have a vector yet — but it was answering that by loading and parsing every person, project, idea, admin item, memory entry and daily log entry in full, across every store, then throwing all of it away except each record's id. On a Brain with a few thousand records that is a few thousand file reads and JSON parses to render two integers. The tally now works from an id index instead: which record ids exist is re-read from the directory listing every time (cheap, and it is the honest source of truth for records added or hard-pruned), while whether a given record is archived or tombstoned — the part that requires opening the file — is resolved once per record and then remembered. Changes that keep a record's id, an archive flip or a delete writing a tombstone over it, drop just that one id from the index so the next count re-reads exactly one file; records arriving from a sync peer, which land deliberately silent so they cannot echo back around the network, ride the same local-only signal the search projection already uses, so an archive performed on another machine is not invisible here. The daily-log walk also loses a cap nobody meant as a policy: it used to ask for the first 10,000 days and would simply have stopped counting after that.

- **[issue-3501] Daily agent reports for past dates read as all-zero, and the dashboard's activity card re-scanned every agent you have ever run.** Both the daily report and the "today" activity card worked out which agents finished on a given date by walking the entire in-memory agent dictionary and string-matching each record's completion timestamp — so the cost grew with your whole agent history rather than with the day being asked about, and once the housekeeping sweep had evicted a day's finished agents out of live state (it keeps roughly a day), asking for that date's report returned zeros even though every one of those runs was still sitting on disk. Both now consult the date-bucket index that already maps each archived agent to its day: the index is a small in-memory id-to-date map, so a date whose agents are all still live costs no disk reads at all, and a date that has been swept out resolves from the archive instead of reporting nothing. Live records still win over their archived copies, since the archive is written at completion time and the live one carries anything recorded since. The "while you were away" card is built on the same lookup now, which also stops it re-reading up to thirty days of archives on every poll for agents it already had in hand. Asking for a report by anything other than a plain calendar day is now rejected outright rather than quietly writing an empty report under a filename nothing can read back, and a report row's duration is derived the same way every other view derives it, so a clock-skewed run can no longer show negative time.

- **[issue-3509] Opening your Bookmarks no longer reads and re-sorts every link you have ever saved.** Answering a single page of `/brain/links` meant loading and JSON-parsing every link record on disk, filtering the whole array in memory, sorting all of it by date, and then throwing away everything outside the fifty rows actually asked for — so the cost of showing page one grew with the size of the entire collection rather than with the size of the page. The links list now rides a small in-memory index of just the four fields the endpoint orders, filters, and counts on, refreshed per record as links change rather than rebuilt per request, so only the requested page's records are opened. The filters keep their exact previous meaning, including that a link saved before the GitHub flag existed still does not match "not a GitHub repo" — absent is not the same as false. Links sharing a timestamp, which is every link from one bulk import, are now ordered by id underneath the date so paging through them cannot skip or repeat a row at a page boundary, and a link with a missing or unreadable date sorts last instead of scrambling the order around it. Two neighbouring paths lost the same whole-collection read: checking that a drag-reorder batch refers to links that still exist, and checking whether a URL you are about to save is already bookmarked.

- **[issue-3510] Typing in your Daily Log no longer re-reads every day you have ever written.** Each daily-log entry is its own file on disk, and every save, autosave, and dictated segment against today was rebuilding a full date-to-entry map of your entire journal history — opening and parsing every past day, merging each one's local Obsidian mirror location back onto it — purely to fill in the payload of a store-wide "the journal changed" event. Nothing consumed that map: the write paths already announce the single affected day, and that is what the memory vectorizer listens on. The event now carries just the day that moved, so an append costs the one entry it touched instead of the whole archive, and a long dictation session no longer re-reads years of entries once per sentence. A delete reports the day with an explicitly empty entry, which is distinct from a day that simply was not part of the change.
- **[issue-3516] Applying an AI-suggested goal hierarchy no longer reports success when it failed.** The routine that writes the suggestion back — creating the new north-star goal, creating the sub-goals under it, then re-parenting everything else — already gave up and reported failure the moment any of those steps was rejected by the server, but both views that call it threw that answer away and showed "Goal hierarchy applied" regardless. So a run that created nothing at all still looked like it had worked, and the list you were staring at kept showing the old arrangement. Both the list and the tree view now say so when the apply fails, and both refresh the goals afterwards either way, because a failure can still have created part of the hierarchy before aborting and leaving that half-written state off screen was the actual complaint. The apply routine swallows each server error on purpose so it can report one clean yes-or-no, so it now also asks those calls to stay quiet — otherwise the failure would have surfaced as two error toasts stacked on top of each other.

- **[issue-3530] Deleting a Digital Twin document no longer leaves it to be resurrected by your other machines.** Peer sync merged the identity documents add-only: whichever machine still had the file put its metadata entry back into `meta.json` and re-wrote the `.md` on disk, so a document you deleted came back on the next sync cycle, every cycle, forever. A delete now records a tombstone on the document's filename, and those tombstones union in both directions — so the machine that still holds the document drops its entry and removes the file, instead of the deleting machine merely defending itself while the peer keeps re-sending. Filename is the key rather than the document id because ids are minted per install and the same document can carry a different one on each machine. Deleting is not permanent in the way a naive tombstone would make it: a document created — or edited — after the delete records a stamp that supersedes the tombstone, which is then dropped, so re-creating a document you removed (by hand, or by an enrichment session regenerating its target) works and survives a peer that has not seen the re-create yet, and an edit you made on one machine is not silently destroyed by a delete another machine performed before that edit. Those two stamps are the one part of a document's entry that is not add-only — each machine takes the newer of its own and its peer's — so a machine holding a stale copy cannot keep a third machine's older delete alive against a document that has since come back. A peer running an older build simply ignores the new field and keeps offering its copy; the upgraded machine still refuses it, so nothing is corrupted while the two versions differ.

- **[issue-3527] The Brain Trust Panel no longer scrolls sideways on a phone.** Its header put the title block and the five audit counters — Total, Filed, Review, Corrected, Errors — on one row that was not allowed to wrap, so on a 375px screen the counters ran off the right edge and dragged the whole page's horizontal scrollbar with them. The title and the counters now stack under `sm` and re-join from `sm` up, the counters wrap among themselves, and the status-filter row wraps too so its Refresh button cannot spill off screen either. Every counter stays visible without scrolling; the desktop layout is unchanged.

- **[issue-3528] The Notes header controls in Brain are now big enough to hit on a phone.** The "Manage vaults" and "New note" buttons wrapped 14px icons in nothing but `p-1.5`, giving them roughly 26x26px of tappable area right next to the vault dropdown — close enough that a thumb aiming for "New note" would land on the dropdown instead. Those two buttons, plus the vault selector, the search box, and the create-note row beside them, now all clear the 44px touch-target floor the rest of the app uses. The search box also gained enough right padding to clear its own clear-search button, which was already 44px wide and had been sitting on top of whatever you typed.

- **[issue-3520] The goal progress slider no longer sits on a percentage the server never stored.** Releasing the slider fired the update and left the dragged number on screen, and the only thing that ever corrected it was an effect that re-synced the slider the instant the drag ended — so on a normal save the percentage visibly snapped back to the old value while the request was still in flight and then jumped forward again when the refresh landed, and on a rejected save it was only that same flap that happened to leave the right number showing. Moving the slider with the keyboard never committed at all: arrow keys never produce a mouse release, so the value the user set stayed on screen, unsaved, until the panel was closed and re-opened — the reported symptom, reached by a different route than the drag. The slider now keeps the value it committed until the stored percentage actually changes underneath it, and resets to what is stored the moment the update reports it failed; the update handler reports that outcome rather than throwing it away. Arrow, Home/End and moving focus off the track all commit like a mouse release does. Releasing again on a percentage that is already saved or already on its way — a touch release fires both a touch end and a synthesized mouse release, and a blur can follow either — no longer sends it a second time, while a percentage the user sets *while* a save is still in flight is held and sent as soon as that save answers, so the value on screen is always one that was actually sent. The "Progress" label is now paired to the slider, so screen readers and click-to-focus find it.

- **[issue-3533] Deleting a Twin persona no longer leaves it to be resurrected by your other machines.** Peer sync merged the personas add-only, so whichever machine still had a persona you deleted put it straight back into `meta.json` on the next cycle — and every cycle after that. A delete now records a tombstone on the persona id, and those tombstones union in both directions, so the machine that still holds the persona drops it too instead of the deleting machine merely defending itself against a peer that keeps re-sending. The id is the right key here (unlike identity documents, which tombstone on filename) because a persona id is minted once by the machine that created it and then travels with the record. Personas also now take the more recently edited copy on a collision rather than always keeping the local one: that is what lets a persona you edited after another machine deleted it survive — the newer stamp supersedes the tombstone, the stale tombstone is dropped, and a third machine holding an old copy can no longer reap the persona against a delete that has since been overruled. If the persona a peer's delete removes was the active one, the active-persona pointer is cleared rather than left dangling. A peer running an older build ignores the new field and keeps offering its copy; the upgraded machine still refuses it, so nothing is corrupted while the two versions differ.

- **[issue-3532] Deleting a social account from your Digital Twin no longer leaves your other machines to put it back.** Peer sync merged the account list add-only: whichever machine still had the account re-inserted it, so an account you removed on one machine reappeared on the next sync cycle, every cycle. A delete now records a tombstone on the account's id, and those tombstones union in both directions — so the machine that still holds the account drops it, instead of the deleting machine merely defending itself while the peer keeps re-sending. The id is the right key here, unlike the identity documents that tombstone on filename: an account id is minted once by the machine that created the account and then travels verbatim between peers, and re-adding the same handle after a delete mints a fresh id, which a platform-and-handle key would have wrongly kept suppressed. An account edited after another machine deleted it also survives — the edit is the user's later word, and the now-obsolete tombstone is dropped so it cannot bounce back from a peer that has not caught up. A peer running an older build simply ignores the new field and keeps offering its copy; the upgraded machine still refuses it, so nothing is corrupted while the two versions differ, and no migration is needed because a file without the field reads as an empty list.

- **[issue-3531] Deleting an autobiography life story no longer leaves it to be resurrected by your other machines.** Peer sync merged the stories add-only, so a story you deleted on one machine was put straight back by any machine that still had it, on the next sync cycle and every cycle after that — there was no way to permanently remove a story you had written. A delete now records a tombstone against the story, and those tombstones union in both directions, so the machine that still holds the story drops it too rather than the deleting machine merely defending itself while the peer keeps re-sending. The tombstone keys on the story's own id, which is safe here in a way it was not for identity documents: a story id is minted once when the story is written and travels with the record, so every machine knows the same story under the same id. A story that was edited after another machine deleted it is kept rather than reaped — that edit is the user's later word on it — and the now-obsolete tombstone is dropped so it cannot bounce back from a peer that has not seen the edit. A peer running an older build simply ignores the new field and keeps offering its copy; the upgraded machine still refuses it, so nothing is corrupted while the two versions differ. Two neighbouring bugs in the same merge went with it: the list of prompts you have already answered was only checked for having changed *length*, so a list that was merely in a different order than a peer's was never written back in the shared order — leaving two machines with the same prompts computing different checksums and re-syncing that file forever — and a story arriving from a peer without a usable id was filed under a blank key, where a second such story would overwrite it and neither could ever be deleted. Separately, a fresh install's first story read handed back the shared default record by reference, so anything written into it lingered in memory for the next reader; that record is now copied per read.
