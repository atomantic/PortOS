# Release v2.37.0

Released: 2026-08-03

## Highlights

**POST (brain training).** A new Practice Plan page decides what you are actually studying: every topic and drill gets a switch, with a live preview of what tomorrow's session becomes. Wordplay, Verbal Agility, Imagination, Morse and each memorized text are now independent topics you can drop from the rotation without deleting their history. The launcher leads with the actions instead of the dashboard, "Up next" starts the drill in one click rather than dropping you on a page, and every memory practice mode has its own shareable link. Mastery can now become permanent instead of decaying forever, and accuracy is no longer mistaken for it.

**Stacker News stewardship.** A complete, safety-first community stewardship surface: independent per-account rules and schedules, encrypted removable credentials, reviewed publishing, conservative local text and vision analysis, identity-verified browser handoffs, and an auditable action ledger. Reads now go through the signed-in pinned browser, so Sync works with no API key at all — Stacker News does not hand those out from a settings page. The vision-model picker only offers models that can actually see an image, and two long-standing identity-check failures (single-page-app navigations, service-worker-served pages) are fixed.

**Agents and Chief of Staff reliability.** A failed run's committed work is now picked up by its retry no matter how the agent was launched, and a task can no longer be handed back to the scheduler before the pointer telling its retry where to resume exists — including across federated peers, where a stale snapshot used to undo the requeue. An agent that commits and pushes but fails to open its pull request is recorded as needing attention rather than "Completed successfully". A blocked or unauthenticated GitHub CLI is now reported as exactly that, everywhere it used to look like a quiet repo, and System Health gained a `forge` check for it.

**Data Manager safety.** Every one of the ~65 directories PortOS creates is now classified with a real description and honest archive/purge flags, so the cleanup page stops refusing to act on the things filling your disk. Images, videos and LoRAs can no longer be wiped in one click — those bytes are the only copy — and purging scratch now refuses while a render, a training run or an update is still using it.

**3D and media generation.** Scene specs gained `extrude` and `tube` geometry plus physical material properties, so cutouts, bent details, glass and cloth are choices rather than approximations. Video render submission moved out of a 717-line route handler, closing a leak that orphaned up to 100MB per failed request. Agy and Grok can no longer hand back a picture they drew with a plotting library when the image backend hits its quota, and the usage page gained an Image Gen card that reports what PortOS actually observed instead of a reassuring guess.

**Media Collections and Prompt Manager.** Collections can be searched, sorted and stripped of the empty auto-created buckets that were burying the ones you made, and a collection now records who created it instead of the grid guessing from its name. The 127-stage prompt list is searchable, grouped and safe to scroll past, its SYSTEM badge comes from the server instead of a client copy that had drifted, and deleting a stage now checks a generated manifest of every stage the code names rather than a hand-written list of ten.

**Usability and accessibility.** Buttons nested inside other buttons — which left favourite stars, phase actions and tag filters unreachable by keyboard — are fixed across four surfaces. Delete is no longer the loudest control on an app row, the Creative Director's developer smoke test moved out of the action bar and now names its cost, Video Gen's Generate button is back above the fold, Review Hub queue cards preview three lines instead of printing whole bodies, and the goal tree labels its nodes instead of showing bare dots.

**Messages and Music.** Gmail can be fully connected from Messages Config, an empty inbox names the step that would actually fill it, and a thread can no longer render under the wrong message. The track generator picker is visible before you save a new track, and synced Music Video projects now use each machine's own render backends.

**Dependencies and infrastructure.** Routing moved to React Router v8, clearing the last outstanding security advisory; `npm audit` is now clean across all four manifests. The pinned `overrides` blocks were audited by resolving each tree twice and diffing — two entries were forcing majors onto consumers written for the previous one, and ten more named packages that were not in that tree at all. `@eslint/js` caught up to the ESLint 10 it configures, which turned on `no-useless-assignment` and surfaced eight real dead stores.

**Development-mode and test fixes.** A StrictMode mount-guard bug that left panels loading forever and buttons stuck after one click is fixed in all twenty-seven places it had been copied to, and a test now fails if the shape returns. Client tests that type into a field and then submit no longer race the keystrokes, and the prompt-integrity snapshot pins prompt bytes rather than the machine that generated it — it used to report drift that had not happened on any install with a custom origin.

## Creative Director

- **A project whose stored record lost its id no longer shows up as an unusable card.** Each project is one database row: the id is a column, and the whole record is duplicated into a JSON blob beside it. Reads handed back the blob untouched, so a row whose blob was written without an id — the column still had one — reached the page as a project with no identity. Its card opened `/creative-director/undefined/overview`, and Start, Pause and Delete all acted on `undefined`. Reads now fill the id in from the column, which is the value every lookup already matches on, and the record repairs itself on its next save.


- **[issue-3287] The developer smoke test no longer leads the Creative Director action bar.** `Run smoke test` sat in the leading position of a four-button header where the eye lands first, named a mechanism rather than an outcome, and consumed one of the seven interactive elements that fit above the fold on a phone — despite spending real render time on every click. It now lives behind a "…" menu beside `Model defaults`, reads `Render a 6s test clip` so the cost is legible before you commit, and asks for an inline confirmation naming what it will spend. The header bar reads `New directive` · `Model defaults` · `New project`.

## Media Gen

- **The favourite star on an image or video card is now reachable by keyboard.** The star sat inside the card's own click-to-preview button. A button nested in another button is invalid HTML with no defined behaviour, and here it left the star unreachable by keyboard and out of the tab order. The star and the badges are now siblings of the preview target rather than children of it, so the star is focusable and clicking it still favourites without also opening the preview. Three more controls with the same defect were fixed alongside it: the Plan/Execute/Verify button on a GSD phase row, the Dashboard link on a Chief-of-Staff GSD project card, and the tag filters on a SongBook entry — each was mouse-only, and each needed a click-suppressing workaround that is no longer necessary.
- **[issue-3283] Media Collections can now be searched, sorted, and stripped of empty auto-created buckets.** Every Creative Director project and render bucket files itself away as a collection the moment it is created, so the grid filled with empty cards that all read as the same clipped `Creative Director: …` text — the trailing project name and date that told them apart were exactly what got cut off. The page now has a search box, a Recently updated / Name / Item count sort, and a "Hide empty" toggle that is on by default (with a "N empty hidden — Show" link when you want them back); collections that actually hold something, plus any you named yourself, sort ahead of the auto-generated empties; and the shared `Creative Director` prefix moved into a small badge above each title so the distinguishing tail stays readable. Your filters live in the URL, so a filtered view is shareable and survives going back from a collection, and creating a collection now opens it — a brand-new bucket is empty by definition, so the filter row would otherwise swallow the thing you just made.
- **A collection whose cover image is missing now shows the syncing placeholder instead of a broken image.** Collection covers were plain `<img>` tags, so a cover pointing at a pruned video thumbnail — or at a federated collection whose files haven't been pulled yet — left the browser's broken-image icon on the card. Covers now use the same component as the rest of the media UI: they fall back to a "Syncing" tile and swap in the real image the moment the file arrives from a peer.

## Prompt Manager

- **[issue-3284] The prompt stage list is now searchable, grouped, and safe to scroll past.** Settings → Prompts listed all 127 stages as one flat column with no search box, so finding "Creative Director — Treatment" meant scrolling a page seven screens tall and reading two-line descriptions to tell near-identical names apart — and every row carried a bare trash icon right beside its own click target, so a mis-tap while hunting offered to delete a stage instead of opening it. There is now a search box pinned above the list that filters on title, description, and stage id as you type, a SYSTEM-only toggle, and collapsible groups (Pipeline, Writers Room, Creative Director, Brain, CoS, …) built from the naming convention the stages already followed. Delete has moved off the row and into the selected stage's editor pane.
- **[issue-3314] The SYSTEM badge and "System only" filter now come from the server instead of a client-side copy that had already drifted.** The list of stages PortOS features call by name was written out three separate times — twice in the prompts API and once in the client — and the client copy was purely advisory, so a key missing from it made that stage unreachable through the new "System only" filter even though the server would still refuse to delete it. `GET /api/prompts` now ships the list alongside the stages and the client renders exactly what it is told. The drift this uncovered is fixed too: `cos-task-enhance` was badged as a system stage but had no prompt entry at all, so CoS task enhancement quietly ignored the Prompt Manager and used a hardcoded prompt with the active provider's default model — it now ships a real, editable stage (seeded into existing installs) whose model tier is honoured.

## Documentation

- **Getting started now uses the standard install and production-start commands, with PostgreSQL called out as required.** The documentation catalog also has a product-surface map, making every major area of PortOS easier to find before you need its focused guide.

## Image Gen

- **Agy and Grok can no longer hand back a picture they drew themselves.** When Antigravity's `generate_image` backend hit its quota (HTTP 429 "you have exhausted your capacity on this model"), agy did not fail the render — it took the instruction "save a PNG at this path" literally and wrote a script that drew a stand-in with a plotting library instead. The result was a real PNG, so it passed the signature check and landed in the gallery looking like a generated image: flat vector shapes, placeholder circles, overlapping labels, and the prompt's own pixel dimensions captioned into the artwork. Both cloud CLIs are now told that only the image tool may produce the image and that reporting a failure is the correct outcome when it can't; a scratch-directory check discards any render whose agent left a drawing script behind. The agy prompt also stopped naming exact pixel dimensions — `generate_image` only exposes an aspect ratio, so that was an instruction it could never satisfy, which is precisely what made reaching for code look reasonable.
- **The usage page now has an Image Gen card, observed rather than guessed.** The provider cards only ever showed the *agent* model's quota, which is a different bucket from the image backend — when the imagen backend returned 429, the Antigravity card was still reporting the Gemini 5-hour group at 78% left, so nothing on the page explained why renders were failing. These CLIs expose no image-quota API at all (Antigravity's `/usage` panel has rows for `GEMINI MODELS` and `CLAUDE AND GPT MODELS` and nothing for images), so the new card reports what PortOS actually watched happen: a real 0%-left meter with the provider's own stated reset time once a render is refused, and a plain 24h render count otherwise — never a reassuring "100% left" bar for a number nobody can measure. A block clears as soon as a render succeeds again, not merely when the stated reset passes. The card appears only when a cloud image backend is enabled; local renders use your own GPU and have no quota.

## Usage

- **The Top Providers and Top Models cards now say how much of your usage each one actually accounts for.** Both cards listed a name, a session count and a token count and stopped there — no cost, no sense of proportion, and no relationship to the detailed cost table sitting further down the same page. On a phone that was the whole story, because the cost table below them is a seven-column layout that only scrolls sideways. Each row now carries a share-of-total bar and percentage, its estimated cost, and its in/out token split, so the ranking is readable at a glance instead of requiring you to compare raw numbers by eye. The two cards also now follow the period you have selected: they were computed from an all-time summary while the table beneath them respected the date filter, so switching to "last 7 days" changed one half of the page and not the other. Models are attributed to the provider that ran them. Underneath, the per-provider cost table gained a card layout on narrow screens — same numbers, including the cache-read and cache-write columns that were hidden entirely below tablet width, without the horizontal scroll.

## Universe Builder

- **A failed settings load no longer resets your image-gen mode.** Opening Universe Builder fetched providers, image models, LoRAs and settings together, and treated any request that failed exactly like one that came back empty. A brief network blip therefore rendered the page as if nothing were configured — and worse, the settings read was used to recompute the render backend, so a failed fetch silently reset your saved image-gen mode to Local and the pipeline image config to defaults. Each request now keeps its last known-good value when it fails, while a genuinely empty response still applies.
- **[issue-3290] Locking a bible field now writes once instead of twice.** Clicking the padlock on the logline, premise, style notes or either influence list sent its save request from inside a React state update, which React is free to run more than once per click — so a single lock toggle fired two identical writes at the server's queue. The save now happens alongside the state change rather than inside it, and eleven previously untested Universe Builder actions — delete, lock, render pin, bucket moves, category add/remove, and the save preflight — are covered by tests that pin the exact request each one sends.

## Calendar

- **The account expand toggle now announces itself to screen readers.** The chevron that opens an account's calendar list rendered as an unlabelled icon button, so a screen reader read only "button" with no indication of what it did or whether the section was already open.

## Sprites

- **The panel close buttons and the Lock/Approve controls are now big enough to tap.** The close buttons on the import and new-sprite panels were a bare 16px icon with no padding, and the reference/walk workflow's Lock, Unlock and Approve confirmations were roughly 18-26px tall — well under the 44px target the rest of the interface uses. On a phone these are the controls that dismiss a blocking panel and commit a candidate, so a mis-tap mattered.
- **[issue-3331] Forking a sprite no longer offers a backend that cannot redraw an image.** A fork is always image+text→image — it seeds the new character from the source's locked reference — but the Backend picker listed every configured image backend, including Agy, which renders text-to-image only. Picking it was accepted, saved as the new character's render pin, and then quietly rendered somewhere else. The fork picker now lists only backends that can take an input image, and the server refuses an explicitly chosen text-to-image-only backend on any seeded sprite render up front, before a record is created, instead of diverging silently. A backend inherited from a saved pin still degrades gracefully to a capable one, the way a pin whose backend was switched off already does.

## Internal

- **System Health now reports whether the GitHub CLI can actually reach GitHub, instead of leaving a blocked `gh` invisible.** Around thirty places in PortOS shell out to `gh` and turn any failure into an empty result, so a CLI that cannot open a connection is indistinguishable from a repo with nothing open: the PR watcher sees no pull requests, branch and issue reconciliation see nothing to reconcile, and an agent told to open a PR finishes reporting success having opened none. That is exactly how a recent agent run ended — it committed and pushed its branch over SSH, which was unaffected, and then silently could not create the pull request. `/system-health` now carries a `forge` block that distinguishes the four states that were previously one: working, not installed, installed but not logged in, and installed and authenticated but unable to connect. Only the last two raise a warning — an install that never had `gh` has opted out of those features rather than broken them. The unreachable case names the cause that is easiest to misread as a local bug: an outbound firewall such as Little Snitch denies the connection rather than refusing it, which surfaces as "bad file descriptor" and looks nothing like a network problem. The probe uses the one GitHub endpoint that does not consume API quota, and its result is cached for a minute so a polled health page does not spawn a process per request.
- **Route handlers now share one pagination parser.** Twenty-two places across fifteen route files hand-rolled `parseInt(req.query.limit, 10) || N` instead of calling the pagination helper that already existed. That spelling has two real consequences: `?limit=0` and negative values are falsy, so they silently fell back to the default rather than being clamped, and several endpoints had no upper bound at all — `?limit=999999` was passed straight through to the datastore. Every migrated endpoint keeps its previous default, and the ones that were unbounded gained a generous ceiling. Three sites were deliberately left alone because their behaviour genuinely differs: two treat a missing or zero limit as meaningful, and one uses an absent limit to mean "no limit". The helper's boundary behaviour now has direct test coverage.
- **Slashdo command loading moved out of the general file utilities.** Two hundred lines of slashdo-specific command loading and template rendering lived in `fileUtils.js` alongside generic JSON, path and upload helpers, while a separate module already owned other slashdo concerns — so working on one feature meant reaching into two unrelated modules. The loading code now has its own module, registered in the library barrel and catalog. Behaviour is unchanged: the moved code is byte-identical to what was removed.
- **[issue-3264] Fixed a development-mode freeze that left panels loading and buttons stuck after one click.** Under `npm run dev`, a mount guard used across fourteen components and hooks was never re-armed after React StrictMode double-mounts a component, so anything gated on it silently stopped updating — the music generator panel sat on "Loading generators…" forever, and every button backed by the shared async-action hook stayed disabled after its first click. All fourteen now use the shared hook that re-arms correctly, and a test fails if the broken shape is reintroduced anywhere in the client.
- **[issue-3266] The mount guard behind issue 3264 now has exactly one implementation.** Thirteen more components and hooks still spelled that guard out by hand — correctly, so the new test passed them, but they were the copy source: reproducing issue 3264 took nothing more than copying one of them and dropping a line. Several also carried their own multi-line essay re-deriving the StrictMode hazard, which is the hazard being rediscovered per file instead of read off a hook name. All thirteen now call the shared hook, and the test fails on the hand-written form whether or not it happens to be correct.
- **[issue-3265] Fixed a test that broke on its own once the calendar passed 2026-07-31.** An image-quota test compared against a reset timestamp baked into its fixture; once that instant passed, the code correctly ignored the stale time and the test started comparing against the wall clock, failing every run. The test now pins its own clock, and the ignore-a-past-reset path it accidentally exercised has coverage of its own.
- **[issue-3267] Removed the unmount guard from the shared async-action hook, along with the test that could never fail.** The guard existed to avoid a "state update on an unmounted component" warning React stopped emitting in version 18, so its only remaining effect was to skip a no-op — while being the exact shape that froze every button backed by the hook under StrictMode. Its regression test asserted that the vanished warning never appeared, which stayed green even with the guard deleted; it now unmounts mid-request and asserts the action still resolves with its value.
- **[issue-3291] The Video Gen form moved out of the page and into a hook of its own.** The page carried 56 pieces of form state and every URL-prefill, mode-transition and payload-shaping rule in one 2,100-line component, so the request the client sends had no single place to read — and no second surface could ever generate video without copying it. Form state, the ImageGen/Continue/Remix/`?lora=` prefill paths, the mode and backend switches that clear stale conditioning inputs, the keyframe/extend/audio/IC submit gates, and `buildGeneratePayload()` now live in `useVideoGenForm`, leaving the page to fetch, run, and render. Behaviour is unchanged, and the payload contract — grok versus local shapes, the empty-string sentinels, keyframe JSON, LoRA parallel arrays, and the mutually-exclusive IC reference channels — now has direct test coverage it never had before.
- **[issue-3294] Track and collection lists can now be paged, and three small duplications were folded back into the helpers that already existed.** `GET /api/tracks` and `GET /api/media/collections` returned every record with no ceiling while the structurally identical albums, artists and LoRA lists already accepted `?limit`/`?offset` — and tracks grow with every upload and generation. Both now take the same opt-in pagination as their siblings, still returning the plain array when no pagination is asked for, so existing callers are untouched. Alongside that: the Writers Room analysis banner stopped re-deriving the shared duration formatter, the Chief of Staff's on-demand spawner reads the app registry once per cycle instead of once per queued request, and the Feature Agents output and runs tabs now clear the previous agent's content when you switch agents — including a refresh whose response arrives after the switch, which could still paint the wrong agent's output.
- **[issue-3250] Stabilize Music Video project-selection tests under CI load.** Project-selection coverage now waits for the requested project to be available before opening its board, preventing intermittent false failures.
- **[issue-3351] The weekly dependency check no longer proposes a TypeScript upgrade that breaks linting.** The client is plain JavaScript and carries TypeScript only to satisfy a linting plugin's requirements, so the offered jump to version 7 brought nothing but a crash — none of the lint tooling supports it yet. That one upgrade is held back until the tooling catches up; every other dependency update flows as before.
- **[issue-3292] Three sprite dialogs that every suite mocked away now have tests of their own.** The fork-a-character dialog, the reference-sprite picker, and the click-to-enlarge preview each carry real logic — the submit gate, the exact payload sent when forking, search filtering by name and id, and which asset the enlarged view opens — but no test file, and every suite that rendered them swapped in a stub. The fork payload was the sharpest edge: the server only ever checked a hand-written example of it, so a mismatch between what the dialog sends and what the server accepts could have sat behind two passing suites. Both of the payloads the dialog actually builds are now asserted on the client and replayed through the real server schema. No behaviour changed.


- **Routing moved to React Router v8, clearing the last outstanding advisory in the dependency audit.** `npm audit` reported one HIGH finding across all four manifests: GHSA-qwww-vcr4-c8h2, a CSRF bypass in React Router's unstable RSC code paths, affecting every release from 7.12.0 up to 8.3.0. PortOS is a Vite SPA that never touches an RSC API, so the exploitable path does not exist here — but the fix landed only in 8.3.0, which means the 7.x line PortOS was pinned to receives no patch and the finding would have recurred on every audit. v8 removes the `react-router-dom` compatibility package that v7 kept around for v6 apps, so all 345 import sites now read from `react-router` directly, with `RouterProvider` from `react-router/dom` as the upgrade notes require; the Vite vendor-chunk rule and the dependency catalog dropped the retired package name alongside them. Nothing else in the v8 changelog applies — the removed flags and the always-on middleware are Framework/Data-mode server concerns, and the raised React (19.2.7) and Node (22.22.0) floors sit below what PortOS already requires. The scaffolded-app template in `scaffoldPortOS.js` is deliberately untouched: it generates a React 18 project, which v8's React floor rules out, and a scaffolded SPA has the same non-existent exposure.
- **Dependency refresh: `google-auth-library` 10 → 11, `@react-three/fiber` 9.7.0, and eleven security overrides moved to their current patches.** The `google-auth-library` major turned out to be a Node baseline bump and nothing else — its dependency set is byte-identical to 10.9.1 and only `engines.node` moved from `>=18` to `>=22`, well under the Node 24 that CI and every install already run — so the OAuth2 client that backs Calendar and Gmail is unchanged. R3F 9.7.0 is a reconciler hardening pass: child reordering no longer drifts out of sync when React reorders, and an unset pierced prop (`position-x` removed on a re-render) now resets the pierced value rather than the base object. The pinned `overrides` blocks in all three manifests — the ones that force transitive dependencies off known-bad versions — had drifted behind their upstreams, and eleven of them (`ws`, `postcss`, `tar`, `qs`, `picomatch`, `systeminformation`, `ip-address`, `basic-ftp`, `brace-expansion`, `socket.io-parser`, `@protobufjs/utf8`) moved to their current patch or minor. Two were left alone on purpose: `js-yaml` and `protobufjs` have new majors, and an override that forces a major onto a transitive consumer which declared compatibility with the previous one breaks it silently rather than at install time.
- **A CoS agent whose worktree was removed cleanly no longer reports "Worktree preserved — uncommitted changes detected".** A completing agent reaches worktree cleanup twice by design: once through the runner path (`handleAgentCompletion` → `runAgentCompletionCleanup`) and once through the spawner's unconditional `finally` safety net, which exists so a throw from `finalizeAgent` can never strand a tree. Neither knows about the other and both are driven by independent events, so they overlapped — and the loser ran `git status --porcelain` while the winner was mid-`git worktree remove --force`, read the in-progress deletions as uncommitted work, and raised a warning plus a user notification for a worktree that removed cleanly ~200ms later. Observed on an agent whose PR had already merged, whose card then claimed its work was preserved. Cleanup is now re-entrant per agent id: a duplicate call joins the pass already running and returns its verdict instead of racing it, so the push, the PR, and the removal each happen once. The preserved-worktree warning also names the dirty paths now (capped at five) — the bare message gave no way to tell real abandoned work from a transient read, and the worktree is usually gone by the time anyone looks.
- **[issue-3313] The URL search-param patch helper is now one hook instead of three copies.** `updateParams(patch, { replace })` — merge a patch into the query string, dropping keys set to empty so a cleared filter leaves the URL clean — had been re-typed into Catalog, Media Collections, and (in a narrower single-key form) the 3D page. It now lives in `useUrlParams`, which reads the live params off a ref because react-router's functional updater hands the callback the params captured at the render that memoized it — a debounced `?q=` write armed before a sort change would otherwise navigate with the pre-change snapshot and silently drop the sort the user just picked. The hook is also referentially stable, so the debounce effects on those pages stop re-arming every time an unrelated param changes.
- **[issue-3335] Deleting a prompt stage now checks the source, not a hand-written list of ten.** `DELETE /api/prompts/:stage` force-guarded exactly the ten curated CoS/Brain/Memory stages, so removing `pipeline-series-concept-judge` (or roughly a hundred others PortOS resolves by literal key) succeeded with no warning and left the feature naming it throwing `Stage <key> not found` on its next run. Adding them all to the curated table was the wrong fix — the same table drives the Prompt Manager's `SYSTEM` badge and its "System only" filter, and badging ~100 of 127 rows makes both meaningless. Deletion protection is now a second, generated set: a checked-in manifest indexes every stage key a `server/` source names, including the ones reached only through an interpolated prefix like `pipeline-panel-${personaId}`, and a drift test fails until a new call site is regenerated into it. The badge and the filter still show the same ten stages; the delete dialog now names the files that reference the one you're about to remove.
- **[issue-3288] Video render submission is no longer a 717-line route handler — and a failed lookup mid-request stops orphaning your upload.** `POST /api/video-gen` did request validation, backend-pin resolution, model checks, durable staging for four upload kinds with rollback bookkeeping, IC-LoRA/keyframe/a2v validation, render-history lookups, LoRA normalization and chunk resolution inline, with twenty-plus throw sites sharing mutable cleanup state — so every new video-gen parameter meant editing the monolith and risking an unrelated validation branch. That whole region now lives in `services/videoGen/prepareParams.js`, mirroring what `imageGen` already did, and the route is a thin parse → prepare → enqueue → respond shell. Validation order and the exact cleanup-on-throw unwind are preserved verbatim, pinned by the existing route suite plus a new service suite. The extraction also closed a real leak (#3326): every *explicit* throw released the staged uploads, but a plain rejected `await` — a music-video project or track lookup, a render-history read, or the enqueue itself — bubbled straight past them, orphaning up to 100MB per request under `data/uploads` with no job to ever clean it up. One rollback guard now covers every rejection point at once and stays correct as new awaits are added, rethrowing the original error untouched.
- **[issue-3353] Client tests that type into a field and then submit no longer race the keystrokes.** A Stacker News save test failed on CI for a pull request whose entire diff was a dependency config file, and passed on the rerun. The cause is a shape that suite had in six places: `user.type` enters `20` as two separate events, and nothing between the last keystroke and the Save click asserted that the controlled input had actually reached `20` — so under load the click could send a payload built from the intermediate `2`, or from the post-clear empty string that `Number('')` turns into `0`. Waiting on the assertion cannot recover from that, because the call has already happened with the wrong argument and re-waiting never produces a second one. A shared `src/test/settledInput.js` helper now pins the settled input value between the keystrokes and whatever depends on them, and every instance of the shape now uses it — all six in the Stacker News suite plus ten more found by auditing the rest of the client tests, across the CoS agent card and reviewer picker, the sprite reference workflow, the media jobs queue, the duplicate-universe merge tab, and Media Collections. Two of those submitted with Enter typed as part of the same keystroke run, where a partially-typed `bad token!` would have been a *valid* username and quietly emitted; the Enter is now a separate press after the draft is pinned. One more asserted only the navigation that followed its submit, so a half-typed collection name could not have failed it — it now asserts the request it sent. The failure mode it replaces is an honest one — an input that never settles now fails saying so, rather than silently asserting against a half-typed value.
- **[issue-3368] A failed agent's committed work is now picked up by its retry no matter which way the agent was launched.** When a run fails with commits on its branch, cleanup deliberately preserves that branch so the retry can continue from it — but turning a preserved branch into an actual resume takes a pointer written onto the task, and only one of the three ways PortOS launches an agent was writing it. A failed direct-CLI or TUI run therefore left a branch full of finished work that nothing would ever point at: the retry started from an empty tree and redid all of it, while the previous attempt's branch sat there untouched. The PR verification added in #3358 made this easy to hit — a run that committed, pushed, and only failed to open its pull request is now retried, and under those two launch modes the retry redid the whole task instead of just opening the PR — but any failed run with commits had the same gap. All three launch paths now share one gate, which still declines to stamp a pointer on a task that has exhausted its retry budget and is waiting on a human.
- **[issue-3373] A failed task is no longer offered back to the scheduler before the pointer telling its retry where to resume exists.** The retry pointer from #3368 can only be worked out *after* worktree cleanup decides what survived — whether the branch is still there and still holds commits — but the failure verdict flipped the task straight back to `pending` before cleanup even started. The dequeue that fires the moment an agent completes could therefore claim the retry during that window and start it on an empty tree, and because the retry then held the task `in_progress`, the pointer write that arrived seconds later correctly declined to stamp a running task — so the preserved branch was orphaned for good. A retryable failure now leaves the task deliberately non-spawnable while cleanup runs, and one write both makes it spawnable again and records where to resume, so it is never one without the other. The hold names the run that armed it, so a slow cleanup from an earlier attempt can't release a later attempt's hold or reopen a task that has since been blocked, and the spawn path refuses a held task outright — a dispatch queued before the failure can no longer slip past on the lease this instance still holds. If PortOS dies mid-transition the held state is on disk, and the startup sweep finishes it — immediately at boot, where nothing can be mid-cleanup, and after a liveness grace on the periodic pass, so a slow merge is never mistaken for a dead process. A task that exhausted its retry budget is blocked and waiting on a human, so it is never held and never pointed, exactly as before.
- **[issue-3358] An unreachable `gh` no longer looks like a quiet repo — and an agent can no longer report success having filed no PR.** Around thirty call sites ran `gh` and turned *any* failure into an empty result, so a firewalled or unauthenticated CLI was indistinguishable from a repo with nothing going on: the PR watcher saw no PRs, the branch reconciler classified every pushed branch as "needs a PR" (and would have had an agent open duplicates on top of the ones already open), the issue reconciler saw nothing to reconcile, and none of it logged a distinguishable error. Those reads now answer with three states instead of two — the forge said nothing, the forge said nothing *exists*, or we could not ask — and every forge-dependent scheduled job (`pr-watcher`, `branch-reconcile`, `issue-reconcile`, layered intelligence, self-diagnostics) probes `gh` first and skips the cycle with one clear line rather than executing against a forge it cannot read. Separately, a run whose task shape promised a pull request is now verified against the forge before it is recorded complete: an agent that commits, pushes over SSH (unaffected by an outbound block) and then fails to create the PR is recorded as needing attention with the branch named, not as "Completed successfully" — and "we could not confirm the PR" is kept distinct from "there is no PR", so a network outage is treated as environmental instead of denting the task type's measured success rate.
- **[issue-3359] The prompt-integrity snapshot now pins prompt bytes instead of the machine that generated it.** `taskPromptDefaults.test.js` hashes every current and preserved-historical prompt body against a checked-in snapshot, because editing a preserved body silently strands every other install on a prompt it can no longer recognize as an upgradable default. Prompt bodies embed this install's API origin, so hashing normalized it away first — but only the *runtime* origin, while the historical bodies written before that interpolation existed hardcode `http://localhost:5555`. The snapshot therefore only reproduced on a machine whose own origin happened to equal that literal: set a custom host, or merely run the suite in a shell with `PORT` set (as every CoS agent does), and five untouched bodies hashed differently and the suite failed reporting drift that had not happened. Regenerating the snapshot there would have been the damaging fix — it blesses whatever edited a preserved body, which is the one thing this test exists to catch. Hashing now collapses the frozen legacy origin too, which reproduces the committed snapshot byte for byte on every install, and the shared hasher is what both the test and a new `scripts/regen-prompt-integrity-snapshot.js` use, so the regeneration path can no longer normalize differently from the assertion. The guard is also in the CI planner's always-run list now: it covers a cross-install contract nothing else covers, so no impact scope may scope it out.
- **[issue-3365] A pinned browser read now closes its own scratch tab, instead of every call site being expected to remember.** `navigateToUrlPinned` opens a fresh Chrome tab per call and tore it down itself on a refusal, but on success handed the caller a tab the caller was supposed to close — a convention that had already been broken twice, once leaving a tab behind for every catalog URL ingested and once for every Stacker News identity check, each fixed by hand-writing another close at the call site. The function already knows which case it is in: a caller that passes `evaluateExpression` did its DOM read on that same session and wants nothing back, while a caller that omits one wants the tab *as* the deliverable. So teardown now defaults to on exactly when an expression was supplied, the three read call sites no longer close anything, and the browser handoff and `POST /api/browser/navigate` still get their tab. `closeAfterRead: false` remains for a future caller that wants to read and keep the tab.
- **[issue-3372] The server suite no longer fails two tests just because it was run from a CoS agent's worktree.** `resolveInstallRoot()` refuses a pinned data root that resolves into `data/cos/worktrees/…`, so worktree-version code can never be talked into reading or writing the live install's data (#1947) — and two tests were quietly leaning on the ambient working directory in a way that tripped exactly that guard. The relative-pin test expected `join(process.cwd(), 'some/rel')`, which inside a claim worktree resolves to a worktree path the resolver correctly refuses; the install-state test asserted that the migration ledger is read from `PATHS.installRoot`, which inside a worktree is itself a worktree path the reader deliberately short-circuits, so the call it asserted never happened. Both now pin the value they depend on — a stubbed cwd and a fixed non-worktree install root — instead of inheriting it from wherever the suite happens to be checked out. The refusal behavior is unchanged and now has a test for the relative-pin case too, and the install-state test asserts its pinned root differs from the code checkout, so it is a real check rather than a tautology on a normal install.
- **[issue-3376] A second machine's stale snapshot can no longer undo a requeue and throw away where the retry was supposed to resume.** Federated peers reconcile a task they both hold by lifecycle rank, on the reasoning that a task only ever moves forward — so the higher status is the newer truth. Two paths break that assumption by design: the orphan sweep and the retry-hold release from #3373 both move a task from `in_progress` back to `pending`, and that write is precisely the one that records the branch and worktree a retry should resume from. A peer still holding its pre-requeue view therefore won the merge on rank alone, restoring `in_progress` and discarding the resume pointer with it, so the retry that eventually ran started from an empty tree and redid work that was already committed. The `challenged` status already had an exemption for this shape; `in_progress` versus `pending` now has one too — but a stricter one, because 'whichever side was edited most recently' turned out to be the wrong test. An ordinary edit landing on a peer's stale `pending` copy also carries a newer timestamp, and letting that win would revert a task an agent is actively running and invite a second agent onto it, which is worse than the delayed retry being fixed. So the requeue now stamps itself, and the merge asks whether that requeue happened after the spawn the other side is reporting; every other pairing falls through to the old behavior, including for a peer running a version too old to stamp. Two things the requeue depends on came along with it: the lease that the requeue deliberately releases is no longer re-attached by the separate claim merge — which had been quietly re-imposing it and blocking the retry for a full lease window — while a lease held by the requeued record itself is still honored, since a dispatch takes its lease a moment before it flips the task to running. And two peers looking at the same claim with the same owner and expiry but a different claim time now settle on one of them instead of each keeping its own forever. The wire format is unchanged, so an older peer converges on the next sweep exactly as it does today.
- **`@eslint/js` was a full major behind the ESLint it configures, and catching up surfaced eight dead stores.** The client runs `eslint` 10.8.0 but pinned `@eslint/js` — the package that supplies `js.configs.recommended` — at 9.39.4, whose peer range is `eslint@^9`. The lint run worked, so nothing complained, but the config presets being applied were the v9 set: ESLint 10 promoted `no-useless-assignment` into `recommended`, and PortOS had been running without it. Bumping to 10.0.1 turned on that rule and it found eight real dead stores, each a value written and then overwritten on every path that reaches a read: five `let x = <default>` initializers where both branches assign (a timezone validity flag, a keyboard-scrub target, a parsed session snapshot, a drag span's end, two fetch-result flags), one overflow cluster that is only ever read inside the branch that builds it, and one in the MIDI parser that advances `pos` immediately before `break`ing out of a loop after which `pos` is never read. None changed behavior; all eight are now gone rather than silenced. `@vitejs/plugin-react` (6.0.5) and `@eslint-react/eslint-plugin` (5.18.1) took their patches in the same pass.
- **Dependency audit: clean, and the two deferred override majors were re-checked rather than re-deferred.** `npm audit` reports zero vulnerabilities across all four manifests (root, `server`, `client`, `autofixer`) — the React Router advisory that drove the v8 migration was the last one outstanding. Every other direct dependency is already at its latest published version. The two overrides held back last pass stay held back for a reason that is now recorded instead of re-derived: pm2 declares `js-yaml` at the *exact* version `4.3.0`, so forcing the 5.x major overrides an exact pin rather than a range, and `onnxruntime-web` (via `kokoro-js`) declares `protobufjs@^7.2.4`, which 8.x is outside of by definition. `typescript` 7.0.2 is likewise blocked upstream, not by choice: it exists in this repo only as a peer for `@typescript-eslint`, whose current 8.65.0 declares `typescript >=4.8.4 <6.1.0` — the 6.0.3 pin is already at that ceiling, and 7 becomes available when typescript-eslint ships support for it. `node-pty` stays on `1.2.0-beta.14`, which is ahead of the 1.1.0 stable, not behind it.
- **Two `overrides` were forcing majors onto transitive consumers for no security benefit — the exact thing the previous pass refused to do to `js-yaml` and `protobufjs`.** Every direct dependency is already current and `npm audit` is still clean across all four manifests, so this pass audited the pinned `overrides` blocks themselves rather than the versions above them. Resolving each manifest twice — once as written, once with `overrides` deleted — and diffing the trees sorts all 39 entries into three groups. Two were actively harmful. `picomatch` was pinned to 4.0.5 against consumers that declared `^2.0.4` and `^2.2.1` — `anymatch` and `readdirp`, reached through pm2's `chokidar@3` file watcher — so pm2's watch globbing was running against a picomatch two majors past the one those packages were written for. `basic-ftp` was pinned to 6.2.0 against `get-uri@6`'s declared `^5.0.2`, in the FTP branch of pm2's PAC proxy agent. Neither pin is load-bearing: deleting each one individually and re-resolving leaves `npm audit` at zero, so no advisory required them and the only thing they bought was silent-breakage risk of the kind that surfaces at runtime instead of at install time. Both are gone, and the lockfile diff is exactly the correction — `basic-ftp` back to 5.3.1 under `get-uri`, `picomatch` 2.3.2 nested under `anymatch` and `readdirp` while vite and vitest keep the 4.0.5 they actually ask for. Ten more entries named packages that were not in the tree they were declared in at all — seven of the root manifest's fourteen, which had been copy-pasted from `server` even though root's only dependency is pm2, plus `brace-expansion`/`systeminformation` in `server` and `js-yaml` in `client`. Removing those produced zero lockfile churn, which is the proof they were inert; the root block now describes pm2's actual tree. The remaining pins all have real consumers and all sit inside the ranges those consumers declared, with two deliberate exceptions kept as-is: `sharp` and `three` are force-deduped across the whole tree because a second copy of a native binary or of three.js is itself the bug.
- **A Wordplay test suite could spend its whole budget waiting and then blame the wrong line.** Its drill-generation waits were bounded at five seconds — exactly the per-test timeout — so an inner wait was allowed to consume the entire test, and the checks that came after it had nothing left to run in. The premature-submit test has eight awaited transitions after that wait and duly failed on CI at 5,011ms, reporting only "Test timed out" against the test's opening line rather than the step that actually stalled. The per-test budget is now derived from the inner bound instead of coinciding with it, so a wait that overruns fails as itself and the assertions after it still get to run.

## Chief of Staff

- **"Try again shortly" no longer hides a forge CLI that will never work again on its own.** Running a perpetual task like claim-issue when its `gh` probe fails always toasted "couldn't complete the check just now (a transient forge/network issue) — try again shortly", which is only true for a momentary blip. A `gh` that isn't installed, isn't authenticated, or is blocked outbound by a local firewall fails identically on every future tick, so the advice sent you in a loop with nothing naming the actual fault — the firewall case is the worst of the three, since a denied `connect()` surfaces as "bad file descriptor" and reads like a local bug rather than a network block. The work detector already knew which CLI it ran and how the call failed, but a transient skip deliberately doesn't park, so that verdict had nowhere to go and was dropped at a debug log. It now travels the same route the park reason already does, and when the failing CLI is `gh` the toast reports its health with the remedy ("allow the gh binary to reach api.github.com", "run `gh auth login`", "install the GitHub CLI"). Attribution comes from the CLI that actually failed rather than the task-type name — `claim-work` picks its forge internally, and branch-reconcile and quota-burn go transient over git and provider faults with no forge involved, so a name-based guess would have told a GitLab or Ollama user to install the GitHub CLI. - **The weekly dependency-updates task now clears out open Dependabot PRs before bumping anything itself.** The prompt went straight to `npm audit` / `npm outdated`, so on a repo where Dependabot had already opened five PRs the agent re-did that work by hand — duplicate bumps that conflicted with the bot branches, and a growing pile of stale bot PRs nobody ever closed or merged. It now runs a triage phase first: list the automated PRs (Dependabot or Renovate, GitHub or GitLab), gather the evidence for each one — version jump, release notes checked against what this repo actually calls, CI logs for a failure, whether the diff is manifest-and-lockfile-only — and take a single verdict. A clean patch/minor gets merged; a stuck-but-wanted PR gets fixed (ask the bot to rebase a conflict, or push the smallest adapting change for a genuine breakage) and then merged; a superseded one is closed with a reason; a major that needs a real migration is left open with a comment and recorded in the repo's tracker. Repairs happen in a throwaway worktree rather than by checking the bot branch out in the app's live tree — this task runs in the working copy you use, so a checkout there would hijack whatever branch you were on — and a rebased bot branch is pushed with a lease instead of being unpushable. GitLab repos get `glab` commands throughout instead of `gh` ones aimed at whatever GitHub repo happened to be configured. Only then does it look for updates the bots missed, skipping any package whose bump a bot PR already owns. Existing installs on the previous default upgrade automatically.

The camera also frames itself to the whole graph on open and whenever a filter or search reshapes it, so no goal starts off-screen with its edges running into empty space.

## Review Hub

- **[issue-3282] Queue cards now preview their body in three lines instead of printing it whole** — Every card rendered its full untruncated body, so a queue of 59 pending items ran roughly 56 screenfuls on desktop and 197 on a phone, and one error card alone printed a URL, a full browser user-agent string and a stack trace inline. Card bodies are now a fixed three-line plain-text preview with a per-card "Show more" that expands the full formatted text in place, titles clamp to two lines so the queue scans as a uniform list, and Accept/Reject/Complete/Dismiss/Delete stay on the collapsed card so a decision never requires expanding. Long agent-authored bodies also no longer inject their own headings into the page's outline.

## Data Manager

- **[issue-3285] Every directory on the Data Manager now says what it holds and whether it is safe to remove.** Seven of the thirteen biggest rows — including the single largest one — were labelled "Unknown category", and because an unrecognised directory also fell back to "not archivable, not deletable", the cleanup page silently refused to act on the very things filling the disk. All ~65 directories PortOS creates under `data/` are now classified with a real description and honest archive/purge flags: LoRA training checkpoints and the managed Python virtualenv are purgeable and say what survives, while generated sprite art, training datasets and 3D meshes are explicitly protected as the only copy. A directory that genuinely has no classification now reads "Not classified — PortOS does not know if this is safe to remove" and explains that Archive and Purge are being withheld on purpose, and a new test fails the build if a future data directory ships without an entry.
- **[issue-3327] Images, videos and LoRAs can no longer be wiped in one click.** All three were marked purgeable, so a single confirm ran a recursive delete over the whole directory — even though those bytes are the only copy, and trained LoRA adapters are excluded from backup snapshots and cost hours of GPU time to retrain. LoRAs are now protected outright, and Images and Videos trade the all-or-nothing Purge button for a per-entry delete in the expanded file list, so reclaiming space stays possible without betting the whole folder on one confirmation. A new `purgeScope` flag records the distinction explicitly rather than overloading "deletable", the purge endpoint refuses a category-wide wipe for item-scoped categories instead of trusting the UI to hide the button, and an unrecognised scope fails closed.
- **[issue-3342] Purging scratch no longer pulls the rug out from under a job that is still running.** Image Cleaner scratch, LoRA training runs and the self-update control files are all genuinely reproducible — which is why they stay purgeable — but "reproducible" only holds when nothing is using them: wiping them mid-flight kills the inputs a queued render is about to read, deletes checkpoints out from under a live trainer, or loses the handle on a running update. Each of those three now carries a liveness probe wired to state PortOS already tracks (the image sweep's own active-job predicate, the training queue *plus* each run's detached-process handle so a trainer that outlived a restart still counts, and the same detached-process check the updater uses to refuse a second update). While a job is in flight the row swaps the Purge button for the reason it is withheld, and the endpoint refuses the whole-directory wipe with a 409 rather than trusting the UI to have hidden the button. A probe that cannot answer counts as busy — the delete is irreversible, so "could not verify" must not read as "nothing is running". Per-entry deletes and every category without a probe are untouched.

## Apps

- **[issue-3286] Delete is no longer the loudest button on an app row.** Every app card rendered `Archive`, `Manage` and a red-tinted `Delete` as three equal-weight buttons, so the most destructive and rarest action was the highest-contrast control on the page — sixteen permanently-armed Delete buttons stacked down the list, sitting a thumb's width from `Manage` once the row wrapped on a phone. `Archive` and `Delete` now live behind a per-row "…" menu (arrow keys, Escape, and 40px touch targets included), `Manage` is the row's single filled primary, the app name reads as an actual link, and deleting asks for an inline confirmation naming the app before anything is removed.
- **An app that terminates TLS on its own port no longer offers launch buttons that cannot connect.** A port serves one scheme, but the launch row derived its `HTTP` and `Dev UI` buttons from `uiPort`/`devUiPort` without checking them against `tlsPort`. A single-listener dev server that reads the shared Tailscale cert reports the same number for all three, so it rendered three buttons for one HTTPS listener — two of which were guaranteed to fail. Those two are now suppressed when the port is the TLS port, leaving the one that works; an app whose dev server genuinely runs on a separate plain-HTTP port still gets its `Dev UI` button. Worth knowing when an app looks unreachable: `.ts.net` is on the browser HSTS preload list, so a plain-HTTP app on a MagicDNS name is force-upgraded to `https://` and never loads, while PortOS still reports it `online` — that status is read from PM2 and does not probe the port.

## Media Collections

- **[issue-3311] A collection now records who created it instead of the grid guessing from its name.** The "auto-generated" ordering and badge shipped in #3283 reverse-engineered provenance on the client from four independent clues — a name prefix, an `Auto-…` description, a `uc-`/`sc-` id, or a universe/series link — so every new machine-created bucket quietly sorted as if you had made it yourself until someone remembered to extend that list. Collections are now stamped `auto` or `user` when they are created, existing ones were classified once by a migration, and the old clue-matching only runs for a record a peer on an older version has not stamped yet.
- **[issue-3312] The "file this into a collection" picker got the same treatment as the grid.** The popover you actually use to file an image or video still listed every collection in raw order with the full prefixed name in each row, so filing something meant scrolling a wall of identical `Creative Director: …` entries in a 240px-wide dropdown. Rows now use the same ordering as `/media/collections` — collections holding something sort above the auto-generated empties — and each row lifts the shared creator prefix into a small badge so the part of the name that tells them apart gets the full row width. Search matches its words in any order instead of demanding one contiguous substring. Empty collections are still listed, since filing *into* an empty collection is the whole point.

## UI Consistency

- **[issue-3319] Stacker News now says which account you are looking at, on every tab.** Territories, monitored items, and queued actions were always filtered to the selected account, but nothing on screen said so — the only hint was a small grey `@username` in the header, and the account list lived on the Accounts tab, so switching accounts meant leaving whatever you were working in. The header now carries an account switcher that works from any tab and keeps you on it, and every scoped heading and empty state names the account: "Communities for @…", "Approval queue for @…", "Add community to @…". The account form — nineteen fields that used to render twice at once, side by side, in one flat scroll — moved into the shared drawer, grouped into Identity, Monitoring & models, Stewardship, and Budgets tabs with the open tab kept in the URL. Because the drawer unmounts inactive tabs, Save re-validates every field itself and jumps to the tab holding the bad one instead of letting an emptied number box through as a zero.
- **[issue-3293] Sprite approve/lock confirmations, the near-black canvases, and the final music-video player now follow the shared conventions.** The shared `ConfirmButtonPair` had no positive tone, so the "Approve this walk" and "Freeze this reference version" confirmations in the sprite workflows hand-rolled their own confirm/cancel markup and each drifted on busy text, spinner, and touch-target height; a `success` tone closes that gap and five hand-rolled pairs now share one implementation, with a 36px minimum height on every pair in the app. The four piano-roll/ambient surfaces that hardcoded a near-black hex now say why they don't follow the theme — the rolls read their background from the same `ROLL_BG` constant their canvas paints with, so the CSS fallback can never drift from the painted pixels, and Ambient mode is explicitly `bg-black` because its white-on-black layers would be unreadable under a day theme. The rendered music video also reserves its 16:9 box like the scene thumbnails already do, so the Download row above it stops jumping when the video's dimensions resolve.

## Three.js Models

- **[issue-3350] Silhouettes with cutouts, bent details, and glass/cloth finishes no longer have to degrade into a coarse triangle mesh.** The scene schema could express primitives, a lathe, and a bounded custom mesh, so anything with a keyhole, a vent, a cable, or a bent handle either got flattened into a box stack or spent its budget on hand-authored triangles. Two schema-backed forms now cover that gap: `extrude` sweeps a closed 2D outline — with optional hole rings — to a depth with optional bevel, and `tube` sweeps a round profile along a Catmull-Rom path. Both are validated on the way in rather than trusted: a ring that encloses no area or crosses itself, a hole that falls outside its outline or overlaps another hole, a path that repeats a point consecutively, and a closed path that repeats its seam or cannot enclose a loop are all rejected, because each renders as an empty face, a stray disjoint face, or NaN geometry rather than an error. `physical` materials also gained bounded `ior`, `transmission`, `thickness`, `sheen`, `iridescence`, and `anisotropy`, so glass, gems, velvet, oil-slick, and brushed metal are material choices instead of approximations — parsed for every material type so a spec round-trips unchanged, but only handed to Three.js for physical ones. The generation prompt now says which form fits which subject and that custom triangles are the last resort, and the preview builds the new geometry through the same construction the downloaded standalone factory emits.
