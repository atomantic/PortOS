# Dashboard Widgets & Layouts (`client/src/components/dashboard/`)

Widgets are registered in `widgetRegistry.jsx` (`{ id, label, Component, width, defaultH?, needs?, gate? }`). The Dashboard renders the active layout's widgets from it. Named layouts persist in `data/dashboard-layouts.json` (owned by `server/services/dashboardLayouts.js`, `GET/PUT/DELETE /api/dashboard/layouts`); the built-ins (`default`, `focus`, `morning-review`, `ops`) are seeded on first read and can't be deleted. The `⌘K` palette synthesizes a `Dashboard: <name>` command per layout when it opens, so new layouts need no registration.

**Grid model.** A layout's `grid: [{ id, x, w, order, h?, fixedH? }]` places cells on 12 columns (`x`/`w`) plus a packing sequence (`order`). There is no stored row (#4133): `packVertically` lays cells out in pixels, each floating up under the nearest placed cell sharing a column, in `order`. An empty `grid` auto-flows via `synthesizeGrid` from each widget's `width` and `defaultH`. Below 640px container width the grid becomes one column in reading order (`order`, then `x`), never array order. `sanitizeGridItem`/`sequenceGrid` in `server/services/dashboardLayouts.js` still derive `order` from a legacy `y` on read, and `scripts/migrations/269-dashboard-grid-order.js` rewrites old files. **A new widget-seeding migration appends `{ id, x, w, order, h }`, not `{ x, y, w, h }`** (seed migrations before 269 still use `y` because they only run on pre-269 files).

**Height is measured, not declared.** A cell measures its widget with a `ResizeObserver`. `h` is only the first-paint fallback and what older clients (which don't know `fixedH`) read, so every drag commit refreshes it via `withMeasuredHeights`. A cell whose height the user dragged has `fixedH: true`, keeps `h` exactly and clips; the ⌃⌄ handle (edit mode, pinned cells) returns it to content height. `defaultH` is a first-paint ballpark (default `4`).

**Arrange mode (desktop).** Each cell gets move (top-right) and resize (bottom-right) handles. A move snaps to columns and re-inserts at the rank its drop position implies (`rankAtPixel` → `insertAtOrder`), renumbering `order` densely; Save persists to the layout's `grid`.

- **Handles are keyboard gestures too (#7263)**: Enter/Space lifts, arrows step, Enter/Space drops, Escape restores, matching dnd-kit's mobile handle. Pointer and keyboard share one placement path (`beginGesture`, `stepGhost`, `finishGesture`/`applyGhost`, the same `fixedH` rule), so a keyboard preview is the commit. The one divergence is deliberate: a horizontal keyboard move leaves `order` alone so ↑/↓ alone owns the sequence. The grid's `role="status"` region narrates keyboard steps and `aria-pressed` carries grabbed/idle. **A handle with `onPointerDown` and no `onKeyDown` is a WCAG 2.1.1 failure**; `DashboardGrid.test.jsx` fails on one.
- **A keyboard grab is modal**: anything that ends Arrange mode under it (Save/Cancel, a rotation across the breakpoint) must cancel it, since unmounting a focused handle fires no blur. One effect watching `editable`/`isMobile` owns that.

**Mobile reordering.** Free-form move/resize is desktop-only; on mobile, edit mode shows one reorder handle backed by `@dnd-kit/sortable` (`PointerSensor` + `KeyboardSensor` + `verticalListSortingStrategy`, as in `cos/tabs/TasksTab.jsx`). Never hand-roll a pointer gesture for it. Use `dndTransformToCss` from `client/src/lib/dndTransform.js`, never `@dnd-kit/utilities`, and keep `touch-action: none` on the handle. On drop, `onDragEnd` re-flows the grid through `reflowToOrder` (keeping each `w`/`h`), which re-packs the desktop layout into row flow; the edit-mode hint says so.

**The mobile/desktop seam has one source of truth.** `DashboardGrid` measures its own container (`useContainerWidth`), which is narrower than the viewport, so a Tailwind `sm:` breakpoint disagrees with it. Anything outside the grid that needs the live mode reads it from `onLayoutModeChange`.

**Widgets lay out by container query, never viewport breakpoint.** Put `@container` on the component's own root (not the grid cell, since the same component renders in drawers and full pages) and use `@sm:`/`@md:`/`@lg:`. Viewport variants are only for device affordances such as hover-vs-touch, and need an allowlist entry: `client/src/test/guards/ui/dashboardWidgetContainerConventions.test.js` fails on any bare `sm:`/`md:`/`lg:`/`xl:`/`2xl:` in a module `widgetRegistry.jsx` lazy-imports. `@container` makes the element a containing block for `position: fixed`, so a widget's fixed overlay is portaled to `<body>` (`Modal`'s `usePortal`).

**Widget order lives in the grid.** `saveGridEdit` rewrites `widgets` into `readingOrderIds(grid)`. `reconcileGrid` iterates the grid and uses `widgets` only for membership, so toggles and renames keep positions. LayoutEditor's Move up/down passes an explicit `reordered` flag from `save`/`commitDuplicate`, computed by `isReordered()` against the `unmovedOrder` ref (`add` appends to it, `remove` filters it, `move` leaves it), and `Dashboard.jsx` forwards it as `reconcileGrid(base, widgets, { reorder })`. **Never infer the flag by comparing `widgets` to `readingOrderIds(grid)`**: older layouts can disagree, and inferring would re-pack an arranged layout on an unrelated save (#4132).

**Adding a widget:**
1. Add an entry to `WIDGETS` in `widgetRegistry.jsx` with a stable kebab-case `id` (stored in layouts) and a rough `defaultH`.
2. Read dashboard data (apps/health) from the `dashboardState` prop rather than fetching it again, and list the streams it or its `gate` reads in `needs`; only widgets that declare `needs` get the prop, and the page fetches only the streams the active layout needs.
3. Add `gate: (state) => boolean` if it only makes sense sometimes.
4. Add its id to the built-in `default` layout in `server/services/dashboardLayouts.js` if it should appear out of the box.

**First paint comes from a local copy (`dashboardBoot.js`).** The last server-confirmed layouts response is cached in `localStorage`, so a reload paints the grid and starts widget chunks before `GET /api/dashboard/layouts` returns, while data reads wait for a known layout so they don't queue ahead of it. The cache is display-only: the picker, Arrange and the editor stay hidden until the server copy lands, and it is never written back.
