# Server conventions (`server/`)

These apply to Express/service/model code. The root `AGENTS.md` rules (error handling outside the request lifecycle, functional programming, single-line logging, Security Model, storage policy, AI Provider Usage Policy, Sensitive Data & Privacy) always apply. Rules marked *enforced* have a tree-wide test that names the offender; unless noted, it has no allowlist.

## Validation and schema parity

- **Schema parity when adding fields.** A field added to a sanitizer, `createXxx` or payload shape gets its Zod schema in the same change (`server/lib/aiToolkit/validation.js` for toolkit shapes, `server/lib/validation.js` for PortOS routes), wired into POST and PUT (`schema.partial()` for PUT); an unwired sub-schema is false confidence. Polymorphic stores like `PUT /api/settings` validate the present slice with `schema.partial()` (see `backupConfigSchema.partial()` in `server/routes/settings.js`). Tolerate UI sentinels (`endpoint: ''`) with `z.preprocess(v => v === '' ? undefined : v, …)`. When a service migrates legacy keys on read, the schema still accepts the legacy shape.
- **A POST/PUT/PATCH handler reading `req.body` validates it with a schema** (`validateRequest(schema, req.body ?? {})`, schema in `server/lib/validation.js` or the domain `*Validation.js`), not a hand-rolled check. *Enforced:* `server/routeValidationConventions.test.js` over `server/routes/`, `lib/aiToolkit/routes/` (schemas in `lib/aiToolkit/validation.js`) and `cos-runner/index.js` (`requestSchemas.js`). Its `ALLOWED_UNVALIDATED` list (raw-binary and multipart bodies) may only shrink; never add a JSON-body handler (#9950).
- **A handler reading `req.query` validates the query object** on any method (`validateRequest(schema, req.query)` or `validate` / `parseBody` / `safeParse` / `Schema.parse` on the query object or a name assigned from it, not one field and not `req.params`). `parsePagination(req.query)` only clamps and doesn't count. `UNVALIDATED_QUERY_BASELINE` in the same test only shrinks: delete a line when its handler validates or disappears, and never add one (#10024).

## Offering models vs running them

**A caller that offers a model choice reads `getSelectableProviders()` / `listSelectableProviders()`; a caller that executes, accounts or writes reads `getAllProviders()` / `listProviders()`.** The selectable pair narrows `models` to the install's declared entitlement (`docs/MODEL_ACCESS.md`, `lib/aiToolkit/internal/modelAccess.js`). Picking wrong fails silently either way: a picker on the unscoped list offers models the account can't run, and a write on the scoped list persists a truncated catalog. Route payloads shaped by `presentProvider` are already scoped; direct service reads are not.

## Write serialization and throughput

- **Serialize writes that can race on a shared record server-side**, at the file level: every PATCH awaits the previous one before reading state. Client guards (refs, `onMouseDown`, status checks) are unreliable. A `Map<recordId, Promise>` is not enough when records share one state file; use one tail per file. Example: `queueSeriesIssuesWrite` in `server/services/pipeline/issuesShared.js` (built on `createKeyCachedQueue`).
- **High-frequency state writes batch.** A per-line `withStateLock → loadState → saveState` mutation (e.g. `appendAgentOutput` in `server/services/cosAgentLifecycle.js`) is fine at human pace but not from PTY output or tool-call streams. Add a batched variant taking an array (`appendAgentOutputLines`), flush on a ~250ms debounce, and drain the buffer in the producer's finish/cleanup before the final state write.

## PostgreSQL parameters

**Serialize a `json`/`jsonb` parameter with `toPgJson`, never bare `JSON.stringify`.** Postgres rejects a lone UTF-16 surrogate or NUL in `jsonb` (and NUL in `text`), which old file stores accepted, so an unrepaired write throws and the record is lost (#12815). `toPgJson` and `normalizePgString` in `server/lib/pgJson.js` repair to U+FFFD. `lib/db.js` normalizes plain parameters on every `query()`, but a pre-stringified JSON string looks like text to it. *Enforced:* `server/pgJsonConventions.test.js` (frozen `scripts/db-migrations/` are skipped).

## Async boundaries

- **An `async` timer callback owns its rejections**: every `await` inside `setTimeout(async …)` / `setInterval(async …)` has an enclosing `try`/`catch` or a `.catch(…)`, because an unhandled rejection is fatal on Node ≥15 (#5668). Log and continue unless the callback owns a failure verdict. *Enforced:* `server/timerCallbackConventions.test.js`; example: the watchdog in `server/services/mediaJobQueue/index.js`.
- **A statement-level call to an `async` function is `await`ed, ends in `.catch(…)`, or starts with `void`** (`void` means it already owns its rejections). A bare call's rejection becomes an `unhandledRejection` that `autoFixer` turns into an AI task (#12978). *Enforced:* `server/floatingAsyncConventions.test.js`.
- **An `async` Socket.IO handler owns its rejections** the same way (whole-body `try`/`catch` as in `voice.js`, or `.catch` on the awaited chain as in `logs.js`); an escaped rejection terminates the process (#5661). *Enforced:* `server/sockets/asyncHandlerGuard.test.js`.
- **Attach a spawned child's terminal listeners before the function next `await`s.** A failed spawn reports on `process.nextTick` and a fast child can exit while you're suspended: an unlistened `error` crashes the process and an unlistened `close` strands the job `running`. Do awaited work before `spawn()`, or call `bufferChildExit(child)` (`services/videoGen/generateVideoHelpers.js`) in the same tick and replay its result (`services/imageGen/local.js`) (#11761). *Enforced:* `server/childListenerOrderConventions.test.js`.

## Tests and peer fan-out

Record create/update paths reach peer sync only through the subscription adapter in `server/services/sharing/recordEvents.js`, a no-op until `peerSync.js` registers at load. A suite that loads the peer-sync graph (`peerSync.js` or `sharing/index.js`, even transitively) mocks `services/instances.js` with `mockNoPeers()` and `services/sharing/peerSync.js` with `mockNoPeerSync()` from `server/lib/mockPathsDataRoot.js`. To assert auto-subscribe in a domain test, register a double with `registerSubscriptionAdapter({...})` and reset with `__resetSubscriptionAdapter()`.

## Import scoping

Import cost multiplies, because every suite reaching a module instantiates its whole closure. `server/lib/importScoping.test.js` pins past narrowings as reachability assertions (add a row when you narrow another); measure fan-out with `node scripts/lib/importReach.js <repo-relative source>`.

- **Don't drag a subtree in for one constant.** Import from the declaring module (`CHECK_SCOPES` from `server/lib/editorial/checkInfra/taxonomy.js`, not the `checkRegistry.js` barrel), and `await import()` a dependency only a boot/rare path needs (`ensureSchemaImpl()` composes DDL that way).
- **A lazy `import()` cuts instantiation, not CI selection**: `vitest related` follows dynamic imports too (#12285). To cut selection, move the needed piece into a leaf both sides import (`services/readinessSignal.js`), or have the heavy service register a callback at boot (`initAutoFixer()` → `services/providerRecoveryHooks.js`). Cut edges are pinned in `SELECTION_CUTS`; a suite that `vi.mock`ed the heavy module registers test doubles instead.
- **Outside an async scope, defer with `import('./x.js').then(…).catch(handler)`** (how `services/promptRunner.js` defers `tuiPromptRunner.js`), ideally inside an existing predicate gate (`runner.js` defers `ollamaAgentContext.js` in the `isOllamaBackedProvider` ternary).
- **The tree-wide guard is base-relative growth**, computed by `scripts/lib/importGrowth.js`: the summed closure growth of suites existing on both sides, against the merge base, must stay under `EXISTING_SUITE_GROWTH_LIMIT` (2,500); new test files don't spend it, and a missing base fails. On failure, narrow or defer the import. Raising the limit is the intentional-regression path: same change, name the module that can't be deferred, and stay under the band the pin test enforces. CI and pregate run it with the planner's `CI_BASE_SHA`. Release promotions keep CI's aggregate policy: pregate's selected `release` refs (`release`, `origin/release`, `refs/heads/release`, `refs/remotes/origin/release`) are exempt from this limit only.
- **Never narrow an import around a barrel a suite mocks.** `vi.mock('./cos.js')` intercepts the specifier, so re-pointing a caller at `./cosTaskStore.js` makes production hit the real code while the suite thinks it's doubled. Grep for `vi.mock` of the module you're leaving first; a lazy `await import()` has no such hazard.

## Generated manifests

- **Derive at first use before committing a manifest.** Deterministic, cheap, shipped-input inventories are computed in memory behind a per-process cache (`server/lib/apiRouteGraph.js` scans routes in ~50ms on first request; `socketEventInventory.js` likewise). A committed copy is justified only when derivation is slow, nondeterministic or needs inputs an install lacks (`promptStageCallSites.generated.json`).
- **A checked-in manifest is addressed by content, never position.** Key each record by declaring file plus semantic identity (stage key plus file paths), never `foo.js:412`, which churns on unrelated edits and conflicts on every rebase. Positional detail may stay in memory (`routeDeclarationKey` in `server/lib/apiRouteGraph.js`).
- **Prove it with `shiftSourceText`** (`scripts/lib/positionInvariance.js`): shift the inputs, regenerate, require byte-identical output. `server/lib/generatedManifests.test.js` backstops the tree by scanning tracked `*.generated.json` for position-shaped keys and failing when a `scripts/*.js` writing one has no sibling test importing `positionInvariance.js`.

## Prompt templates

- **Stage-prompt template changes need a migration.** `scripts/setup-data.js` only copies missing prompt files, so a change to a `data.reference/prompts/stages/*.md` file (e.g. a new `{{template.variable}}`) ships with a `scripts/migrations/NNN-…js` built on `makePromptReplaceMigration`, exporting `ACCEPTED_OLD_MD5` / `NEW_SHIPPED_MD5`, that updates installed copies whose hash still matches a shipped version. Hash with normalized line endings. Never hand-mirror hashes into `scripts/setup-data.js` (`buildPromptDriftTables` sweeps the exports). Re-point earlier migrations naming the same file at the new hash and keep the superseded one in the accepted set (`_shippedHashDrift.test.js`). `makeSeedMigration` only copies missing files. Example: `scripts/migrations/394-factual-extraction-lens-prompts.js`.
- **A migration's number is an ordering hint; its filename is its identity.** The applied-list keys on the filename and the runner sorts lexically, so a duplicate numeric prefix is legal and needs no renumbering. Order a new migration after the ones it depends on. Renaming or deleting a migration already on the base branch re-runs or drops it on every install that applied it, so `scripts/migrations/migrationFilenames.guard.test.js` fails on it; a retirement goes in its reviewed `RETIRED_MIGRATIONS` list.
- **A new migration is a frozen snapshot of its transform**: it imports `_lib.js` primitives, `server/lib` pure helpers or a frozen copy, never `server/services`; declares no local copy of a `_lib.js` helper (`readJsonOrNull`, `writeJsonAtomic`, …); and writes any `purge: true` marker as a top-level property of the default export. *Enforced:* `scripts/migrations/migrationConventions.guard.test.js`.
- **A `PROMPT_VERSIONS` bump for a scheduled-task prompt needs no migration**: run `node scripts/regen-prompt-integrity-snapshot.js`, and `readSchedule()` in `server/services/taskScheduleStore.js` upgrades uncustomized stored prompts (in `data/cos/task-schedule.json`) on the next load. Six old migrations rewrote a `task-schedule.json` path the store never reads; they stay, but `scripts/migrations/promptBumpMigrations.guard.test.js` fails on a seventh.
- **Creative prompts get the IP-latitude clause by classification, not by wrapping call sites.** PortOS is an artist's tool: a model that genericizes or disclaims a deliberate reference to existing IP produces defective output, and clearance is the operator's job. `server/lib/creativeLatitude.js` owns the clause and the table classifying what gets it, applied at the three transports: `promptService.buildPrompt` (by stage name, failing safe), `promptRunner.runPromptThroughProvider` (by the run's `source` tag, an allowlist), and `aiProvider.callProviderAISimple` (callers pass `creative: true`). A new creative stage or LLM-calling service is covered once its name or `source` is classified there; `creativeLatitude.test.js` and `creativeLatitude.sources.test.js` fail on unclassified entries. A caller budgeting context before the stamp reserves `CREATIVE_LATITUDE_TOKENS`. **The clause is shown, never hidden (#11317)**: where the user typed the text the LLM receives, the service stamps with `withCreativeLatitude` itself and returns the sent text plus `CREATIVE_LATITUDE_ADDITION` as `promptAdditions` for the client's `SentPromptPanel` (example: `services/mediaPromptRefiner.js`).
