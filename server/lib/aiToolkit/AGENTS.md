# AI Toolkit (`server/lib/aiToolkit/`)

The AI provider/runner/prompt toolkit is vendored in-tree here. (It was previously the `portos-ai-toolkit` npm package.) Keep the directory self-contained — no imports out to other PortOS modules — so future upstream syncs don't fight local edits.

**Key points:**
- `index.js` exports `createAIToolkit`, `createProviderStatusService`, the four Router factories (providers / runs / prompts / providerStatus), and the context-fit pair `knownContextWindow` / `contextWindowRejection` — the host applies the same rule to the EXPLICITLY requested provider, which `getFallbackProvider` never sees. Both answer `null` for an unknown window, which every caller must keep reading as "no constraint"; nothing infers a window from a model id.
- **The Ollama `num_ctx` ceiling is declared ONCE, in `internal/ollamaBacked.js`** (`clampToRuntimeContextWindow`), beside the predicate that gates it. `knownContextWindow` applies it through that helper and must never restate the `Math.min` inline — the host's prompt budgeter (`server/services/stageRunner.js#effectiveContextWindow`), the untrusted-content abuse guard (`server/services/untrustedContent.js#runUntrustedContentAnalysis`, which held its own hand-rolled `Math.min` pair until #7473) and the browser's provider-card meter call the same function, and when the rule was stated twice they drifted (#7466). It is an upper BOUND over every planning rung, a user's explicit `contextWindow` included, and the answer outright when nothing else declared one. Host callers import the `internal/` leaf directly, or `knownContextWindow`/`contextWindowRejection` straight off `providerStatus.js` (both deep imports skip the public barrel's `fs`/`child_process` reach): `stageRunner.js` sits inside the server suite's import budget, and `untrustedContent.js` — a request-path module — deliberately imports `providerStatus.js` rather than `stageRunner.js`, whose own closure would cost that budget ~40 extra module instantiations per reaching test file for no behavior it needs.
  - **A rung of that ceiling this directory cannot resolve arrives as DATA, never as an import out.** PortOS also sets the daemon-wide window through the ambient `OLLAMA_CONTEXT_LENGTH` (`server/lib/ollamaContext.js#resolveOllamaContextLength`), which the toolkit may not reach and the browser cannot read at all — so the host resolves it and stamps it onto an in-memory provider projection with `withRuntimeContextWindow`, declared in the same file as the clamp that reads it. `runtimeContextWindow` ranks BELOW `provider.numCtx`, exactly as `resolveOllamaContextLength` ranks the two, and is never persisted to `providers.json` (it describes the process running right now). Adding another host-resolved rung follows the same shape: stamp a field beside the reader, do not import out. Precedent: #7472.
- Provider configuration (models, tiers, fallbacks) lives in `providers.js`
- `loadProviders()` auto-migrates legacy codex configs to the `codex-configured-default` sentinel; `server/index.js` warms it at startup so the rewrite happens before any request
- PortOS extends toolkit routes in `server/routes/providers.js` for vision testing and provider status (status routes live in PortOS, not the toolkit, because they call PortOS-side socket helpers)
- When adding new provider fields (e.g., `fallbackProvider`, `lightModel`), update `createProvider()` in `providers.js`
- `updateProvider()` uses spread so existing providers preserve custom fields, but `createProvider()` has an explicit field list
- **Refreshing more than one provider goes through `refreshProviderModelsBatch(ids)`, never a loop over `refreshProviderModels(id)`.** Every single-provider refresh ends in `saveProviders`, which invalidates the read cache and rewrites all of `providers.json`; an N-provider fan-out that way is N full-file writes, each superseded by the next. The batch form groups by `ollamaRefreshGroupKey` (one probe per daemon + probe shape), probes each group's lead without persisting, then applies every result and saves **exactly once**. It never throws for a per-provider failure — each group carries its own `status` (`updated` / `failed` / `missing`) so the host logs one line per group rather than one per member. PortOS's post-install fan-out (`refreshOllamaBackedProviders` in `server/services/localLlm.js`) is the worked example.

**A provider's MODEL ACCESS policy scopes on READ, never at refresh.** `internal/modelAccess.js` owns which of an upstream's advertised catalog an install is entitled to run — the thing a `/models` response cannot tell you (NVIDIA NIM answers with its whole product line and no tier field, so its free endpoints are indistinguishable over the wire). Three rules hold it together, and each has already been the bug the other way round:

- **The stored catalog is never narrowed.** `applyModelAccess` runs at the route (`routes/providers.js` here, `presentProvider` in the host), so `providers.json` keeps the real list and a cleared policy restores it with no re-probe. The scoped payload carries the original as `modelCatalog` — **the provider editor seeds its model textarea from that**, because it saves the box verbatim and would otherwise persist the narrowed list over the real one.
- **`all` and an empty pattern list both mean NO CONSTRAINT** (the root AGENTS.md sentinel rule). A mode picked before any pattern is typed is a half-finished edit, not an instruction to blank every model picker in the app. A stored `{ mode: 'all', patterns: [...] }` is a PARKED list and must keep its patterns.
- **A model the record NAMES is never hidden** (`defaultModel`, the four tiers, `fallbackModel`) — a picker whose stored value is missing from its options renders blank and re-points the provider on the next save.

Inheritance mirrors `withGatewayApiKey`: a gateway-backed wrapper with no policy of its own takes the sibling gateway record's, resolved on read into `modelAccessEffective` / `modelAccessSource` — two derived field names, not the persisted `modelAccess`, because that one IS in `providerSchema` and a client echoing a GET back on a PUT would pin the inherited value forever. Composition order against `withGatewayApiKey` is load-bearing (that helper attaches the key NON-enumerably, so a spread after it drops the credential). A write response carries the resolution forward from the read the route already performed (`withResolvedModelAccess`) rather than re-reading — several suites drive those routes with a service double whose `getProviderById` answers a different fixture. Glob matching is a hand-rolled iterative matcher, not a translated RegExp: the patterns are user input (`*a*a*a*b` backtracks exponentially), and a translation would have to re-inline the escape `server/lib/textUtils.test.js` forbids — which this directory cannot import its way out of. Contract and field list: `docs/MODEL_ACCESS.md`.

**Provider-service extension point.** `createProviderService` / `createAIToolkit` accept `onProvidersSaved(data)`, invoked after every SUCCESSFUL `providers.json` write with the data that landed. PortOS injects it in `server/services/bootstrap.js` to keep its machine-local provider connection graph (`server/services/providerGraph.js`, #6367) reconciled with a file that a legacy `PATCH /api/providers/:id`, a model refresh, a migration or a downgraded release may also write. The hook is deliberately non-fatal: the write already landed and the cache already reflects it, and callers include boot warmups and schedulers with no `next(err)` to bubble to, so a throwing hook is logged and swallowed. Pair it with `applyProviderPatches(patches)`, which applies partial updates to SEVERAL named records in ONE write and — unlike `updateProvider` — performs no sibling fan-out, because a projection must touch exactly the routes it named and no conventional neighbour.

**Runner extension points.** The runner exposes a small declared override surface (in `runner.js`) so the host (PortOS) supplies its own runners without reaching into private internals:

- `setCliRunner(fn)` / `setTuiRunner(fn)` — register host CLI/TUI runners (pass `null` to revert). PortOS calls both in `server/index.js`: its CLI variant is stdin-based and knows the per-CLI argv conventions (Codex `exec -`, Antigravity `agy --print`, Claude Code `-p -`); the TUI runner has no toolkit built-in, and `setTuiRunner` attaches/detaches `executeTuiRun` so the runs router's `typeof runnerService.executeTuiRun === 'function'` gate stays honest.
- `registerExternalRun(runId, killable)` / `unregisterExternalRun(runId)` / `hasExternalRun(runId)` — track host-spawned child processes / ptys. The toolkit's own `stopRun`, `isRunActive`, and `deleteRun` consult this registry *first*, so **a host runner that spawns its own process MUST register it here** (PortOS does this in `services/runner.js`) — otherwise the runs router reports live runs as inactive and refuses to stop them, and deleting a live run leaks a zombie process. `stopRun` also stamps a one-shot marker consumed through `consumeExternalRunStop(runId)` before unregistering, which lets the host classify the resulting signal as cancellation instead of a provider failure. That classification rides out to callers as `canceled: true` on the run metadata and `code: 'RUN_CANCELED'` on the rejection the prompt runner raises — **anything that turns an LLM failure into a verdict (a pause kind, a filed gap/investigation task, a provider bench, an `error` status) must call `isRunCanceledError` from `errorDetection.js` first**, or it files bug reports about a human pressing Stop. **`executeApiRun` keeps its own equivalent marker internally**, because its killable is an `AbortController` whose reason-less `abort()` reaches the finalizer as Node's bare `AbortError: This operation was aborted` — a message no pattern matches, so every Stop of an API run finalized as an UNKNOWN provider failure, fired `onRunFailed`, and was escalated to a tier-4 investigation task. It now writes the same `canceled` / `completionReason` terminal shape the CLI path does and fires no failure hook; a timeout still outranks it, since the timer's own abort is what ended that run. No sibling-method monkey-patching is needed: adding a new lifecycle method (e.g. `pauseRun`) just means having it consult `externalRuns` too.
- `createProviderStatusService({ prerequisitesMet })` — host gate for "can this provider run AT ALL?" (its CLI binary present). `getFallbackProvider` consults it on every candidate: task-level, configured, and system-priority alike. Injected rather than computed here because the answer needs host I/O (a PATH probe) and this directory stays self-contained; PortOS supplies `prerequisitesMetForRouting` from `services/providerPrerequisites.js` in `bootstrap.js`. It MUST be synchronous, and a missing / throwing / non-boolean answer deliberately reads as "yes" — an unknown answer has to route exactly as it did before, because emptying the fallback chain is a far worse failure than the late ENOENT the gate exists to prevent.
- Time-based state transitions need read-side mirrors. `providerStatus.init()` clears expired `estimatedRecovery` entries; every reader (`getStatus`, `getAllStatuses`, `isAvailable`) must re-apply the same recovery check on read — otherwise providers stay "unavailable" past their recovery deadline until the next process restart.

**`provider.timeout` is a NO-PROGRESS bound in `executeApiRun`, not a wall clock.** A streaming run carries two ceilings, and conflating them is what #7560 fixed: one wall-clock timer could not tell a provider that opened the stream and stalled from one that was actively streaming and merely slow, so a reasoning model spending its whole budget in the hidden channel (NVIDIA NIM's nemotron sends 126 of 128 frames as `reasoning_content`) was killed mid-generation at 300s alongside genuinely dead upstreams.

- **Stall bound** = `timeout || provider.timeout || DEFAULT_API_RUN_TIMEOUT_MS`, re-armed by every `reader.read()` that yields bytes. It is the hang detector, and it cuts a silent provider off at exactly the moment the single timer did — reinterpreting the field this way costs no protection, because catching a hung provider is the only job that timer ever actually did.
- **Absolute cap** = `Math.max(DEFAULT_API_RUN_MAX_RUNTIME_MS, stallBound)`, never extended, so a provider trickling one byte per minute still cannot hold its `activeRuns` slot forever. The `Math.max` is load-bearing: an install that deliberately raised `provider.timeout` past the default cap must keep running as long as it asked to, never be clamped DOWN by a ceiling it never configured.

Only the STREAMING path reads the field this way. `aiProvider.js`, `askService.js`, `services/runner.js` and `promptRunner.js` are non-streaming and keep reading it as a wall clock, which is correct there — no persisted field changed shape, so no migration and no schema parity work is owed. Both bounds finalize through the same `markSettled()` / `finalizeTimeout(bound)` pair, so the single-settlement gate, Stop-marker handling and reasoning salvage are shared. **`finalizeTimeout` names which bound fired** in the message and in `metadata.timeoutBound` (`'stall'` | `'absolute'`), because the two are different diagnoses — a provider that went quiet is a bench candidate, one that outran its budget while producing is not. Neither message may contain the literal `"timeout"`: `analyzeError`'s NETWORK_ERROR pattern matches that substring and is tested BEFORE the timeout pattern, so it would misclassify the run as a connectivity fault. `"timed out"` is the phrase that reaches `ERROR_CATEGORIES.TIMEOUT`.

The worked example for "barrel + documented exports" (see root `AGENTS.md` → Module Organization) is this directory's `index.js`.
