# FastH3 V2 image-to-video: no Apple Silicon model can take the adapter

Date: 2026-09-22

Issue: [#7828](https://github.com/atomantic/PortOS/issues/7828) (child of [#7805](https://github.com/atomantic/PortOS/issues/7805))

## Verdict

Do not add a PortOS-only first-frame adapter on the pinned FastH3 MLX path, and do not swap in another published checkpoint to unlock image mode on the V2 rows. The V2 student weights do accept first/last-frame conditioning, but only through ComfyUI. Every MLX runtime that can anchor a frame loads a different DiT: the base MiniMax H3 FL2VA transformer, not `FastVideo/FastVideo-FastH3-8-Step-V2`.

Image-to-video on Apple Silicon stays on the existing MiniMax H3 MLX rows (`minimax_h3` runtime, modes `image` and `fflf`). Those rows keep the base model's reference schedule. They are not a substitute for V2's eight-step ladder or its 80% VSA.

Preview v1 was distilled for text-to-video-and-audio only. V2 changed that on the Comfy path: one checkpoint serves both text and first/last frame, with VSA keep-percent 10 (80% sparse), 24 fps, and the 17k+5 frame grid. That is capability evidence for the weights. It is not an MLX API.

A mask-and-latent adapter written only in PortOS would have to reimplement Comfy's keyframe encode (`MiniMaxH3ImageToVideo` stretches the first frame, cover-crops the last, VAE-encodes both, and pins them on the conditioning sequence) inside `fastvideo/mlx_runtime/minimax_h3_pipeline.py`, which has no image latent, first-frame mask, or conditioning-row hook. That is the algorithm change #7828 already deferred, and it still cannot be checked against an Apple Silicon render of the upstream path because that path does not exist.

## Contract to wait for

Reopen implementation when FastVideo's MLX entry accepts a first frame (and, if they ship it, a last frame) on this checkpoint and preserves all of the following:

- repo `FastVideo/FastVideo-FastH3-8-Step-V2` at `3da2ddfe1954d9cda4c05b643dc0f26007a655c5` (or a successor whose `fastvideo_inference.json` still names the eight-rung ladder)
- video/audio scheduler shifts from that sidecar (video shift 10)
- VSA sparsity 0.8, tile 64, routing weights retained by `--include-vsa`
- the existing quantization cache identity (`int8` / `int6` converted DiTs)
- synchronized audio at 24 fps

Until that entry exists, `scripts/generate_fastvideo.py` keeps rejecting `--image` for `family=fasth3`, including V2. Enabling the picker would render a text-only clip.
