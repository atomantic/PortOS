# Security risk assessment

Use this policy with [AGENTS.md](../AGENTS.md#security-model) for PortOS; a managed application may have a different trust model. A security scanner, dependency advisory, unsafe-looking API or missing validation is a candidate for investigation, not proof of an exploitable security finding. Do not suppress scanners or change dependencies solely to silence a report.

## Establish the boundary

For each candidate, identify the attacker and their actual control, entry point and data flow to the vulnerable sink, relevant configuration and existing controls, and the resulting unauthorized impact. Cite source paths and tests or a safe synthetic reproduction; distinguish a source-traced path from a demonstrated exploit. Check advisory status, affected versions, installed dependency path and how the affected behavior is invoked. Development-only does not by itself make a dependency safe: a compromised package or install/build script can execute with developer or CI authority even when it processes no untrusted input.

PortOS is a single-owner system, not a multi-tenant service. The owner and delegated agents acting within their grant are trusted operators; intentionally powerful owner features are not vulnerabilities merely because an operator can provide a dangerous value. An accidental hang, malformed owner input or data loss can still be a reliability or data-safety issue with concrete impact. Classify and route it accordingly rather than inventing an attacker or disabling the feature.

Single-owner does not mean all data or callers are trusted. Trace malicious dependencies, imported files, retrieved content, third-party APIs, model output and unauthorized LAN/tailnet callers to their actual sinks. Consider browser origins, CSRF and DNS rebinding against local services, including password-free defaults. A loopback address or private network alone does not prove browser-origin access is safe. Check any explicitly configured exposure or alternative deployment separately: report its prerequisites and impact as a conditional risk, and do not assume it is enabled or authorized. The prohibition on publicly exposing PortOS administration remains in force.

## Existing external-content guard

Use the existing model-abuse guard for relevant untrusted ingress, not as a generic gate on trusted owner input. Owners may also choose **Check content** in Models → Abuse Guard to scan any pasted text, including trusted content; this runs the local abuse scan, not the separate GitHub contribution assessment. Reuse the guard where the actual path invokes it. `server/lib/untrustedContentSources.js` lists the source policies for GitHub issue/PR/notification, Stacker News, Moltbook and messaging (including email, iMessage and Signal); the name of a source alone does not prove every ingress or downstream use is screened. Some GitHub intake paths exclude trusted collaborators using forge-verified repository ownership or write permission (including for the authenticated account); treat each author and mixed-source contribution separately, and do not infer project trust from a display name, label or content. Trace the particular call site, complete input, settings and subsequent authority. `screenUntrustedContent` applies deterministic screening and a configured classifier (required by default, optionally absent when configured); the GitHub issue/PR path also requires a separate security-model assessment. The guarded analysis uses a tool-free API transport, with private messaging constrained to local endpoints. Failures and blocks must retain their actual behavior and evidence.

Issue reconciliation verifies the author's repository authority, then scans the complete issue body and outside discussion together once before releasing the requirements and verified merge identity to maintenance. This deliberate mixed-content check includes third-party text quoted in the issue; it does not inspect attachment contents. Authorship alone does not establish the provenance or safety of quoted or attached material. The requirements are not duplicated in the scan input.

Trusted-author exclusion from external-intake queues does not skip the separate pre-merge assessment: it screens the complete PR and linked-issue evidence, whose provenance can be mixed. Do not infer that a trusted PR opener authored every commit, linked issue or external comment.

Screening is a layer against model abuse, not proof content is benign or authority to execute it. It does not replace path, parser, browser, network, package-integrity or authorization defenses. Imported files, arbitrary web content and other paths must not be assumed to pass through it. Preserve existing gates and use them for covered workflows rather than introducing a redundant guard.

## Disposition and reevaluation

- **Actionable security finding:** evidence supports attacker control, a reachable sink and unauthorized impact under the stated configuration. Fix the crossing, preserving legitimate owner and delegated-agent workflows, and test both refusal and authorized operation where applicable.
- **Conditional risk:** the path requires a specific exposure or configuration. State those prerequisites and assess them against supported and prohibited deployment policy; do not silently treat a hypothetical setup as the default.
- **Reliability/data safety:** concrete accidental harm without an unauthorized actor belongs in the appropriate quality category; retain its evidence and severity.
- **Not applicable or withdrawn:** record the advisory/finding, current evidence, affected path and why the required control, reachability or impact is absent. Reevaluate when the advisory, dependency/version, call path, trust boundary, deployment or exposure changes. Do not repeatedly file or remediate the same unchanged disposition; search current and closed issues and prior decisions first.
- **Unconfirmed:** explicitly record missing evidence and the next verification step. Absence of proof is not proof of safety; do not mark it resolved or score it as a verified defect.

The withdrawn picomatch advisory GHSA-fc5q-39xc-vjpf illustrates the process: issue #16751 was closed after fresh audits were clean. An owner-configured watch glob is not evidence of an attacker-controlled input path. Reassess if upstream status or reachability changes; do not add an arbitrary override for the withdrawn advisory. This disposition does not exempt other picomatch paths, other advisories, or package compromise.
